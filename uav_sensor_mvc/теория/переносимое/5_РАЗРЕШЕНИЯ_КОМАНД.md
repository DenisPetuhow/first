# Разрешения на команды: что делать самому, а что спрашивать

> **Правился:** 14.09.2026 — §0: два режима работы, «без остановок» включён; ⚠️ §1–§4
> описывают режим «с подтверждением» и не сверялись с 06.09.2026.

> **Зачем правило.** Каждый запрос разрешения — это остановка: помощник замирает,
> человек переключается, раунд тратится. Но и обратное плохо: молча запускать
> долгие расчёты или трогать историю git нельзя. Правило разделяет одно и другое.

## 0. Два режима работы — переключаются командой

**Заведено 14.09.2026 по команде заказчика:** «разработай новый режим работы для себя без
остановок, ты всё делаешь кроме коммитов и пушей … чтобы меня не спрашивать».

| | ⏩ **без остановок** (действует) | ⏸ **с подтверждением** (до 14.09.2026) |
|---|---|---|
| включить | `/bez-ostanovok` | `/s-podtverzhdeniem` |
| файл режима | `.claude/режимы/без_остановок.json` | `.claude/режимы/с_подтверждением.json` |
| без вопросов | **всё**: `Bash`, `PowerShell`, `Edit`, `Write` целиком; прогоны, пересборка данных, сеть, документация | разведка, проверки, свои скрипты — поимённо (§3) |
| спрашивается | `git commit`, `git push`; страховка: `checkout` / `restore` / `reset` / `clean`, `rebase` / `merge` / `branch -d`, `rm -r`, `Remove-Item`, `pyinstaller` | перезапись данных участка, сеть, долгие эталонные прогоны, вся история git, удаление |
| документация | по правилам `CLAUDE.md` **сразу**, без вопроса «обновить?» | назвать разделы и ждать ответа |
| итог | одно уведомление в конце серии | по ходу |

Команда копирует файл режима в `.claude/settings.json` и проверяет JSON; правила
поведения на время режима записаны в самой команде (`.claude/commands/*.md`).

⚠️ **Почему коммит не проскочит при разрешённом `Bash` целиком.** Claude Code сверяет
правила в порядке **deny → ask → allow**: совпало с `ask` — вопрос, даже если `allow`
разрешает весь инструмент. Составная команда `a && git commit` проверяется по частям.

**Пример.** `python tools/reference_cases.py` — выполняется молча (раньше спрашивался);
`git add -A && git commit -m …` — `git add` проходит, на `git commit` всплывает вопрос.

⚠️ **Страховка оставлена сознательно, хотя заказчик назвал только коммит и пуш.**
`geo_cache/` и `tile_cache/` в git не лежат: `rm -r` по ним не откатить ничем.

**Пример.** Рельеф Marshut 4.6 ГБ сшивался из исходников, которые уже удалены из
`_части/`; тайлов в старой раскладке 13 273 — одна опечатка в пути стоила бы суток.

⚠️ **Режим снимает ВОПРОСЫ, а не решения, оставленные за заказчиком.** Задачи «не начинать
без команды» (10.9, 10.13 / `osmium`, отложенные теги), открытые вопросы В*, 10.1-б,
ветка `exe-build-2`, файл `координаты.txt` — не трогаются и в нём; уходят строкой в итог.

## 1. Три категории действий

| Категория | Что это | Как поступать |
|---|---|---|
| 🟢 **Разведка и свои инструменты** | посмотреть файлы, найти в коде, прочитать настройки, **написать и запустить свой скрипт** для разбора данных | **делать молча**, не спрашивая |
| 🟡 **Долгие и затратные прогоны** | проверки документации, полные прогоны модели, пересборка кэша, генерация большого числа файлов | **спросить перед запуском**, коротко назвав, что и зачем |
| 🔴 **Необратимое и внешнее** | коммит, push, удаление, установка пакетов, обращения в сеть | **только по явной команде** — см. [6_КОММИТЫ_GIT.md](6_КОММИТЫ_GIT.md) |

### 🟢 Делать молча — примеры

* открыть и прочитать любой файл проекта, включая настройки и транскрипты;
* найти упоминания имени в коде (`Grep`, `Glob`);
* посмотреть, какие есть скиллы, плагины, версии библиотек;
* **написать вспомогательный скрипт** в служебной папке и запустить его: извлечь
  текст из `.docx`, посчитать статистику, разобрать журнал, проверить гипотезу;
* сгенерировать промежуточные данные для собственной проверки.

> Ключевая мысль: **разведка и самопроверка — это часть работы, а не отдельное
> решение**. Спрашивать «можно я посмотрю?» — то же самое, что спрашивать «можно я
> подумаю?».

### 🟡 Спросить перед запуском — примеры

⚠️ **Критерий пересмотрен 03.09.2026 (решение заказчика): спрашивать нужно про
НЕОБРАТИМОЕ, а не про долгое.** Раньше в «спросить» стояли проверки документации — по
признаку «затратный прогон». На деле они только читают и печатают, идут секунды и
запускаются после каждой правки, поэтому каждый вопрос был остановкой на ровном месте.
Цена в секундах — плохой признак; хороший — **можно ли откатить одной командой**.

* **перезапись данных**, к которым привязаны записанные замеры: пересборка кэша слоёв
  участка, генерация рисунков пособия;
* **сеть и диск**: скачивание тайлов, установка пакетов;
* **история git**: `add`, `commit`, `push`, а также `checkout` и `reset` — они ещё и
  затирают несохранённые правки;
* **удаление и перезапись папок**: `rm`, сборка `.exe` (она удаляет каталог назначения);
* **долгий расчёт, чьи числа идут в эталон** — контрольный прогон модели;
* массовая правка десятков файлов.

**А вот это спрашивать не нужно** — оно нужно для работы и откатывается: чтение любых
файлов, разведка, свои проверки (`check_*`), генераторы оглавлений и карты кода (пишут
только собственные файлы и блоки между маркерами), компиляция, копирование во временную
папку.

Формулировка вопроса — одна строка: **что запускаю, сколько примерно займёт, зачем**.
Не «можно?», а «прогнать проверку документации (4 скрипта, ~1 мин) — ссылки после
переноса могли поехать?».

## 2. Чего НЕ надо спрашивать отдельно

Отдельная беда — вопрос «начинаю?» после того, как план уже изложен. Он не даёт
человеку новой информации: решение уже описано, диагноз поставлен, остаётся сделать.

| ❌ Так не надо | ✅ Так надо |
|---|---|
| «План: П1, П2, П5. **Начинаю?**» | «Сделал П1, П2, П5. Вот числа. П3 не трогал — он меняет ядро выборки, скажите, брать ли» |
| «Диагноз такой-то. **Исправлять?**» | «Исправил, замер до/после: 128 → 150» |
| «**Пересобирать кэш?**» (когда без этого работа не завершится) | пересобрать и доложить; спросить, только если это долго |
| «**Продолжаем в эту сторону?**» | продолжить и показать результат |

**Когда вопрос всё-таки нужен:**

* **развилка поведения**, где варианты дают разный результат и оба разумны
  («веер всех повадок» против «только выбранный режим»);
* **значение параметра**, меняющее итог расчёта, если нет объективного критерия выбора;
* **приоритет**, когда работы много и порядок существенно влияет на пользу;
* всё из категории 🔴.

> Проверка вопроса на нужность: **изменит ли ответ то, что я буду делать?**
> Если при любом ответе действия одни и те же — вопрос лишний.

## 3. Как оформлять список разрешений

Разрешения задаются в `.claude/settings.json` проекта (и `~/.claude/settings.json`
для всех проектов):

```json
{
  "permissions": {
    "allow": ["Bash(python tools/переносимое/скрипты/docmap.py:*)"],
    "ask":   ["Bash(git push:*)"],
    "defaultMode": "acceptEdits"
  }
}
```

* `allow` — выполняется без запроса;
* `ask` — всегда спрашивать, даже если попадает под `allow`;
* шаблон `Имя(команда:*)` сверяется с **началом** команды, `:*` — «и любое продолжение».

### ⚠️ Ловушка, из-за которой список не работает

**Нельзя предварять команду `cd "путь" &&`.** Правило сверяется с началом строки, и
команда `cd "…" && python x.py` начинается с `cd`, а не с `python` — разрешение не
срабатывает, запрос всплывает снова.

Рабочая директория и так установлена в корень проекта: `cd` не нужен, а нужен —
пишется абсолютный путь к файлу внутри самой команды.

> 🧮 **Замер, из-за которого правило записано.** Разбор транскрипта одной длинной
> сессии: **757** команд `Bash`/`PowerShell`, из них **656 начинались с `cd "путь" &&`**.
> При этом список разрешений покрывал лишь **24 %** вызовов — остальные 576 всплывали
> запросом. Основная причина была не в коротком списке, а в приставке `cd`.

⚠️ **Та же ловушка — приставка переменной окружения.** `PYTHONIOENCODING=utf-8 python x.py`
начинается не с `python`, и правило `Bash(python x.py:*)` его не покрывает. На Windows
такая приставка нужна постоянно (консоль в cp1251 роняет вывод на «→» и «×»), поэтому
для часто запускаемых скриптов заводится **пара** правил — с приставкой и без.

⚠️ **И третий вариант той же ловушки — флаг `-X utf8` (найдено 05.09.2026).** Он делает
ровно то же, что `PYTHONIOENCODING=utf-8`, но вставляется МЕЖДУ `python` и путём к
скрипту: `python -X utf8 tools/x.py`. Такая команда не начинается ни с `python tools/x.py`
(правило без флага), ни с `PYTHONIOENCODING=... python tools/x.py` — своя, третья форма
префикса. За сессию 05.09.2026 это подтвердилось уже РАЗРЕШЁННЫМИ по сути проверками
(`check_names.py`, `docmap.py`, `gui_check.py` и др.), которые всё равно всплывали
запросом. Правило то же: для часто запускаемых скриптов заводить **тройку** вариантов —
`python x.py`, `PYTHONIOENCODING=utf-8 python x.py`, `python -X utf8 x.py`.

⚠️ **Проверено повторно 03.09.2026:** правило про `cd` записано, а нарушалось снова —
почти каждая команда сессии шла с приставкой. Само по себе записанное правило не
работает, если о нём не помнить в момент набора команды; поэтому оно продублировано
там, куда смотрят всегда — в `CLAUDE.md` рядом со списком проверок.

### Что имеет смысл внести в `allow`

| Вносить | Не вносить |
|---|---|
| свои скрипты из служебной папки (запускаются десятками раз) | `git add`, `git commit`, `git push` |
| текстовые утилиты разбора: `grep`, `sed`, `head`, `tail`, `wc`, `awk`, `sort` | `rm`, `mv`, `Remove-Item` |
| `python -c` для разовых проверок | установку пакетов, обращения в сеть |
| чтение git: `status`, `diff`, `log`, `branch` | долгие прогоны — им место в 🟡 |

## 4. Перенос в другой проект

1. скопировать эту папку целиком;
2. в `.claude/settings.json` перенести раздел `allow`, заменив пути к скриптам;
3. проверить, что в списке **нет** записывающих команд git;
4. сверить категории §1 с тем, что в новом проекте считается «долгим»: где-то полный
   прогон — секунды, и тогда он переходит из 🟡 в 🟢.
