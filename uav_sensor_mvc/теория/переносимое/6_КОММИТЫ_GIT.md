# Работа с git: коммиты, ветки, что не должно попасть в историю

> **Главное правило.** `git add`, `git commit`, `git push` выполняются **только по
> явной команде человека**. Не «работа выглядит законченной — закоммичу», не «сделаю
> на всякий случай точку возврата». Сказано «коммить» — коммитим; не сказано — нет.
>
> Чтение истории (`status`, `diff`, `log`, `branch`, `show`) — наоборот, свободно и
> без спроса: это разведка.

---

## 1. Почему запись отделена от чтения

Коммит меняет общую историю, push отправляет её наружу — и то и другое трудно
откатить чужими руками. Ошибка стоит дороже, чем сэкономленный вопрос. При этом
посмотреть, что изменилось, — действие безобидное и нужное постоянно.

Отсюда асимметрия: **читать историю — молча, писать — по команде**.

---

## 2. Перед коммитом — обязательная проверка

Три шага, все три перед каждым коммитом:

```bash
git status          # что вообще попало в изменения
git diff            # что именно поменялось в коде
git branch          # в той ли ветке работаем
```

**На что смотреть в `git status`:**

| Признак | Что значит | Что делать |
|---|---|---|
| файлы кэшей и данных | попали случайно | добавить в `.gitignore`, не коммитить |
| правки, которых не делал | остались от прошлой сессии | **сказать человеку**, не заметать в общий коммит |
| десятки файлов при мелкой правке | скорее всего переносы строк или кодировка | разобраться до коммита |

⚠️ **Отдельно предупреждать**, если в изменениях есть чужая или прошлая работа: человек
должен знать, что коммит захватит не только сегодняшнее.

---

## 3. Ветка

* работать в **рабочей ветке**, не в основной;
* если оказались в основной — сначала завести ветку, потом коммитить;
* переключение веток (`checkout`, `switch`) — тоже по команде: в рабочем дереве могут
  быть незакоммиченные правки, и переключение их заденет.

---

## 4. Сообщение коммита

**Одна строка, по-русски, о сути изменения — с числом, если оно есть.**

Хорошо (из истории этого проекта):

```
Шаг сетки датчиков считается от радиуса: при R = 2 км и пяти датчиках засечка 79 -> 91 %
Движение БПЛА по физике аппарата: предел поворота, окно разворота, скругление линии
Запретные зоны, рисуемые пользователем: маска запрета, штриховка, честное предупреждение
```

Плохо:

```
исправления            ← что исправлено?
update threat_grid.py  ← это видно из diff
фиксы после ревью      ← какие и зачем?
WIP                    ← в общей истории таким записям не место
```

**Правила формулировки:**

1. **что изменилось по сути**, а не какой файл тронут — файлы видны в `diff`;
2. **число «было → стало»**, если правка что-то измерила: `79 -> 91 %`, `128 → 150`;
3. настоящее время, без «я»: «Шаг считается от радиуса», не «Я поменял шаг»;
4. подробности — в тело сообщения через пустую строку, если одной строки мало;
5. в конце тела — строка соавторства, если она принята в проекте:

```
Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>
```

---

## 5. Что не должно попадать в историю

| Не коммитить | Почему |
|---|---|
| кэши карт и геоданных (`tile_cache/`, `geo_cache/`, offline-пакеты) | сотни мегабайт, восстанавливаются скачиванием |
| `__pycache__/`, `*.pyc` | производные от исходников, у каждого свои |
| результаты сборки (`build/`, `dist/`, `*.exe`) | пересобираются из исходников |
| личные заметки, черновики, временные файлы | не часть проекта |
| ключи, токены, пароли | **никогда**, даже в частный репозиторий |

Всё перечисленное — в `.gitignore`. Если такой файл уже попал в историю, просто
удалить его из рабочего дерева мало: он остаётся в прошлых коммитах.

---

## 6. Push

* **отдельное действие и отдельная команда**: разрешение на коммит не означает
  разрешения на push;
* принудительный push (`--force`, `--force-with-lease`) — только при прямом и
  недвусмысленном указании: он переписывает то, что могли забрать другие;
* перед первым push новой ветки — сказать, куда именно она уйдёт.

---

## 7. Чего не делать никогда без прямого указания

| Действие | Чем опасно |
|---|---|
| `git reset --hard` | молча уничтожает незакоммиченные правки |
| `git checkout -- <файл>` | то же самое для одного файла |
| `git clean -fd` | удаляет неотслеживаемые файлы, включая черновики |
| `git rebase`, `git merge` | переписывают историю, конфликтуют с чужими ветками |
| `git commit --amend` | меняет уже существующий коммит; предпочитать новый |
| `--no-verify`, отключение подписи | обходит проверки, настроенные не просто так |

Если кажется, что без такого шага не обойтись, — **описать ситуацию и предложить**,
а не выполнить.

---

## 8. Перенос в другой проект

1. скопировать файл, заменить §3 (имя рабочей ветки) и §5 (список игнорируемого);
2. сверить §4 с фактическим стилем сообщений: посмотреть `git log --oneline -20` и
   держаться того, что принято;
3. §1, §6, §7 переносятся без изменений — они не зависят от проекта.
