# 8. Как писать комментарии в коде

> **Правился:** 14.09.2026 (коммит `30eec6d`) — в коммит вошли правки 13.09, описанные ниже; нового содержания нет.
> 13.09.2026 — пример больше не заготовка под 10.1 (задача снята). Правило
> заведено 12.09.2026 по решению заказчика, с согласованным примером.

> **Зачем.** Комментарий пишется не «чтобы был», а чтобы **человек понял механизм, не
> читая сам код**. Если пояснение пересказывает строку — оно только занимает место; если
> его нет вовсе — механизм придётся разбирать заново каждый раз.
>
> ⚠️ **Правило действует на НОВЫЙ код и на переписывание существующего функционала.**
> Уже написанное не трогаем: переписывать рабочий код ради формата вредно.

---

## 1. Три вида пояснений

| Что поясняем | Где | Объём | Что в пояснении |
|---|---|---|---|
| **функция, класс** | сразу после `def` / `class` | **до 3 строк** — потолок, не норма | что делает · что принимает · что отдаёт |
| **новая переменная** | **в той же строке**, справа | несколько слов | что это + ⚠️ **единица измерения** |
| **ветвление** (`if`, `try`, тернарник) | в строке `if` либо перед ним | одна строка | **что проверяем → что делаем** |
| **алгоритм, формула** | строка перед ним | 1–2 строки | **почему так**, а не пересказ |

**Для функции — три вещи:** что делает · что принимает · что отдаёт. Не по шаблону с
заголовками, а слитно, лишь бы все три были названы.

⚠️ **Ветвление поясняется ПАРОЙ, а не половиной.** «Проверка рамки» — непонятно, чем
кончится; «отдаём как есть» — непонятно, когда. Нужны обе половины:
`if span <= 0:  # рамка вырождена` → `return …  # делить нечего`.

⚠️ **Тернарник внутри выражения — тоже ветвление.** `(over if i else 0.0)` без пояснения
читается как загадка; с пояснением «кроме первой полосы» — сразу ясно.

⚠️ **Единицы измерения обязательны.** Градусы или радианы, км или метры, доля или
проценты. На этом уже обжигались: `arc_length_from_angle` принимает **радианы**, а
`make_arc_by_angle` — **градусы**, и перепутать их стоило разбора с нуля.

## 2. Согласованный пример

⚠️ **Функция вымышленная** и в коде не появится: задача 10.1 (полосы мозаики), под которую
она писалась, снята 13.09.2026 — подложка стала поштучной. Пример показывает только
**формат** комментариев.

```python
def mosaic_stripes(lat_min, lat_max, view_h_km, max_err_m=50.0):
    # Делит мозаику на полосы по широте: внутри полосы расхождение Меркатора
    # с км-фреймом ≤ max_err_m. Вход: широты краёв (град), высота вида (км), допуск (м).
    # Отдаёт: список пар (lat_низ, lat_верх) снизу вверх, не пустой.
    span = lat_max - lat_min                       # высота мозаики, градусы
    if span <= 0:                                  # рамка вырождена (края совпали или задом наперёд)
        return [(lat_min, lat_max)]                # делить нечего — отдаём как есть
    # Ошибка растёт как КВАДРАТ высоты полосы: деление пополам снижает её вчетверо,
    # отсюда корень из отношения «сколько есть» к «сколько терпим».
    err_one = mercator_shift_m(lat_min, lat_max, view_h_km)   # сдвиг при ОДНОЙ полосе, м
    n = max(1, ceil(sqrt(err_one / max_err_m)))    # число полос; max — чтобы не вышло 0
    step = span / n                                # высота полосы, градусы
    over = step * 0.001                            # ⚠️ перекрытие: иначе белая щель между полосами
    out = []
    for i in range(n):
        lo = lat_min + i * step - (over if i else 0.0)          # низ: сдвигаем, кроме первой полосы
        hi = lat_min + (i + 1) * step + (over if i < n - 1 else 0.0)   # верх: кроме последней
        out.append((lo, hi))
    return out
```

**Что здесь сделано и почему именно так:**

| Приём | Зачем |
|---|---|
| три строки на функцию, слитно | суть и цель переданы, а места занято втрое меньше блочного шаблона |
| единицы у каждого аргумента | «широты краёв (град), высота вида (км), допуск (м)» — перепутать нельзя |
| `# высота мозаики, градусы` в строке объявления | не надо искать, что такое `span` |
| **у `if` — ЧТО проверяем и ЧТО делаем** | «рамка вырождена» + «делить нечего»: видно и условие, и решение, не читая тела |
| «Ошибка растёт как КВАДРАТ…» перед формулой | объясняет **корень** в коде; без этого строка выглядит магией |
| `# max — чтобы не вышло 0` | защита в выражении: почему она там, а не «на всякий случай» |
| **у тернарников внутри цикла** | «кроме первой полосы» / «кроме последней» — иначе `if i else 0.0` читается как загадка |
| `⚠️` у `over` | место, которое сломается молча: щель между полосами увидят, а причину — нет |

⚠️ **Ветвление поясняется парой «что проверяем → что делаем».** Одного «проверка рамки»
мало: непонятно, чем кончится. Одного «отдаём как есть» — тоже: непонятно, когда.

## 3. Чего НЕ писать

* ⚠️ **пересказ строки.** `i += 1  # увеличиваем i на единицу` — шум. Пояснение нужно
  там, где из кода не видно **замысла**, а не там, где не видно действия;
* **очевидные аргументы.** `path — путь к файлу` ничего не добавляет; `path — путь к
  .osm.pbf, читается один раз` — добавляет;
* **историю правок в коде.** Для неё есть журнал. В коде уместна только та история,
  которая объясняет **нынешнее** решение: «было X, ломалось на Y, поэтому Z».

## 4. Признак хорошего комментария

**Проверка одним вопросом:** сможет ли человек по одним пояснениям сказать, что механизм
делает и где его легко сломать, **не читая кода**? Если да — достаточно; если для этого
нужно читать код, комментарий не работает.

⚠️ **Второй признак — комментарий переживает правку кода.** Пояснение к «почему» живёт
годами, пояснение к «как именно» устаревает с первой же оптимизацией. Поэтому и пишем
про замысел, а не про действия.
