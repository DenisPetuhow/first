> **Зачем.** Комментарий пишется не «чтобы был», а чтобы **человек понял механизм, не
> читая сам код**. Если пояснение пересказывает строку — оно только занимает место; если
> его нет вовсе — механизм придётся разбирать заново каждый раз.
>
> ⚠️ **Правило действует на НОВЫЙ код и на переписывание существующего функционала.**
> Уже написанное не трогаем: переписывать рабочий код ради формата вредно.

## 1. Три вида пояснений

| Что поясняем | Где | Объём | Что в пояснении |
|---|---|---|---|
| **функция, класс** (и вложенная функция) | сразу после `def` / `class` | **до 3 строк** — потолок, не норма | что делает · **«Вход:»** что принимает · **«Отдаёт:»** что отдаёт («ничего» — тоже) |
| **новая переменная** — и **внутри функции**, и распаковкой `a, b = …` | **в той же строке**, справа (или строкой выше) | несколько слов | что это + ⚠️ **единица измерения** |
| **цикл** (`for`, `while`) | в строке цикла либо перед ним | одна строка | **что перебираем** и зачем |
| **ветвление** (`if`, `elif`, `try`/`except`, тернарник) | в строке `if` либо перед ним | одна строка | **что проверяем → что делаем** |
| **алгоритм, формула** | строка перед ним | 1–2 строки | **почему так**, а не пересказ |

**Для функции — три вещи:** что делает · что принимает · что отдаёт. Слитно, без блочных заголовков, но вход и
выход — **словами «Вход:» и «Отдаёт:»**, как в образце §2: по ним их находит проверка (§2а). Нет аргументов — «Вход:»
не нужен; ничего не отдаёт — «Отдаёт: ничего».

⚠️ **Ветвление поясняется ПАРОЙ, а не половиной.** «Проверка рамки» — непонятно, чем
кончится; «отдаём как есть» — непонятно, когда. Нужны обе половины:
`if span <= 0:  # рамка вырождена` → `return …  # делить нечего`.

⚠️ **Тернарник внутри выражения — тоже ветвление.** `(over if i else 0.0)` без пояснения
читается как загадка; с пояснением «кроме первой полосы» — сразу ясно.

⚠️ **Единицы измерения обязательны.** Градусы или радианы, км или метры, доля или
проценты. На этом уже обжигались: `arc_length_from_angle` принимает **радианы**, а
`make_arc_by_angle` — **градусы**, и перепутать их стоило разбора с нуля.

## 2. Согласованный пример

⚠️ **Функция вымышленная** и в коде не появится: задача 10.1 (полосы мозаики), под которую
она писалась, снята 13.09.2026 — подложка стала поштучной. Пример показывает только
**формат** комментариев.

```python
def mosaic_stripes(lat_min, lat_max, view_h_km, max_err_m=50.0):
    # Делит мозаику на полосы по широте: внутри полосы расхождение Меркатора
    # с км-фреймом ≤ max_err_m. Вход: широты краёв (град), высота вида (км), допуск (м).
    # Отдаёт: список пар (lat_низ, lat_верх) снизу вверх, не пустой.
    span = lat_max - lat_min                       # высота мозаики, градусы
    if span <= 0:                                  # рамка вырождена (края совпали или задом наперёд)
        return [(lat_min, lat_max)]                # делить нечего — отдаём как есть
    # Ошибка растёт как КВАДРАТ высоты полосы: деление пополам снижает её вчетверо,
    # отсюда корень из отношения «сколько есть» к «сколько терпим».
    err_one = mercator_shift_m(lat_min, lat_max, view_h_km)   # сдвиг при ОДНОЙ полосе, м
    n = max(1, ceil(sqrt(err_one / max_err_m)))    # число полос; max — чтобы не вышло 0
    step = span / n                                # высота полосы, градусы
    over = step * 0.001                            # ⚠️ перекрытие: иначе белая щель между полосами
    out = []
    for i in range(n):
        lo = lat_min + i * step - (over if i else 0.0)          # низ: сдвигаем, кроме первой полосы
        hi = lat_min + (i + 1) * step + (over if i < n - 1 else 0.0)   # верх: кроме последней
        out.append((lo, hi))
    return out
```

**Что здесь сделано и почему именно так:**

| Приём | Зачем |
|---|---|
| три строки на функцию, слитно | суть и цель переданы, а места занято втрое меньше блочного шаблона |
| единицы у каждого аргумента | «широты краёв (град), высота вида (км), допуск (м)» — перепутать нельзя |
| `# высота мозаики, градусы` в строке объявления | не надо искать, что такое `span` |
| **у `if` — ЧТО проверяем и ЧТО делаем** | «рамка вырождена» + «делить нечего»: видно и условие, и решение, не читая тела |
| «Ошибка растёт как КВАДРАТ…» перед формулой | объясняет **корень** в коде; без этого строка выглядит магией |
| `# max — чтобы не вышло 0` | защита в выражении: почему она там, а не «на всякий случай» |
| **у тернарников внутри цикла** | «кроме первой полосы» / «кроме последней» — иначе `if i else 0.0` читается как загадка |
| `⚠️` у `over` | место, которое сломается молча: щель между полосами увидят, а причину — нет |

⚠️ **Ветвление поясняется парой «что проверяем → что делаем».** Одного «проверка рамки»
мало: непонятно, чем кончится. Одного «отдаём как есть» — тоже: непонятно, когда.

## 2а. Проверка: `check_comments.py`

Правило держится не памятью, а проверкой (заказчик 19.09.2026: «сделай, чтобы ты всегда
помнил про эти правила и про новые переменные»).

```bash
python tools/переносимое/check_comments.py         # против HEAD: что ещё не закоммичено
python tools/переносимое/check_comments.py HEAD~3  # против другого коммита
python tools/переносимое/check_comments.py --all файл.py   # весь файл, без git
```

Ловит шесть вещей (с 29.09.2026): функция **без пояснения**; пояснение **длиннее 3 строк**; в пояснении нет
**«Вход:»** (если есть аргументы) или **«Отдаёт:»**; новая **переменная без пояснения** — первое присваивание в
области имён, распаковка `a, b = …`, поле `self.x` в `__init__`, однобуквенные имена (кроме `i`, `j`); **цикл** и
**ветвление** (`if`, `elif`, `except`) без пояснения в строке или строкой выше. Комментарий ищется по токенам (решётка в
строке `"#ff0000"` — не комментарий). Код возврата 1 — есть находки.

⚠️ **Смотрит ТОЛЬКО изменённые строки** (`git diff`) **плюс новые файлы целиком**: правило
действует на новый код, а уже написанный мы не трогаем.

### ⚠️ Урок 20.09.2026: проверка, которая всегда говорит «чисто»

**Как вскрылось.** Модуль типов БПЛА (план 12, 12.3) прошёл проверку «ЧИСТО» при
**«файлов с правками 1»**, хотя правок было четыре. Разбор нашёл сразу два дефекта,
и оба — молчаливые:

| Дефект | Почему молчал | Чем лечится |
|---|---|---|
| пути `git diff` отсчитаны от корня **репозитория**, а скрипт клеил их к корню **проекта** (проект лежит подпапкой) | файл «не найден» → `continue` без единого слова | база берётся из `git rev-parse --show-toplevel` |
| **новый файл, ещё не добавленный в git**, `git diff` не видит вовсе | пустой список — не ошибка | добавлены `git ls-files --others`, файл берётся целиком |
| у `ls-files` пути от ТЕКУЩЕЙ папки, а у `diff` — от корня репозитория | половина файлов снова «не найдена» | флаг `--full-name` |

**Замер:** было «файлов с правками 1, чисто» → стало «файлов 4, находок 26». Из 26 по делу
оказались **6**, остальные 20 — законные служебные имена (`col`, `hint`, `btn`, `item`,
`row`), под них дописан фильтр `SKIP_VARS`.

⭐ **Главный вывод — не про пути.** Проверка, которая при поломке печатает «чисто», хуже
отсутствующей: она даёт ложное спокойствие. Поэтому ненайденные файлы теперь **называются
вслух** (`⚠️ НЕ НАЙДЕНО НА ДИСКЕ`). ⚠️ Это та же болезнь, что закрытый блок в `РАБОТА.md`,
неделю утверждавший, будто сборки нет.

### ⚠️ Второй заход: скрипт требовал переписать ЧУЖИЕ докстринги

**Как вскрылось.** Правка задачи 12.2 добавила по строке в давно написанные `set_area`,
`_build_ui`, `_on_scene_click` — и скрипт потребовал сократить их пояснения. Это прямо
противоречит правилу «уже написанный код не трогаем»: функция стала «изменённой» из-за
одной строки в теле.

**Чем вылечено.** О пояснении судим **только по шапке** — строке `def` и самому пояснению
под ней (`head_span`). Тронуто тело — функция чужая, её докстринг не наше дело; тронут
`def` — функция новая, пояснение спрашиваем.

**Заодно фильтр `SKIP_PREFIXES`:** имена виджетов Qt (`btn_`, `lbl_`, `chk_`, `spin_`,
`combo_`, `rb_`, `grp_`, `tbl_`) содержат и что это, и что делает —
`btn_close = QPushButton("Закрыть")` комментировать нечем. **Замер:** находок 12 → 2, и
обе оказались настоящими.

⚠️ **Что она не ловит:** единицы измерения, парность пояснения у ветвления, осмысленность
текста. Это остаётся на глаза — скрипт сужает выборку, а не заменяет чтение.

### ⚠️ Третий заход (26–29.09.2026): проверка молчала о главном

**Как вскрылось.** Заказчик: «пояснения функциям давал, но нет к переменным внутри функций, нет пояснения циклов, нет,
что на вход и что на выход». Проверка на том же коде говорила «ЧИСТО»: она смотрела лишь, **есть ли** пояснение, а
переменные — только вида `имя = …`, пропуская `d`, `t`, `p` (стояли в списке служебных) и распаковку; циклов и
«Вход / Отдаёт» не видела вовсе. Я поверил её «ЧИСТО», не сверив код с образцом.

**Чем вылечено.** Шесть проверок вместо трёх (выше). **Замер:** код планов 13 и 13.1 (`HEAD~2`, 24 файла) — «ЧИСТО» →
**278** находок → после правки **0**; в новом коде 29.09 проверка поймала 14 таких же пропусков сразу. Логику правка не
тронула — AST без пояснений до и после совпадает во всех 17 файлах.

⭐ **Вывод тот же, что в первом заходе, — только тоньше:** проверка, которая молчит о части правила, опасна так же, как
сломанная. Правило появилось раньше проверки — **сверять с образцом глазами**, пока проверка не научена.

## 3. Чего НЕ писать

* ⚠️ **пересказ строки.** `i += 1  # увеличиваем i на единицу` — шум. Пояснение нужно
  там, где из кода не видно **замысла**, а не там, где не видно действия;
* **очевидные аргументы.** `path — путь к файлу` ничего не добавляет; `path — путь к
  .osm.pbf, читается один раз` — добавляет;
* **историю правок в коде.** Для неё есть журнал. В коде уместна только та история,
  которая объясняет **нынешнее** решение: «было X, ломалось на Y, поэтому Z».

## 4. Признак хорошего комментария

**Проверка одним вопросом:** сможет ли человек по одним пояснениям сказать, что механизм
делает и где его легко сломать, **не читая кода**? Если да — достаточно; если для этого
нужно читать код, комментарий не работает.

⚠️ **Второй признак — комментарий переживает правку кода.** Пояснение к «почему» живёт
годами, пояснение к «как именно» устаревает с первой же оптимизацией. Поэтому и пишем
про замысел, а не про действия.
