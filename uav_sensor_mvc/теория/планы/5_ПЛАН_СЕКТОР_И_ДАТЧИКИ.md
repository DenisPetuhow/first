## 0. Границы работы: что меняется, а что НЕТ

Это важнее всего: половина ошибок в большой правке — от того, что тронули лишнее.

| ✅ Меняется | ❌ НЕ меняется |
|---|---|
| **источник векторных данных** (новый файл карты) | формат внутренних слоёв: `dict` имя → список ломаных в км |
| **спавн (появление) БПЛА**: одна фиксированная точка → сектор и 5 точек входа | **модель движения**: блуждание по коридорам, цена шага, предел поворота, сглаживание |
| **правила размещения** датчиков и порядок расстановки | весовая карта: слои, рельеф, населённые пункты, маска проходимости |
| **число типов датчиков**: один → два (малый и большой) | физика полёта: `R_min`, `TURN_MAX_DEG`, окно разворота |
| окно настройки датчиков, превью запуска | архитектура MVC: модель без Qt, представление не считает |

> ⚠️ **Формулировка заказчика дословно:** «механика БПЛА меняется только спавн, модель
> их движения та же, и векторная карта весов так же действует с рельефом».

## 3. Задача 1 — новая векторная карта

### 3.1. Что требуется

Заказчик даёт **новый векторный файл** карты. Его нужно преобразовать так, чтобы
приложение отображало карту и считало по ней весовую сетку.

### 3.2. Как решать

Ключ к дешёвому решению: **не трогать саму машину весов**. Внутренний формат слоёв —
это `dict`: имя слоя → список массивов `(N, 2)` в локальных километрах. Всё, что нужно,
— привести новый файл к этому формату; дальше `build_threat_grid` работает как есть.

```
новый файл ──► конвертер ──► тот же dict слоёв ──► build_threat_grid ──► карта весов
                    ▲
          ЗДЕСЬ вся новая работа
```

**Порядок действий:**

1. **Определить формат файла** — открыть первые байты, посмотреть расширение.
   Типовые случаи и чем читать:

   | Формат | Расширение | Библиотека |
   |---|---|---|
   | Shapefile | `.shp` + `.dbf` + `.shx` | `pyshp` (shapefile) или `geopandas` |
   | GeoJSON | `.geojson`, `.json` | стандартный `json` |
   | GeoPackage | `.gpkg` | `fiona` / `geopandas` |
   | MapInfo | `.tab`, `.mif` | `fiona` (драйвер MapInfo) |
   | KML/KMZ | `.kml`, `.kmz` | `fastkml`, либо разбор XML |
   | DXF | `.dxf` | `ezdxf` |

2. **Понять, какие в нём слои и как они названы** — вывести список слоёв/атрибутов и
   сопоставить их с нашими десятью (`THREAT_LAYERS` в `config.py`: река, ручей, дороги
   двух типов, ж/д, ЛЭП, трубопровод, лесополоса, мост, застройка).
3. **Написать конвертер** — новую функцию `layers_from_vector(path, lon0, lat0, bbox)`
   рядом с `layers_from_osm` (`threat_grid.py`, строка 1285). Она обязана вернуть **тот
   же** `dict`, что и `layers_from_osm`.
4. **Подключить в `load_layers`** (строка 1206) — добавить ветку по расширению рядом с
   существующими `.npz` и `.pbf/.osm`.
5. **Добавить в окно выбора карт** `DigitalMapsDialog` (строка 2055) — новый фильтр
   файлов.
6. **Пересобрать кэш** `tools/build_threat_grid.py` → `geo_cache/threat_layers.npz`.

### 3.3. Ловушки

* ⚠️ **Проекция координат.** Наши слои — в **локальных километрах** от якоря
  `(lon0, lat0)`; функция перевода — `lonlat_to_km` (строка 70). Если новый файл в
  метрической проекции (UTM, Пулково-42, Web Mercator), сначала перевести в
  широту/долготу, и только потом в километры. Признак ошибки: карта уезжает на сотни
  километров или сжимается.
* ⚠️ **Кодировка атрибутов.** У Shapefile имена слоёв часто в `cp1251`; при чтении
  указывать кодировку явно, иначе русские названия превратятся в мусор.
* ⚠️ **Пересборка кэша обязательна** после смены источника: `.npz` хранит уже
  разобранные слои и **коды типов населённых пунктов** — правило записано в
  [ОГРАНИЧЕНИЯ.md 3.10г](../ОГРАНИЧЕНИЯ.md).

### 3.4. Открытый вопрос к заказчику

**Формат и состав нового файла не назван.** До ответа делать конвертер вслепую нельзя.
Спросить: расширение файла, в какой системе координат, какие в нём слои (что считать
рекой, дорогой, застройкой).

## 4. Задача 2 — сектор направления и пять точек входа

Ядро работы. Меняется **только спавн**: откуда БПЛА появляется. Движение остаётся тем же.

### 4.1. Что требуется (по описанию заказчика)

1. Кнопка **«Задать сектор направления»**;
2. пользователь щёлкает **по краю карты** — получается точка `P`;
3. строится прямая **цель `B` → `P`**;
4. от этой прямой откладывается **±45°** — получается **сектор** с вершиной в цели;
5. часть **краёв карты**, попавшая в сектор, — это возможные направления появления БПЛА;
6. по этой части края, **с учётом весовой карты**, выбираются **5 точек входа**;
7. точки обозначаются на карте;
8. старт каждого маршрута берётся из этих пяти.

### 4.2. Геометрия — как считать

```
u = (P − B) / |P − B|                     орт направления «цель → указанная точка»
сектор = { направления d : угол(d, u) ≤ 45° }
```

Принадлежность направления сектору проверяется через скалярное произведение — без
арктангенсов и без разрывов при переходе через 180°:

```
d · u ≥ cos(45°) · |d|          ⟺   направление внутри сектора
```

**Отбор точек на краю карты:**

1. взять ячейки границы прямоугольника `bbox_km` (четыре стороны);
2. оставить те, для которых направление `цель → ячейка` попадает в сектор (формула выше);
3. отбросить непроходимые (`passable_mask`, `threat_routes.py` строка 139) — точка входа
   обязана быть достижимой, иначе маршрут из неё не построится;
4. из оставшихся выбрать **5** с наибольшим весом `w(e)`, **разнесённых** между собой —
   иначе все пять слипнутся в одном «горячем» углу.

**Как обеспечить разнесённость** — тем же жадным приёмом, что и у датчиков: брать
максимум веса, затем исключать соседей ближе `d_min` и повторять. Разумное начальное
`d_min` — примерно `(длина края в секторе) / 10`; вынести в константу.

### 4.3. Где править

| Шаг | Файл :: место |
|---|---|
| хранить сектор и точки | `ThreatModel.__init__` (строка 1826): поля `sector_dir`, `entry_points` |
| считать точки | новый метод `ThreatModel.compute_entry_points()` рядом с `entry_km` (2512) |
| отдавать выбранную точку | переписать `entry_km` → выбор из списка; `entry_target_km` (2517) — вернуть выбранную |
| кнопка | `threat_view.py` рядом с `btn_input` (646) |
| режим клика по карте | по образцу режима «указать цель» (`set_target`, 2500) |
| обработчик | `threat_controller.py` рядом с обработчиками кликов (296–330) |
| отрисовка сектора и точек | `threat_view.py` — слой поверх карты |

### 4.4. Как встроить пять точек в построение маршрутов

Здесь главное — **не сломать кэш контекста**.

* `build_iter_context(grid, entry_km, target_km, ...)` (строка 763) кэшируется по ключу
  `_ctx_key()` (строка 2012). Дорогие поля считаются **от цели** и от входа не зависят
  (§1.2, факт 1) — поэтому **не надо** пересчитывать контекст для каждой из пяти точек.
* Зависят от входа только: проекция ячеек на ось «вход→цель» (строки 819–822) и часть
  параметров VIA. Возможные решения, в порядке предпочтения:
  1. **считать ось от ЦЕНТРА сектора** (усреднённое направление) — контекст остаётся
     один, разброс по пяти точкам обеспечивается стартовой ячейкой;
  2. если качество маршрутов просядет — хранить пять «лёгких» надстроек над общим
     контекстом (только проекции), не дублируя поля Дейкстры.
* В `plan_routes` (2039) и `iter_step` (2170) при розыгрыше каждого маршрута выбирать
  стартовую точку из пяти. Распределение: равномерно либо пропорционально весу точки —
  **начать с равномерного**, как более честного при неизвестном противнике.

### 4.5. Что проверить

* пять точек лежат **на краю** карты и **внутри** сектора;
* из каждой строится хотя бы один маршрут (иначе точка выбрана в непроходимой зоне);
* область достижимости (`flight_envelope`, 192) перестроилась под новый вход;
* при смене сектора маршруты и датчики **сбрасываются** — как это уже сделано в
  `set_target` (2500–2510).

## 5. Задача 3 — правила размещения датчиков

### 5.1. Что требуется

1. **минимум один датчик рядом с точкой старта**, но **не за ней**;
2. правило «маршрут не уходит назад» — **остаётся** (это про движение, не про датчики);
3. правило «датчики не ставятся за целью» — **смягчить**: разрешить и до, и после цели,
   но так, чтобы датчики **не пересекались между собой** и **не перекрывали цель больше
   чем на 30 %**.

### 5.2. Где править

**Всё в одном месте** — `_place_by_routes` (`threat_grid.py`, строка 2342):

```python
if D2 > 1e-9:                       # ← строки 2357–2359, ЭТО и надо заменить
    s = ((cand - A) @ d) / D2
    cand = cand[(s >= 0.0) & (s <= 1.0)]      # оставляли только между A и B
```

**Новое правило** вместо жёсткого отсечения:

```
s = проекция кандидата на ось «вход → цель», в долях |AB|
допустимо:  s ≥ 0            (не позади точки старта — правило 1 сохраняется)
            s ≤ 1 + запас    (за целью — можно, но не дальше запаса)
```

Запас за целью выразить в долях радиуса, а не в долях `|AB|`: `|AB|` меняется при каждом
клике по цели, и правило «поплывёт». Разумно `s_макс = 1 + k·R / |AB|`.

### 5.3. Ограничение «перекрытие цели ≤ 30 %»

Формулировка заказчика: датчики не должны «пересекать цель более чем на 30 %».
Читается как: **зона датчика не должна накрывать окрестность цели больше чем на 30 %
своей площади**. Считается через площадь пересечения двух кругов — формула и разбор
уже выписаны в [пособии, часть 2 §9.1](../пособие/2_ГЕОМЕТРИЯ_И_ОБОЗНАЧЕНИЯ.md):

```
S_пересечения = 2R²·arccos(d / 2R) − (d/2)·√(4R² − d²)
```

Отсюда получается **минимальное допустимое расстояние** от датчика до цели, и правило
сводится к простой проверке `|c − B| ≥ d_min` — считать площади в цикле не нужно.

⚠️ **Уточнить у заказчика:** 30 % от площади **зоны датчика** или от **защищаемой
окрестности цели**? От ответа зависит `d_min`. По умолчанию взять первое.

### 5.4. Ловушка

Датчик у точки старта уже существует — это якорь `anchor_a` (строка 2375). При пяти
точках входа якорь должен ставиться **у той точки, которая используется чаще** (или у
каждой, если датчиков хватает). Не забыть: при `len(anchors)` больше числа датчиков
жадный алгоритм не сможет разместить ничего полезного.

## 6. Задача 4 — два типа датчиков и окно настройки

### 6.1. Что требуется

| Тип | Радиус | Количество | Отрисовка |
|---|---|---|---|
| малый | **2 км** | **20** | как сейчас |
| большой | **15 км** | **3** | **другой фон покрытия** |

Значения — начальные, меняются в интерфейсе. Окно настройки — **не блокирующее**
основное. Большие датчики: распределяются по выборке маршрутов, **не пересекаясь между
собой**, и прикрывают цель **со всех сторон** («треугольник, возможно неправильный»).

### 6.2. Где править

| Шаг | Место |
|---|---|
| параметры | `config.py` :: `Params` — рядом с `threat_N`, `threat_R` (строки 531–541) добавить `threat_N_big`, `threat_R_big`, `threat_k_big` |
| окно | `threat_view.py` — новый класс по образцу `InputDataDialog` (2127), обязательно `setModal(False)` |
| кнопка | рядом с `btn_input` (646) |
| обработчик | `threat_controller.py` по образцу окна «Входные данные» (296–330) |
| хранение | `ThreatModel`: `self.sensors` (малые) + `self.sensors_big` (большие) |
| отрисовка | `threat_view.py` :: `LAYER_STYLE`, `THREAT_COLORS`, `_build_scene_items` |

⚠️ **Не заводить второй экземпляр модели.** Оба типа считаются одной моделью на одной
выборке маршрутов — иначе они не будут «видеть» друг друга при проверке пересечений.

### 6.3. Круговой щит у цели

Требование «прикрывают цель со всех сторон» — это **угловое** распределение, а не
покрытие площади. Проверяемая формулировка:

```
для трёх больших датчиков: углы направлений «цель → датчик» должны быть
разнесены примерно на 360° / 3 = 120°, с допуском
```

Реализация: при выборе очередного большого датчика к обычному приросту покрытия
добавить **штраф за угловую близость** к уже поставленным. Это сохраняет жадную схему и
не ломает гарантию (штраф не делает функцию несубмодулярной, если он зависит только от
уже выбранных).

⚠️ **Проверить достижимость.** При `R` = 15 км и требовании «не пересекаться» три
датчика должны стоять не ближе `2 · 15 = 30 км` друг от друга. На участке 94 × 75 км это
возможно, но впритык — если алгоритм не находит расстановку, ослаблять разнос
постепенно, как это уже сделано для малых (строки 2386–2388).

## 7. Задача 5 — порядок расстановки

### 7.1. Что требуется

Расстановка идёт **этапами**, а не одним жадным проходом:

```
① датчик(и) у точки старта движения БПЛА
② 2–3 датчика рядом с целью
③ 3 БОЛЬШИХ датчика: круговой щит у цели, минимальное взаимное перекрытие,
   с учётом движения БПЛА
④ все оставшиеся малые — обычный жадный выбор по выборке маршрутов
```

### 7.2. Как решать

Переписать `place_sensors` (строка 2311) как последовательность этапов, где каждый
следующий видит уже занятые позиции:

```python
def place_sensors(self):
    занятые = []
    занятые += этап_старт()          # ① якоря у точек входа
    занятые += этап_цель()           # ② 2–3 малых у цели
    занятые += этап_большие()        # ③ 3 больших, угловой разнос
    занятые += этап_остальные()      # ④ жадный выбор на остатке
```

**Механизм для этапов ①–③ уже есть** — это параметр `anchors` в
`CoverageCache.greedy` (используется в строке 2385). Каждый этап добавляет свои позиции
в список якорей следующего; отдельный алгоритм писать не нужно.

⚠️ **Сохранить свойство субмодулярности.** Принудительные якоря его не нарушают:
гарантия `(1 − 1/e)` формулируется для **оставшихся** позиций при фиксированных
якорях. Это стоит явно записать в методичку — иначе при следующей сверке возникнет
вопрос, действует ли ещё оценка качества.

### 7.3. Что проверить

* сумма по этапам = заказанному числу датчиков (`threat_N` малых + `threat_N_big` больших);
* ни один этап не «съел» весь бюджет, оставив следующие пустыми;
* при малом числе датчиков (например 5) этапы деградируют разумно, а не падают.

## 8. Задача 6 — превью запуска

### 8.1. Что требуется

Перед показом интерфейса — картинка на **5 секунд**.

### 8.2. Как решать

Стандартный механизм Qt — `QSplashScreen`. Правится один файл: `main_qt.py`, функция
`main` (строка 44), между созданием `QApplication` (строка 65) и `tabs.show()` (99).

```python
app = QtWidgets.QApplication(sys.argv)
pix = QtGui.QPixmap(путь_к_картинке)
splash = QtWidgets.QSplashScreen(pix)
splash.show()
app.processEvents()                     # иначе окно останется пустым
...                                     # создание вкладок идёт как есть
QtCore.QTimer.singleShot(5000, splash.close)
tabs.show()
```

**Ловушки:**

* ⚠️ **`app.processEvents()` обязателен** — без него заставка покажется пустым
  прямоугольником;
* ⚠️ **не блокировать поток** `time.sleep(5)` — интерфейс за это время не построится, и
  пользователь увидит зависшее окно. Только таймер;
* ⚠️ **путь к картинке в сборке `.exe`** — файл нужно положить в `datas` рецепта
  PyInstaller, иначе в собранной программе заставки не будет
  ([СБОРКА_EXE.md](../интерфейс/СБОРКА_EXE.md));
* картинку заказчик должен предоставить — **уточнить**, какая именно.
