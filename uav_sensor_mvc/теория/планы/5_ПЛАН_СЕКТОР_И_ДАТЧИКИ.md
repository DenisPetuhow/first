## 0. Границы работы: что меняется, а что НЕТ

Это важнее всего: половина ошибок в большой правке — от того, что тронули лишнее.

| ✅ Меняется | ❌ НЕ меняется |
|---|---|
| **источник векторных данных** (новый файл карты) | формат внутренних слоёв: `dict` имя → список ломаных в км |
| **спавн (появление) БПЛА**: одна фиксированная точка → сектор и 5 точек входа | **модель движения**: блуждание по коридорам, цена шага, предел поворота, сглаживание |
| **правила размещения** датчиков и порядок расстановки | весовая карта: слои, рельеф, населённые пункты, маска проходимости |
| **число типов датчиков**: один → два (малый и большой) | физика полёта: `R_min`, `TURN_MAX_DEG`, окно разворота |
| окно настройки датчиков, превью запуска | архитектура MVC: модель без Qt, представление не считает |

> ⚠️ **Формулировка заказчика дословно:** «механика БПЛА меняется только спавн, модель
> их движения та же, и векторная карта весов так же действует с рельефом».

```

                                зависит: порядок расставляет ОБА типа
```

## 3. Задача 1 — новый участок карты ✅ СДЕЛАНО 28.08.2026

### 3.1. Что требуется

Перевести приложение на **новый кусок местности**: район Плесецк — Мирный
(Архангельская обл.), файл `geo_cache/APX.osm.pbf`.

> ⚠️ **Первая редакция этого раздела была написана вслепую** — 60 строк про конвертер
> шести векторных форматов. Ответ заказчика («формат прежний, `.osm.pbf`») обнулил их
> целиком. Урок вынесен в переносимые правила:
> [7_СОСТАВЛЕНИЕ_ПЛАНА.md §1](../переносимое/7_СОСТАВЛЕНИЕ_ПЛАНА.md).

### 3.2. Как решено

Формат прежний, поэтому машина весов и разбор OSM не тронуты вовсе. Вместо конвертера
появился **реестр участков**: участок — это не рамка, а четыре связанные вещи.

```
THREAT_AREAS["plesetsk"] = границы + исходник .osm.pbf + файл слоёв .npz + рельеф
                                     ▲
                 переключается одной строкой THREAT_AREA
```

| Что сделано | Где |
|---|---|
| реестр участков и активный ключ `THREAT_AREA` | `config.py` :: `THREAT_AREAS` |
| производные величины берутся из активного участка | `config.py` :: `THREAT_BBOX_LONLAT`, `THREAT_LAYERS_FILE`, `THREAT_DEM_FILE`, `THREAT_ENTRY`, `THREAT_TARGET` |
| кэш слоёв **у каждого участка свой** (прежний не затирается) | `threat_grid.py` :: `layers_cache_path`, `load_layers` |
| участок без своего DEM не ломает поиск рельефа | `threat_grid.py` :: `dem_files` |
| скрипт берёт исходник и приёмник из участка, принимает и явные | `tools/build_threat_grid.py` |

**Прежний участок Северодонецк → Луганск не удалён**, а остался второй записью реестра:
на нём сделаны все замеры журнала, и он включается сменой `THREAT_AREA`.

**Решения, принятые по ходу (заказчик, 29.08.2026):**

1. **Раствор 60°, а не 90°** — `THREAT_SECTOR_HALF_DEG` = 30° в каждую сторону.
   Сектор ±45° захватывал слишком широкую дугу края, и «направление» размывалось.
2. **Своя палитра разметки.** Первый вариант — зелёный `THEME["ok"]` — сливался с
   весовой картой. Взят белый (в палитре turbo белого нет вовсе) с тёмной обводкой и
   тёмной подложкой под пунктиром: `THREAT_COLORS["sector" / "sector_edge" /
   "entry_pt" / "entry_pt_edge"]`.
3. **Чекбокс показа** — прячет разметку, не отменяя сектор.
4. **Пауза повтора** `THREAT_SECTOR_ENTRY_COOLDOWN` = 2: точка не повторяется, пока не
   отработают две другие. Равный жребий давал серии, и на коротком прогоне часть точек
   не участвовала. Замер: повторов подряд 0, через один 0, отработали все 5.
5. **Клик — ЦЕНТР сектора.** Рассматривался вариант «клик = крайняя граница, сектор
   идёт от неё в одну сторону»; принят центральный: указанное направление логичнее
   видеть серединой, иначе сектор целиком уезжает вбок от того, куда указали.
6. **Точка входа обязана быть достижимой** — проверяется при отборе, одним полем
   Дейкстры от цели. Из недостижимой точки БПЛА не полетит, и она бы просто съедала
   попытки.
7. **Пересчёт — по «Применить», а не по клику.** Цель и сектор задают подряд, и
   пересчёт после каждого клика шёл дважды, первый раз — по промежуточной обстановке
   (новая цель со старым сектором). Теперь клики копят изменения (`_pending_recalc`),
   расчёт идёт один раз. Маршруты и датчики при клике сбрасываются: они построены по
   прежней обстановке, показывать их дальше — врать.
8. **Два чекбокса вместо одного:** «Точки входа» (включён — они участвуют в расчёте) и
   «Границы сектора» (выключен — служебная разметка «откуда отбирали»).

**Замер (участок `plesetsk`, чистые умолчания):** 5 точек входа, все на краю
(≤ 0.75 км от рамки), углы от оси 3.5–23.9° при пределе 30°; маршруты стартуют ровно из
этих точек, в выборке представлены **все пять**; 250 маршрутов, 150 итераций, 15
датчиков, засечка ≥ k = 100 %, **10.3 с** (с одним входом было 11.2 с — пять входов не
подорожали, потому что дорогие поля считаются один раз).

⚠️ **Qt-часть проверена компиляцией и сверкой имён, а не запуском:** в окружении
разработки не поднимается плагин `offscreen` («no Qt platform plugin could be
initialized»). Живая проверка — запуском `python main_qt.py`; заказчик подтвердил, что
кнопка и отрисовка работают.

### 4.1. Что требовалось (по описанию заказчика)

1. Кнопка **«Задать сектор направления»**;
2. пользователь щёлкает **по краю карты** — получается точка `P`;
3. строится прямая **цель `B` → `P`**;
4. от этой прямой откладывается **±30°** (изначально было ±45°, сужено 29.08.2026) —
   получается **сектор** с вершиной в цели;
5. часть **краёв карты**, попавшая в сектор, — это возможные направления появления БПЛА;
6. по этой части края, **с учётом весовой карты**, выбираются **5 точек входа**;
7. точки обозначаются на карте;
8. старт каждого маршрута берётся из этих пяти.

### 4.2. Геометрия — как считать

```
u = (P − B) / |P − B|                     орт направления «цель → указанная точка»
сектор = { направления d : угол(d, u) ≤ 30° }      THREAT_SECTOR_HALF_DEG
```

Принадлежность направления сектору проверяется через скалярное произведение — без
арктангенсов и без разрывов при переходе через 180°:

```
d · u ≥ cos(30°) · |d|          ⟺   направление внутри сектора
```

**Отбор точек на краю карты:**

1. взять ячейки границы прямоугольника `bbox_km` (четыре стороны);
2. оставить те, для которых направление `цель → ячейка` попадает в сектор (формула выше);
3. отбросить непроходимые (`passable_mask`, `threat_routes.py` строка 139) — точка входа
   обязана быть достижимой, иначе маршрут из неё не построится;
4. из оставшихся выбрать **5** с наибольшим весом `w(e)`, **разнесённых** между собой —
   иначе все пять слипнутся в одном «горячем» углу.

**Как обеспечить разнесённость** — тем же жадным приёмом, что и у датчиков: брать
максимум веса, затем исключать соседей ближе `d_min` и повторять. Разумное начальное
`d_min` — примерно `(длина края в секторе) / 10`; вынести в константу.

| Шаг | Файл :: место |
|---|---|

| обработчик | `threat_controller.py` рядом с обработчиками кликов (296–330) |
| отрисовка сектора и точек | `threat_view.py` — слой поверх карты |

### 4.4. Как встроить пять точек в построение маршрутов

Здесь главное — **не сломать кэш контекста**.

* `build_iter_context(grid, entry_km, target_km, ...)` (строка 763) кэшируется по ключу
  `_ctx_key()` (строка 2012). Дорогие поля считаются **от цели** и от входа не зависят
  (§1.2, факт 1) — поэтому **не надо** пересчитывать контекст для каждой из пяти точек.
* Зависят от входа только: проекция ячеек на ось «вход→цель» (строки 819–822) и часть
  параметров VIA. Возможные решения, в порядке предпочтения:
  1. **считать ось от ЦЕНТРА сектора** (усреднённое направление) — контекст остаётся
     один, разброс по пяти точкам обеспечивается стартовой ячейкой;
  2. если качество маршрутов просядет — хранить пять «лёгких» надстроек над общим
     контекстом (только проекции), не дублируя поля Дейкстры.
* В `plan_routes` (2039) и `iter_step` (2170) при розыгрыше каждого маршрута выбирать
  стартовую точку из пяти. Распределение: равномерно либо пропорционально весу точки —
  **начать с равномерного**, как более честного при неизвестном противнике.

### 4.5. Что проверить

* пять точек лежат **на краю** карты и **внутри** сектора;
* из каждой строится хотя бы один маршрут (иначе точка выбрана в непроходимой зоне);
* область достижимости (`flight_envelope`, 192) перестроилась под новый вход;
* при смене сектора маршруты и датчики **сбрасываются** — как это уже сделано в
  `set_target` (2500–2510).

⚠️ **Прежний код не удалён, а закомментирован** в `_place_by_routes`: если окажется, что

[МЕТОДИЧКА_ДАТЧИКИ_ДВА_ТИПА §3.1](../вкладка_3/МЕТОДИЧКА_ДАТЧИКИ_ДВА_ТИПА.md).

### 5.1. Что требовалось

1. **минимум один датчик рядом с точкой старта**, но **не за ней**;
2. правило «маршрут не уходит назад» — **остаётся** (это про движение, не про датчики);
3. правило «датчики не ставятся за целью» — **смягчить**: разрешить и до, и после цели,
   но так, чтобы датчики **не пересекались между собой** и **не перекрывали цель больше
   чем на 30 %**.

### 5.2. Где править

**Всё в одном месте** — `_place_by_routes` (`threat_grid.py`, строка 2342):

```python
if D2 > 1e-9:                       # ← строки 2357–2359, ЭТО и надо заменить
    s = ((cand - A) @ d) / D2
    cand = cand[(s >= 0.0) & (s <= 1.0)]      # оставляли только между A и B
```

**Новое правило** вместо жёсткого отсечения:

```
s = проекция кандидата на ось «вход → цель», в долях |AB|
допустимо:  s ≥ 0            (не позади точки старта — правило 1 сохраняется)
            s ≤ 1 + запас    (за целью — можно, но не дальше запаса)
```

Запас за целью выразить в долях радиуса, а не в долях `|AB|`: `|AB|` меняется при каждом
клике по цели, и правило «поплывёт». Разумно `s_макс = 1 + k·R / |AB|`.

### 5.3. Ограничение «перекрытие цели ≤ 30 %»

Формулировка заказчика: датчики не должны «пересекать цель более чем на 30 %».
Читается как: **зона датчика не должна накрывать окрестность цели больше чем на 30 %
своей площади**. Считается через площадь пересечения двух кругов — формула и разбор
уже выписаны в [пособии, часть 2 §9.1](../пособие/2_ГЕОМЕТРИЯ_И_ОБОЗНАЧЕНИЯ.md):

```
S_пересечения = 2R²·arccos(d / 2R) − (d/2)·√(4R² − d²)
```

Отсюда получается **минимальное допустимое расстояние** от датчика до цели, и правило
сводится к простой проверке `|c − B| ≥ d_min` — считать площади в цикле не нужно.

⚠️ **Уточнить у заказчика:** 30 % от площади **зоны датчика** или от **защищаемой
окрестности цели**? От ответа зависит `d_min`. По умолчанию взять первое.

### 5.4. Ловушка

⚠️ **Раздел устарел 29.08.2026: якоря отключены** (см. §5.0). Ниже — как было, когда
якорь у входа ещё ставился принудительно; текст оставлен для истории решения.

Датчик у точки старта существовал как якорь у входа (`_place_by_routes`). При пяти
точках входа якорь должен был бы ставиться **у той точки, которая используется чаще**
(или у каждой, если датчиков хватает). Не забыть: при числе якорей больше числа датчиков
жадный алгоритм не сможет разместить ничего полезного.

```
③ 3 БОЛЬШИХ датчика: круговой щит у цели, минимальное взаимное перекрытие,
   с учётом движения БПЛА
④ все оставшиеся малые — обычный жадный выбор по выборке маршрутов
```

### 7.2. Как решать

Переписать `place_sensors` (строка 2311) как последовательность этапов, где каждый
следующий видит уже занятые позиции:

```python
def place_sensors(self):
    занятые = []
    занятые += этап_старт()          # ① якоря у точек входа
    занятые += этап_цель()           # ② 2–3 малых у цели
    занятые += этап_большие()        # ③ 3 больших, угловой разнос
    занятые += этап_остальные()      # ④ жадный выбор на остатке
```

**Механизм для этапов ①–③ уже есть** — это параметр `anchors` в
`CoverageCache.greedy` (используется в строке 2385). Каждый этап добавляет свои позиции
в список якорей следующего; отдельный алгоритм писать не нужно.

✅ **Ответ заказчика (вопрос 6):** якоря не должны стоять «сбоку» от жадного алгоритма.
Правильная схема — **жадный алгоритм заранее знает занятые позиции и добирает остальное
до `N`**:

```python
якоря = этап_старт() + этап_цель() + этап_большие()   # обоснованные позиции
итог  = cache.greedy(N, anchors=якоря)                # добор остатка тем же критерием
```

Разница принципиальная. При «расставить отдельно, потом запустить жадный» второй этап
не видит, что уже покрыто, и дублирует покрытие. При передаче через `anchors` прирост
каждой следующей позиции считается **сверх уже покрытого якорями** — то есть якоря
работают как первые шаги того же алгоритма, а не как отдельная процедура.

**Чем обосновывается каждый якорь** (это и требовалось: не «поставить, потому что так
сказано», а из задачи):

| Якорь | Обоснование |
|---|---|
| ① у точки входа | БПЛА обнаруживается **как можно раньше**: чем ближе к границе появления, тем больше времени на реакцию |
| ② 2–3 у цели | последний рубеж: цель должна оставаться под наблюдением, даже если маршрут пришёл неожиданной стороной |
| ③ 3 больших кругом | сектор приходит с **любой** стороны, поэтому нужен круговой контроль, а не полоса вдоль одного направления |
| ④ остаток | там, где плотность маршрутов выше всего, — это и есть жадный критерий |

⚠️ **Сохранить свойство субмодулярности.** Принудительные якоря его не нарушают:
гарантия `(1 − 1/e)` формулируется для **оставшихся** позиций при фиксированных
якорях. Это стоит явно записать в методичку — иначе при следующей сверке возникнет
вопрос, действует ли ещё оценка качества.

### 7.3. Что проверить

* сумма по этапам = заказанному числу датчиков (`threat_N` малых + `threat_N_big` больших);
* ни один этап не «съел» весь бюджет, оставив следующие пустыми;
* при малом числе датчиков (например 5) этапы деградируют разумно, а не падают.

## 9. Задача 7 — порог «город» по данным участка (вместо числа 4.0 км²)

### 9.1. Что требуется

Правило: «town площадью ≥ `THREAT_TOWN_CITY_KM2` — город (пролёт запрещён), мельче —
деревня (мягкий штраф)». Число подобрано **по прежнему участку** и на новом стоит ровно
на краю распределения: пятна там 0.25 … 4.0 км², то есть исход решался последней
десятой долей.

**Принято 29.08.2026 как временная мера: порог снижен до 2.0 км²** — города на новом
участке появились (2 → 4 пятна, 1.8 → 6.2 км²). Это подгон, и он останется подгоном:
на третьем участке число снова придётся подбирать вручную, а на прежнем оно уже
сдвинуло городскую зону на +7.7 %. Требуется **показатель, который считается по
загруженной карте** — так же, как уже сделана собственная градация НП.

### 9.2. Почему это вообще решаемо: половина механизма уже есть

В коде уже принят принцип «пороги берём от данных участка, а не из константы»:

| Что уже считается по данным | Где |
|---|---|
| распределение пятен застройки: минимум, медиана, максимум, число | `threat_grid.py` :: `settlement_stats` |
| паспорт пятна: **масштаб** (площадь) и **компактность** (плотность 0..1) | `place_profiles` |
| перевод пункта в соседний класс по обоим признакам, с отсевом выбросов | `grade_places` |

**Абсолютным осталось ровно одно число** — `town_city_km2`, и именно оно решает,
будет ли запрет пролёта. Задача — довести до конца уже принятый принцип.

### 9.3. Предлагаемое решение: порог по РАЗРЫВУ в распределении

Город отличается от деревни не «числом квадратных километров», а тем, что он
**оторван по масштабу от массы остальных пунктов**. Это измеримо.

```
площади пятен, отсортированные:   0.25  0.25  0.5  0.75  1.0  1.5 │ 4.0  4.0
                                                                   ▲
                                              наибольший скачок 2.7× — вот граница
                         порог = √(1.5 × 4.0) ≈ 2.45 км²  (среднее геометрическое пары)
```

**Алгоритм** (новая функция `city_area_threshold` рядом с `settlement_stats`):

1. взять площади пятен, у которых есть метка `place` класса town/city;
2. отсортировать; в верхней половине (крупнее медианы) найти **наибольшее отношение
   соседних площадей** `a[i+1] / a[i]`;
3. порог = **среднее геометрическое** этой пары — граница проходит по разрыву,
   а не по краю одного из классов;
4. **предохранители с двух сторон**, чтобы относительный критерий не сошёл с ума:
   * порог не ниже `THREAT_CITY_MIN_KM2` (≈ 1 км²) — три дома не станут городом
     оттого, что рядом нет ничего крупнее;
   * порог не выше `THREAT_URBAN_MIN_AREA_KM2` = 8 км² — пятно такого размера
     остаётся городом при любой статистике (правило уже есть);
5. **если разрыва нет** (максимальное отношение меньше `THREAT_CITY_GAP_MIN` ≈ 1.8) —
   распределение сплошное, разделять нечего: берётся прежнее абсолютное число.
   Поведение тогда ровно как сейчас;
6. **второй признак — обязателен**, как в `grade_places`: город должен быть не только
   крупным, но и компактным (плотность не ниже медианной по кандидатам). По одному
   масштабу в города уедет вытянутая промзона вдоль дороги.

**Что это даёт на наших двух участках** (ожидание, проверяется прогоном):
на прежнем участке разрыв между деревнями и Северодонецком (17.25 км²) огромный —
порог встанет заметно выше 4.0, и городская зона не должна вырасти; на новом
участке разрыв 1.5 → 4.0 даёт порог ≈ 2.45, и Плесецк с Мирным становятся городами.

### 9.4. Отвергнутые варианты (и почему)

| Вариант | Почему нет |
|---|---|
| подкрутить число до 2.0 «под этот участок» | подгон: следующий участок снова потребует ручного подбора — то, от чего уходим |
| порог как поле каждого участка в `THREAT_AREAS` | тот же ручной подбор, просто разложенный по записям |
| «город = верхние 10 % пятен по площади» (квантиль) | механический: на участке из шести посёлков всегда назначит город, даже когда города нет |
| порог от медианы (`медиана × k`) | медиану держат хутора, она не про города; на нашем участке медиана 0.75 км² |

### 9.5. Что проверить

* **прежний участок — главная проверка на «не подгон»**: городская зона должна
  остаться **3 441 ячейка** или измениться объяснимо; эталон
  [ОГРАНИЧЕНИЯ §6](../ОГРАНИЧЕНИЯ.md);
* новый участок: сколько пунктов стало городами, какой вышел порог и по какому разрыву;
* **механизм должен выключаться** (`THREAT_CITY_GAP_MIN` = 0 → прежнее поведение) —
  правило проекта: любой новый механизм имеет выключатель;
* в сводке по НП печатать сам порог и разрыв — иначе число снова станет «магическим».

### 9.6. Открытый вопрос

Считать разрыв по **всем** пятнам застройки или только по тем, у кого есть метка
`place`? Предлагается второе: пятно без метки — это чаще промзона или дачи, оно
искажает верхний хвост. Умолчание — только с меткой.

```

вес_итог = вес · clip(k, 0.25 … 1.40),  с полом THREAT_DEM_FLOOR
плюс ОТСЕЧКА: «уж очень высокое место» — вес снимается совсем
```

умолчания, рельеф включается явно.

| Показатель | Эталон до правок |
|---|---|
| ячеек-коридоров | 11 101 |
| городская зона | 3 441 ячейка |
| датчиков размещено | 15 из 15 |
| датчиков на воде | 0 |
| засечка ≥ `k` = 3 | 98.7–100 % |
| время прогона | ≈ 17 с |

⚠️ **Часть эталона неизбежно изменится** — это нормально: спавн стал другим, датчиков
стало два типа. **Правило:** после каждой задачи записать новые числа и **объяснить,
почему они изменились**. Число, изменившееся без объяснения, — признак поломки.

Проверки документации (по решению, прогон затратный):
