# Методичка · Все модели движения, маршрутов и расстановки датчиков (вкладки 1–3)

Сводный документ: собраны ВСЕ подходы к построению движения/маршрутов БПЛА в трёх
вкладках, правила расстановки датчиков, загрузка подложки и цифровых карт — с
формулами и пояснениями. Детальные выводы по вкладкам 1–2 — в [`МЕТОДИЧКА.md`](МЕТОДИЧКА.md);
механика весовой карты вкладки 3 — в [`МЕТОДИЧКА_КАРТА_УГРОЗ.md`](МЕТОДИЧКА_КАРТА_УГРОЗ.md);
тайлы/подложка — [`МЕТОДИЧКА_КАРТА.md`](МЕТОДИЧКА_КАРТА.md); загрузка OSM —
[`МЕТОДИЧКА_ЗАГРУЗКА_КАРТ.md`](МЕТОДИЧКА_ЗАГРУЗКА_КАРТ.md).

Обозначения: `A` — старт, `B` — цель, `L_max` — запас хода, `R` — радиус
обнаружения датчика, `k` — требуемая кратность обнаружения.

---

## 0. Три вкладки — три разных постановки

| Вкладка | Что известно | Как рождается маршрут | Что оптимизируем |
|---|---|---|---|
| 1. «Маршрут A→B» | точки A и B, L_max | АНАЛИТИЧЕСКАЯ геометрия (дуги/петли/манёвр), случайный разброс | расстановка N датчиков по выборке маршрутов |
| 2. «Зона старта → цель» | ЗОНА старта (эллипс) и B | то же, но старт — случайная точка зоны | то же + учёт разброса стартов |
| 3. «Карта угроз» | реальная местность (OSM) | по ВЕСОВОЙ карте: маршрут тянется к рекам/дорогам, обходит города | датчики по весам + сами маршруты пролёта |

Ключевое различие: во вкладках 1–2 рельеф/дороги НЕ учитываются (идеальная геометрия
в пустом поле), маршруты — случайные кривые в пределах запаса хода. Во вкладке 3
маршрут определяется РЕАЛЬНОЙ местностью через весовую карту.

## 1. Общий геометрический каркас (вкладки 1–2)

### 1.1 Эллипс достижимости

Любой путь длиной ≤ `L_max` из A в B целиком лежит в эллипсе с фокусами A, B:

    E = { P : |PA| + |PB| ≤ L_max }

Полуоси: большая `a = L_max/2`, фокусное `c = |AB|/2`, малая `b = √(a²−c²)`.
Доказательство включения: для точки P на пути `|PA| ≤ (длина A→P)` и
`|PB| ≤ (длина P→B)`, значит `|PA|+|PB| ≤ длина ≤ L_max`. Поэтому ограничение по
запасу хода само удерживает траекторию внутри эллипса.

### 1.2 Предельный угол отклонения (для дуг)

Дуга из A в B по касательно-хордовому углу θ имеет длину `Larc(θ)`. Предельный угол
`θ_max` — такой, что `Larc(θ_max) = L_max`. Разброс маршрутов задаётся выборкой θ:

    θ ~ усечённое распределение на [−θ_max, θ_max], ширина = профиль разброса.

## 2. Вкладка 1 · модели движения (A→B)

Контракт генератора: вернуть `np.ndarray (n_points, 2)` в км. Три модели (`SAMPLERS`):

1. **Дуги (этап 1)** — `make_arc_by_angle(A, B, θ)`: дуга окружности с центральным
   углом от θ. Разброс — профиль малый/средний/сложный (амплитуда θ).
2. **Петли/змейка (этап 2)** — синусоида с закреплёнными концами A, B; амплитуда
   ограничена запасом хода. Суммарная кривизна гармоник ≤ 1/R_min (учёт радиуса
   разворота, формула 13 в `МЕТОДИЧКА.md`).
3. **Манёвр по путевым точкам** — ломаная A→точки→B со скруглением углов дугами
   радиуса ≥ R_min. Число точек — пользовательский диапазон [n_min, n_max].

**Физика (ТТХ → R_min).** Радиус разворота из крена φ и скорости V:

    R_min = V² / (g · tan φ)

(V — крейсерская скорость, типично ~180 км/ч для коммерческого БПЛА
самолётного типа; φ — макс. крен). Это
физический предел «крутизны» манёвра — общий для вкладок 1–2.

**Профили разброса** — это АМПЛИТУДА отклонения от прямой (не число точек):
малый ~0.1·b, средний ~0.4·b, сложный ~b (b — полу-малая ось эллипса), смешанный —
случайный выбор режима каждую итерацию (доли 25/25/50 в пользу сложного).

## 3. Вкладка 2 · старт из ЗОНЫ → цель

Отличие: старт не точка A, а СЛУЧАЙНАЯ точка `S₀` из зоны неопределённости (эллипс
вокруг A: глубина вдоль оси, ширина поперёк). Каждый маршрут — из своей `S₀` в B.

Модели движения: «дуга из старта», «ломаная», «манёвр» (те же ядра, что вкладка 1,
но из S₀). Огибающая достижимости — объединение эллипсов (S₀, B) по всем S₀ зоны
(любой маршрут внутри неё). Путевые точки: переключатель «в зоне старта / только за
зоной» (мягкое условие). Зона старта — область НЕОПРЕДЕЛЁННОСТИ, не препятствие.

## 4. Вкладка 3 · цифровая карта угроз

Здесь маршрут не «рисуется формулой», а вытекает из РЕАЛЬНОЙ местности.

### 4.1 Весовая карта (costmap)

Местность делится на сетку 500×500 м. Каждый цифровой слой накладывается на сетку;
вклад линейного слоя в ячейку:

    вклад = вес_слоя × (длина_пересечения_в_ячейке / размер_ячейки)

(пропорционально присутствию объекта в ячейке; нормировка делает слои сопоставимыми).
Суммарный вес ячейки:

    W(ячейка) = Σ_слоёв вклад  +  funnel_бонус·(число_слоёв−1)  +  мост  −  город

* аттракторы (река/дорога/ж-д/ЛЭП/трубопровод/лесополоса) — «+»: БПЛА тяготеет к
  протяжённым ориентирам;
* funnel-бонус — «+» за схождение нескольких ориентиров (перекрёстки/переправы);
* мост (река ∧ магистраль/ж-д) — «+»;
* НАСЕЛЁННЫЙ ПУНКТ — жёсткий «−» (город исключается из пролёта, см. §4.3).

Подробно — в `МЕТОДИЧКА_КАРТА_УГРОЗ.md`.

### 4.2 Маршруты пролёта по costmap (реализовано, чекбокс «маршруты»)

Стоимость прохода ячейки — тем МЕНЬШЕ, чем БОЛЬШЕ её вес:

    cost(ячейка) = base_cost + weight_scale · (1 − W_норм),   W_норм = clip(W⁺ / p90(W⁺), 0, 1)

где `W⁺ = max(W,0)`, `p90` — 90-й перцентиль ПОЛОЖИТЕЛЬНЫХ весов. Маршрут — путь
МИНИМАЛЬНОЙ суммарной стоимости от входа к цели (Дейкстра на 8-связной сетке).

> **Почему перцентиль, а не максимум (исправленный баг).** Если нормировать на
> `max(W⁺)`, один сверх-тяжёлый узел (река+много дорог+мост) делает `W_норм` у всех
> остальных ≈ 0, стоимость почти ОДИНАКОВОЙ, и Дейкстра идёт ПО ПРЯМОЙ (кратчайшей),
> игнорируя коридоры — маршруты выходили прямыми диагоналями. По `p90` типичные
> ячейки коридора получают `W_норм ≈ 1` (дёшево), «пустые» — дорого, поэтому маршрут
> реально ИДЁТ ПО ТЕПЛОВОЙ КАРТЕ (рекам/дорогам). Проверка: средний вес вдоль
> маршрута ≫ веса вдоль прямой.

Свойства:

* `base_cost > 0` — «мостик через провалы»: короткая цепочка НУЛЕВЫХ ячеек между
  двумя тяжёлыми коридорами проходима, маршрут НЕ рвётся (требование пользователя).
  Длинные провалы дороги (много ячеек × стоимость пустой), поэтому мостятся ТОЛЬКО
  короткие разрывы, а не строится прямая через пустошь;
* РЕКА в городе — проходима (см. §4.3): БПЛА идёт по руслу сквозь город;
* прочий город — большая доп. стоимость `urban_cost` (мягкий обход: маршрут сильно
  избегает застройки, но старт/финиш В городе возможны, иначе окружённый город дал
  бы «маршрут не найден»);
* K альтернативных коридоров — итеративно: найдя путь, штрафуем его ячейки (×2.5)
  и ищем следующий → набор разнообразных линий пролёта (`THREAT_ROUTE_COUNT`).

### 4.3 Исключение КРУПНЫХ городов, но реки — проходимы

Проблема: в городе много дорог/перекрёстков → funnel-бонус делал город самым
«тяжёлым», хотя над плотной застройкой БПЛА как раз НЕ идёт.
Решение: помечаем застроенные ячейки; считаем ПЛОТНОСТЬ застройки в окне ~4×4 км
(box-фильтр). Где плотность ≥ порога (по умолчанию 25% — это КРУПНЫЙ город, не
деревня) — ячейка исключается: её вес заменяется штрафом (город «холодный»), маршрут
её обходит.

    urban = (box_mean(built, окно) ≥ порог)  И  (в ячейке НЕТ реки)
    W[urban] := штраф;  для маршрута urban — большая доп. стоимость

Два важных уточнения (по замечаниям пользователя):

* **Реки в городе НЕ исключаются.** Ячейки, где проходит река, остаются коридором
  даже внутри города — БПЛА идёт по руслу/ручьям сквозь застройку. Поэтому из маски
  города вычитаются речные ячейки (`urban &= ~river`), их вес сохраняется, и маршрут
  может пройти по реке через город.
* **Только крупные города.** Порог плотности поднят (25% в окне 4 км), чтобы
  деревни/хутора НЕ блокировались — над ними пролёт возможен; исключаются лишь
  большие населённые пункты. Пороги — в `config.THREAT_URBAN_*`.

### 4.4 «ВСЕ возможные места пролёта» — envelope по запасу хода (реализовано)

Чекбокс «маршруты (все места пролёта)» показывает НЕ 14 линий, а **всю область**,
куда БПЛА вообще может дойти из входа в цель, уложившись в ЗАПАС ХОДА `L_max`
(главное ограничение — из окна «Входные данные»). Реализация — два поля
геометрических расстояний по проходимым коридорам:

    passable = (коридоры: W>0)  ⊕ дилатация на ≤ max_gap  −  город (кроме рек)
    glen_вход(ячейка)  — кратчайшая ДЛИНА пути (км) от входа по passable
    glen_цель(ячейка)  — то же от цели
    envelope = { ячейка : glen_вход + glen_цель ≤ L_max }

Свойства:
* **Все пути, включая длинные обходы.** Если можно обогнуть и зайти в цель с другой
  стороны, и это укладывается в `L_max` — такие ячейки тоже в envelope. Раньше
  показывались только короткие коридоры; теперь — всё в пределах запаса хода.
* **Мостики через провалы — только прямые и ≤ РАЗРЫВА** (см. ниже). Коридоры
  «склеиваются» дилатацией на пол-провала: разрыв короче порога перекрывается прямым
  участком, длиннее — НЕ перекрывается: там коридор разорван, маршрут идёт в обход или
  (если обхода в пределах `L_max` нет) невозможен.
* Поверх области рисуются линии-ПРИМЕРЫ маршрутов (см. «Сколько всего маршрутов» ниже).

Показывается розовой полупрозрачной заливкой ячеек + линии-примеры. «Мин. длина
вход→цель» выводится в показателях.

#### РАЗРЫВ между весовыми секторами (`Params.threat_max_gap_km`, окно «Входные данные»)

Порог сшивания коридоров — **параметр интерфейса**, не константа. Смысл физический:
*пустое место (нулевой вес) короче разрыва БПЛА перелетит* — секторы считаются одним
коридором; длиннее — коридор разорван, и маршрута через него нет.

Это главный рычаг «связности» карты: он меняет и ОБЛАСТЬ ЗАЛЁТА, и набор возможных
маршрутов ещё ДО итераций. Замер на реальных данных OSM (bbox ~2400 км²):

| Разрыв | Проходимо ячеек | Область залёта | Кратчайший путь |
|---|---|---|---|
| 0 км | 28 % | 900 км² | 86,7 км |
| 1 км | 50 % | 1908 км² | 83,5 км |
| **2 км** (по умолч.) | 58 % | **2439 км²** | 83,5 км |
| 3 км | 63 % | 2688 км² | 83,5 км |
| 5 км | 67 % | 2667 км² | 79,2 км |

При смене разрыва пересобирается контекст выборки (его кэш-ключ — `(разрыв, цель)`),
пересчитываются область и маршруты.

#### Сколько ВСЕГО возможных маршрутов (и почему нельзя показать «все»)

Естественный вопрос: зачем выборка, если можно перебрать все пути деревом — линия,
развилка на 3, у каждой снова развилка, и так до цели? Ответ даёт **точный подсчёт БЕЗ
перечисления** (`count_possible_routes`), динамическим программированием от цели наружу:

    N(цель) = 1,   N(ячейка) = Σ N(соседей, которые ближе к цели)

Порядок обхода — по убыванию расстояния до цели, поэтому граф ациклический (шаг всегда
сокращает расстояние) и каждая ячейка считается один раз: сложность O(ячеек).

На реальных данных: **ветвление 3,31** соседа-«к цели» на ячейку (то самое «разветвление
на 3 линии»), длина пути **167 шагов** по сетке 500 м, итого

    N ≈ 3,4 × 10¹⁰⁷ маршрутов

Для сравнения: атомов в наблюдаемой Вселенной ~10⁸⁰. Маршрутов на 27 порядков больше —
перечислить или нарисовать их нельзя никаким компьютером. **Отсюда разделение ролей:**

* **«Где БПЛА может пролететь» → ЗАКРАШЕННАЯ ОБЛАСТЬ.** Она отвечает за все 10¹⁰⁷ путей
  сразу и считается ТОЧНО (два поля Дейкстры, не перебор). Никакой выборки здесь нет.
* **«Как он может лететь» → выборка линий** (`THREAT_ROUTE_COUNT`, по умолчанию 250).
  Это примеры внутри области, а не полный перечень.

Число возможных маршрутов выводится в статистике вкладки — чтобы было видно, из чего
сделана выборка.

#### Как выборка раскладывается по области ШИРОКО (`_spread_over_area`)

Задача линий-примеров — лечь по области максимально широко и равномерно, а не показать
«типичный» путь. Поэтому:

1. **Повадки берутся ВЕЕРОМ.** Режим веса, разброс и профиль расхода — все `mix`
   (перебираются случайно). Выбор в панели итераций на эту картину НЕ влияет: она
   показывает возможности целиком, а не один сценарий (см. §4.5).
2. **Жадный субмодулярный отбор.** Набирается пул кандидатов
   (`THREAT_ROUTE_POOL_MULT × COUNT`), из него отбираются маршруты, покрывающие ЕЩЁ НЕ
   ПОКРЫТУЮ часть области; покрытые ячейки гасятся. Следующий маршрут вынужден идти по
   ДРУГОМУ коридору — выборка расходится, а не липнет к кратчайшему пути. Тот же принцип
   и та же гарантия (1 − 1/e), что у расстановки датчиков (§5.2).

Эффект на реальных данных: покрытие области выборкой из 250 линий **35 % → 54 %**.
Размер пула насыщается (×1 → 48 % за 3 c; ×2 → 54 % за 8 c; ×3 → 57 % за 12 c;
×4 → 58 % за 16 c) — выбран ×2: дальше растёт цена, а не покрытие.

### 4.5 Итерационная СТОХАСТИЧЕСКАЯ модель (РЕАЛИЗОВАНА — `sample_one_route` / `ThreatModel.iter_batch`)

Статика (§4.4) отвечает на «КУДА вообще может дойти БПЛА». Симуляция отвечает на
«КАК он пойдёт в конкретном пролёте» — и именно её датчики должны закрывать. Ниже —
**итоговый рекомендованный подход** и обоснование (по всем замечаниям пользователя).

**Механика одного пролёта (развилистый рандом).** БПЛА стартует из входа и шагает по
клеткам; на КАЖДОЙ РАЗВИЛКЕ (ячейке с ≥2 направлениями-кандидатами — это и есть
«пересечения», §_crossings_) выбирает следующий сегмент СЛУЧАЙНО с вероятностью,
зависящей от веса соседнего коридора:

    P(идти в соседа j) ∝ f_режим(W_коридор(j)) · b_цель(j)

* `W_коридор(j)` — вес коридора, на который ведёт сосед (не одной клетки, а сегмента
  до следующей развилки — чтобы «увидеть» дорогу целиком);
* `b_цель(j) = exp(κ · cosθ)` — лёгкое СМЕЩЕНИЕ К ЦЕЛИ (θ — угол между направлением
  на соседа и на цель): не даёт блуждать назад/по кругу, но не диктует прямую;
* между развилками БПЛА идёт по коридору (не выбирает каждую клетку — иначе выродится
  в дрожь).

**Четыре режима выборки `f_режим` (как просил пользователь).** Чтобы в выборке были
НЕ только «жирные» русла/шоссе, но и второстепенные пути:

| Режим | `f(W)` | Что даёт |
|---|---|---|
| 1. приоритет высокого веса | `W^γ`, большой γ | почти всегда самый тяжёлый коридор (река/шоссе) |
| 2. сбалансированный | `W^γ`, средний γ | заметный разброс, но с уклоном к тяжёлым |
| 3. приоритет НИЗКого веса | `W^(−γ)` (или `(Wmax−W)^γ`) | тяготеет к второстепенным путям |
| 4. смешанный 33/33/33 | случайно один из режимов 1–3 на каждый маршрут | в выборке и макс-, и мин-весовые маршруты |

Так снимается риск «локального рандома» (когда итерируются только русла) — режимы 3
и 4 специально вытягивают маловероятные коридоры. Веса и γ — в интерфейсе.

**Кинематика (радиус разворота и «не слишком извилисто»).** Чтобы линии были
реалистичны:
* на развилке, ГДЕ БПЛА реально сворачивает, вставляется МАНЁВР — дуга радиусом
  `R_min = V²/(g·tan φ)` (из скорости/крена, окно «Входные данные»), а не излом под
  90°; после дуги курс выравнивается на новый коридор;
* НАПРАВЛЕНИЕ меняется НЕ чаще, чем раз в `Params.threat_turn_interval_km` («длина
  прямого участка», окно «Входные данные»): между сменами курс держится, путь не «дёргается»;
* прямые мостики через провалы — не длиннее РАЗРЫВА (`Params.threat_max_gap_km`, §4.4).

**Показ и связь с датчиками.** В отличие от статики (envelope — вся область сразу),
при ИТЕРАЦИЯХ маршруты показываются ПО ОДНОМУ, как во вкладке 2: анимация пролёта
маршрута за маршрутом. Каждый сгенерированный маршрут добавляется в выборку; из
плотности выборки строится «тепловая карта маршрутов», и датчики РАССТАВЛЯЮТСЯ по ней
тем же жадным субмодулярным алгоритмом (§5.2) — то есть закрывают именно те коридоры,
по которым реально идёт БПЛА, с учётом кратности и распределённости. Это ровно схема
вкладок 1–2, но источник маршрутов — реальная карта.

**Почему именно так (обоснование выбора).**
* *Развилки, а не «выбор 1 из 100 готовых».* Пользователь прав: заранее считать N
  маршрутов и тянуть из них — беднее и предсказуемее. Пошаговый выбор на перекрёстках
  даёт настоящее ветвление, реагирующее на структуру дорог.
* *Вероятность по весу сегмента, а не клетки.* Иначе БПЛА «застревает» на локально
  ярком пикселе; сегмент до следующей развилки отражает реальный выбор «куда свернуть».
* *4 режима + смещение к цели.* Баланс между реализмом (обычно идут по руслу) и
  полнотой выборки (нужны и редкие пути для честной расстановки датчиков) — без них
  выборка вырождается в один коридор.
* *Кинематика (R_min, интервал смены курса).* Делает линии физичными и мешает
  «пиксельной» извилистости; параметры вынесены в интерфейс для калибровки.

**Что и как РЕАЛИЗОВАНО (`model/threat_routes.py::_walk_field`/`sample_one_route`, запуск через
`ThreatModel.iter_step`/`iter_batch`, кнопки Пуск/Шаг/Пакетно).**
Пошаговый стохастический обход построен так (немного иначе, чем в исходном эскизе, —
устойчивее и без «убегания» от цели):

* **Смещение к цели — полем расстояний.** Один раз считаем поле `gt` (Дейкстра от
  ЦЕЛИ по проходимым коридорам) — геометрическое расстояние «отсюда до цели». На каждом
  шаге тяга к цели = `exp((gt[тек] − gt[сосед]) / τ)`: шаг, приближающий к цели,
  экспоненциально вероятнее шага в сторону/назад. Это гарантирует ПРИХОД к цели и
  держит маршрут близко к кратчайшему (важно: тогда он влезает в запас хода), а
  РАЗНООБРАЗИЕ берётся из выбора РАЗНЫХ коридоров, а не из длинных крюков.
* **Выбор развилки по режиму** — множитель `f_режим(W_норм соседа)`:
  `heavy = 0.1+1.6·W`, `light = 0.1+1.6·(1−W)`, `balanced = 0.3+0.8·W`; `mix` —
  случайный из трёх на каждый маршрут. «Пол» у каждого режима не даёт вероятности
  занулиться (не вырождается в один коридор — например, только реки). `W` нормируется
  по p90 (как стоимость).
* **Держание курса.** Пока с последнего доворота пройдено `< threat_turn_interval_km`,
  прямой сосед получает большой множитель, боковой — малый: путь идёт прямыми
  участками с редкими доворотами (не «дрожит»); разворот назад запрещён.
* **Кинематика (R_min).** Готовая ломаная упрощается (RDP) и сглаживается сплайном
  Катмулла–Рома: острые углы сетки → плавные ДУГИ, прямые остаются прямыми —
  приближение манёвра радиусом `R_min = V²/(g·tan φ)`. Допуск упрощения подбирается
  так, чтобы кривая не вышла из коридора (см. «Безопасное сглаживание» ниже).
* **Запас хода — главный фильтр.** Маршрут длиннее `L_max` отбраковывается (строго,
  без допуска). `L_max` авто = `|AB| + 25 %` (но не меньше кратчайшего коридорного пути
  + `THREAT_LMAX_CORRIDOR_FRAC` = 35 %) или задан руками. Число маршрутов —
  `Params.threat_iter_routes` (поле «число итераций», по умолчанию 150).
* **Показ.** Итерационные маршруты рисуются ПО ОДНОМУ (таймер ~22 пути/с) — анимация
  «наматывания веера», как поэтапный показ во вкладке 2.

#### ТРИ НЕЗАВИСИМЫЕ ОСИ повадок БПЛА (три списка в панели итераций)

Это три РАЗНЫХ вопроса, они не дублируют друг друга:

| Список | Параметр | На что отвечает |
|---|---|---|
| **Режим итераций** | `threat_iter_mode` | *Куда* тянется маршрут: к тяжёлым коридорам (реки/дороги) или к «пустошам» |
| **Разброс по карте** | `threat_iter_spread` | *Как далеко вбок* уходит от прямой вход→цель (через какую VIA-точку) |
| **Расход запаса** | `threat_spend` | *Когда* тратится запас хода: виляет сразу или ближе к цели |

Первые две — про геометрию в пространстве, третья — про распределение виляния **во
времени полёта**. Все три действуют на ИТЕРАЦИИ; «возможные маршруты» (§4.4) строятся
веером всех повадок сразу.

* **Режим по весу** `f_режим(W)`: `max` = `0.1+1.6·W`, `medium` = `0.3+0.8·W`,
  `min` = `0.1+1.6·(1−W)`, `mix` — случайный из трёх на каждый маршрут. «Пол» у каждого
  режима не даёт вероятности занулиться (выборка не вырождается в один коридор).
  `W` нормируется по p90. «Мин. вес» специально вытягивает одинокие коридоры (там, где
  только река) — снимает баг «в центре нет пути».
* **Разброс** — через какую VIA-точку идти: `center` (вдоль прямой), `middle`, `edge`
  (дальний обход, заход в цель с любой стороны), `mix`. Боковой разброс отделён от веса,
  поэтому пути покрывают карту в ЛЮБОМ режиме.

#### РАСХОД ЗАПАСА ХОДА (`_spend_tau`) — почему маршруты раньше не доходили

**Проблема (вскрылась только на реальных данных).** Блуждание по 8-связной сетке извилисто
по своей природе: коэффициент извилистости ~1,24 (медиана 103 км при кратчайшем пути
83,5 км). А авто-запас хода даёт всего +35 % (112,7 км). Распределение длин **пересекало**
бюджет: маршрут вилял «вслепую», проедал весь запас и отбраковывался у самой цели, пройдя
113 км из 112,7 доступных. Итог — **96,5 % попыток впустую**, из 250 заказанных маршрутов
строился 41.

**Решение — физичное.** Реальный БПЛА на исходе топлива не петляет. Введём **свободный
запас**: на каждом шаге известно, сколько километров ещё можно потратить на виляние:

    slack = (остаток хода) − (кратчайший путь до цели отсюда)
          = (budget − пройдено) − d_цель(текущая ячейка)

Если `slack < 0` — дойти уже нельзя, маршрут обрывается СРАЗУ (не жжём шаги впустую).
Пока `slack > 0` — он управляет «температурой» выбора соседа τ в тяге к цели
`exp((d[тек] − d[сосед]) / τ)`:

    τ = τ_tight + (τ_free − τ_tight) · by_slack · by_phase
    by_slack = min(1, slack / SLACK_FULL)          # запас есть -> можно вилять
    τ_free = 0.40 (свободно),  τ_tight = 0.05 (жёстко к цели),  SLACK_FULL = 10 км

Малое τ резко выделяет соседа с максимальным приближением к цели — маршрут **выпрямляется**.
Большое τ уравнивает соседей — маршрут свободно выбирает коридоры.

**Профиль** (`by_phase`) решает, КОГДА тратить запас (`frac_done` — доля всего маршрута,
уже пройденная):

| Профиль | `by_phase` | Поведение |
|---|---|---|
| `late` — «виляет, потом прямо» | `1` | Пока запас есть — идёт по коридорам; на исходе выпрямляется и идёт к цели |
| `early` — «прямо, потом виляет» | `frac_done` | Сначала кратчайшим путём, запас тратит ближе к цели |
| `even` — «равномерно» | сверка с планом `0.5 + 3·(frac_done − spent_frac)` | Тратит запас понемногу на всём пути |

Важно: `frac_done` считается по ВСЕМУ маршруту, а не по текущему участку — иначе путь
через VIA дважды «начинал бы сначала» (для этого участки получают `done0_km`/`tail_km`).

**Проверка** (доля «лишних» километров, потраченная в 1-й половине пути):
`late` 66 % · `early` 42 % · `even` 49 % — профили реально различимы.

#### Фильтр VIA по достижимости

Вторая причина отказов: **половина VIA-точек была физически недостижима** — минимальный
путь вход→via→цель через них 123–162 км при запасе 112,7 км. Это не проверялось, и каждая
попытка через такую точку была гарантированным отказом (47 % всех попыток).

Теперь в контексте выборки для каждой VIA хранится `via_minlen = d(вход→via) + d(via→цель)`
(считается один раз по готовым полям Дейкстры). `_pick_via` разыгрывает только те, у кого
`via_minlen ≤ L_max`. Плюс бюджет первого участка = `L_max − d(via→цель)`: на второй
участок гарантированно остаётся ход (иначе первый проедал всё).

**Совокупный эффект (реальные данные):** успех выборки **5 % → 92 %**, маршруты строятся
полным числом (250/250, 150/150) и при этом ВДВОЕ БЫСТРЕЕ — попытки не тратятся впустую.

#### Безопасное сглаживание (`_smooth_safe`)

Расчётная ломаная по ячейкам всегда лежит в коридоре. Но СГЛАЖИВАНИЕ — то, что рисуется
на экране и по чему считаются датчики — срезало углы и уводило линию туда, куда БПЛА не
летит: в плотную застройку и за область залёта (замер: 828 ячеек вне области, 2721 точка
в непроходимом).

Поэтому допуск упрощения (RDP) **подбирается**: пробуем заданный (∝ длине прямого участка),
и пока кривая режет запретное — уменьшаем вдвое (углы срезаются меньше, линия жмётся к
расчётной). В пределе — сглаживание по опорным точкам сетки, оно из коридора не выходит.
Стало **0 нарушений**.

Попутно выяснилось, что прежний допуск приёмки `L_max × 1.15` был мёртвым костылём:
сглаживание маршрут только СПРЯМЛЯЕТ (111 → 103 км), длиннее запаса хода не выходит никто.
Проверка ужесточена до строгой `≤ L_max`.

### 4.6 Датчики по тепловой карте маршрутов + переключение «до/при итерациях» (РЕАЛИЗОВАНО, этап 4)

Идея пользователя реализована (по команде «давай попробуем 4 этап»):
`THREAT_URBAN_IN_WEIGHT=True` (минус городам, реки сквозь город остаются);
`route_density_field()` и `place_sensors()` берут ВЫБОРКУ = итерации, если идут, иначе ВСЕ
возможные пути (строятся, если их нет); 2-я тепловая карта до итераций показывает
плотность всех возможных, при итерациях — выборку пролётов, на сбросе — снова все возможные.
Проверка на демо: минус в весе (wmin=−40), маршруты обходят город (в застройке ~8 % точек —
это реки сквозь город), датчики НЕ на городе (1/12), покрытие 78 % (до итер.) → 91 % (при
итер.) вместо сломанных 22 % по сырому весу. «Обобщённая выборка» для датчиков — вес
`medium` (∝ сумме весов тепловой карты, «наиболее вероятные») + разброс `mix` (распределённо).

**Суть.** Разорвать конфликт «города должны давать МИНУС в вес (маршрут их обходит), но
тогда датчики, максимизируя положительный вес, разбегаются от городов». Решение — датчики
считать НЕ по сырому весу, а по **тепловой карте МАРШРУТОВ** (частота пролёта БПЛА):

* **До итераций.** Чекбокс «маршруты» строит ВСЕ возможные пути А→Б (уже сделано). Из их
  плотности — 2-я тепловая карта «где вообще может лететь БПЛА». Датчики расставляются
  ПО НЕЙ (с правилами A/B, §5) — города там уже холодные (БПЛА их обходит), минус в весе
  датчикам не мешает. На интерфейс выводится число возможных маршрутов (сделано).
* **При запуске итераций.** 2-я карта и датчики ПЕРЕСТРАИВАЮТСЯ под выборку конкретных
  пролётов (уже — при «Пуск/Пакетно»).
* **На сбросе.** Возврат: 2-я карта снова показывает ВСЕ возможные маршруты.

**Оценка идеи: верная и рекомендуется.** Это ровно схема вкладок 1–2 (SAA: датчики по
выборке маршрутов), только источник выборки — реальная карта. Убирает главный конфликт и
делает поведение предсказуемым (до итераций — «потенциал угрозы», при итерациях — «факт»).

**Пути реализации (что менять, оценка сложности).**
1. `THREAT_URBAN_IN_WEIGHT=True` — вернуть минус городам (реки сквозь город остаются). Тривиально.
2. `route_density_field()` — источник: `iter_routes` если идут итерации, иначе `routes`
   (все возможные). 1 строка.
3. `place_sensors()` — если нет выборки итераций, но есть/можно построить «все возможные
   маршруты» — расставлять по НИМ (`_place_by_routes`), иначе как сейчас. Уже написано и
   откачено до команды.
4. Состояние 2-й карты: `pre` (все возможные) ↔ `sample` (итерации). Переключать в
   `on_iter_play` (→sample) и `on_reset`/`iter_reset` (→pre). Мелкая правка контроллера.
5. Число возможных маршрутов — считать по тепловой карте и запасу хода (эвристика:
   растёт с L_max и радиусом смены направления). Сейчас = число реально построенных путей.

**Риск/нюанс.** Построение «всех возможных» — секунды (стохастика + кэш контекста); для
UI держать в фоне (уже так для «маршрутов»/«Пакетно»). Порог «≥3 маршрута» — чтобы не
ставить датчики по пустой выборке.

**Проверка реализации (июль 2026).** Схема подтверждена численно: расстановка по выборке
итераций объективно лучше на своей выборке (ср. кратность 5.61) как расстановки по
«возможным путям» (4.43), так и по сырому весу (3.71). Смена профиля расхода в панели
итераций сдвигает датчики на 3–9 км — модель на выборку реагирует. При этом вскрылись
три дефекта, все исправлены:

| Дефект | Проявление | Исправление |
|---|---|---|
| Датчики не обновлялись ПО ХОДУ итераций | пересчёт был только после ПОСЛЕДНЕЙ итерации; «Шаг» не пересчитывал вовсе — казалось, что датчики не реагируют на выборку | `_maybe_refresh_sensors` в контроллере: пересчёт каждые ~10 % от T (не чаще 1 раза в 5 маршрутов) |
| 4 из 12 датчиков не ловили ни одного пролёта | при насыщении обоих ключей `argmax` по нулевому `score` брал первый кандидат подряд — угол карты | третичный ключ в `greedy` (§5.2) |
| Ставилось 9 из 12 заказанных | жёсткий разнос 1.6·R блокировал оставшиеся полезные позиции | разнос ослабляется 1.6·R → до `threat_min_sep_frac`·R, пока не наберётся N (параметр ожил как нижняя граница) |

Итог на реальных данных: 12/12 датчиков, все ловят пролёты, средняя кратность 4.6 → 8.0.
«Покрытый вес» при этом снизился 66 % → 58 % — это НЕ регресс: датчики теперь идут по
коридорам пролёта, а не по сырому весу карты; целевая метрика — засечка пролётов, она и
выводится в заголовке и в блоке показателей.

**Нюанс насыщения.** При текущих параметрах (R=12 км, k=3) уже 5 датчиков дают 100 %
засечки с кратностью ≥ k — задача «лёгкая», и метрика ≥k не различает варианты
расстановки. Чтобы сравнивать наборы, смотрите СРЕДНЮЮ КРАТНОСТЬ либо засечку при
уменьшенном радиусе (при 0.6·R разница видна: 57 % против 100 %).

## 5. Расстановка датчиков (все вкладки)

### 5.1 Метрики обнаружения

Для маршрута γ и набора датчиков S:

* кратность `n(S,γ)` — число РАЗНЫХ датчиков, засёкших γ (вход в радиус R хоть раз);
* сегментное покрытие `m` — доля из L_seg равных участков пути, покрытых хотя бы
  одним датчиком (равномерность);
* полезность одного маршрута: `φ(S,γ) = α₁·min(n,k)/k + α₂·m`, веса (α₁,α₂) — режим.

### 5.2 Жадный субмодулярный выбор (вкладки 1–2)

Целевая функция — выборочное среднее `F_t(S) = (1/t)·Σ φ(S, γ_i)` по накопленным
маршрутам — монотонна и субмодулярна ⇒ жадный алгоритм даёт гарантию

    F(S_greedy) ≥ (1 − 1/e) · F(S_opt) ≈ 0.632 · оптимум   (Nemhauser–Wolsey–Fisher)

Кандидаты — сетка внутри эллипса/коридора; при насыщении основного критерия
включается вторичный (распределение по плотности). Датчики не в зоне старта и не за
целью B (якорь + развязка ~1.35·R).

**Три ключа выбора (лексикографика).** Основной — прирост `φ`; при его насыщении —
вторичный (прирост покрытой доли маршрута); когда насыщены ОБА — **третичный**: сколько
маршрутов кандидат вообще накрывает (резерв кратности). Третичный ключ обязателен: без
него на насыщенной задаче `score` обнулялся у всех кандидатов и `argmax` брал ПЕРВЫЙ по
порядку массива — датчики уходили в угол карты. Замер на реальных данных вкладки 3:
4 из 12 датчиков не ловили ни одного пролёта. Если и третичный ключ нулевой (полезных
позиций не осталось) — расстановка прекращается, датчики в пустоту не ставятся.

### 5.3 Weighted maximum coverage (вкладка 3)

Тот же жадный алгоритм, но единица покрытия — не точка маршрута, а КЛЕТКА весовой
карты. Датчик в позиции c «покрывает» клетки в радиусе R; ценность набора —
суммарный ПОКРЫТЫЙ ВЕС с насыщением по кратности k:

    value(S) = Σ_клеток W⁺·min(cnt,k)/k  (аттракторы),  − штраф за покрытие репеллеров

Кандидаты — регулярная сетка с шагом `threat_cand_step_km` МИНУС вода (датчик не на
воде). `min_sep` (доля R) убирает слишком близких кандидатов — распределённость.
«Без итераций» = T=1: весь costmap подаётся как одна статичная псевдотраектория.

### 5.4 Что такое «кандидатные позиции» (вкладка 3)

Это НЕ места, куда точно встанут датчики, а **множество допустимых мест-претендентов**,
из которых жадный алгоритм ВЫБИРАЕТ N лучших. Строятся так:

1. регулярная сетка узлов с шагом `threat_cand_step_km` км по всему участку
   (`xs = kx0+step/2, kx0+step·1.5, …`; так же по y);
2. из неё удаляются узлы на ВОДЕ (и в буфере) — на воду датчик не ставим;
3. оставшиеся узлы и есть кандидаты (чекбокс «кандидатные позиции» их показывает).

Меньше шаг — больше кандидатов (точнее размещение, дольше счёт), больше шаг — грубее
и быстрее. Итог: датчики стоят только в узлах этой сетки, вне воды.

## 7. Сводка формул

| Величина | Формула |
|---|---|
| Эллипс достижимости | `|PA|+|PB| ≤ L_max`; `a=L_max/2, c=|AB|/2, b=√(a²−c²)` |
| Радиус разворота | `R_min = V²/(g·tan φ)` |
| Вклад линии в ячейку | `вес_слоя × (длина_пересечения / размер_ячейки)` |
| Вес ячейки | `Σ вкладов + funnel·(слоёв−1) + мост − город` |
| Стоимость маршрута | `base_cost + weight_scale·(1 − W⁺/maxW⁺) + urban_cost·[город]` |
| Плотность застройки | `box_mean(built, окно) ≥ порог ⇒ исключить` |
| Полезность (датчики) | `φ = α₁·min(n,k)/k + α₂·m` |
| Гарантия жадного | `F(S) ≥ (1−1/e)·F(S_opt)` |
| Будущая рандом-развилка | `P(сосед) ∝ W(сосед)^γ` (γ большой — приоритет; малый — разброс) |
