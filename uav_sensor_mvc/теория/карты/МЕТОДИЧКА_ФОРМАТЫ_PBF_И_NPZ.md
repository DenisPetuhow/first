## 1. Коротко: исходник и рабочий формат

**`.osm.pbf` — исходник. `.npz` — рабочий формат.** Программа в обычной жизни читает
только второй.

| | `.osm.pbf` | `.npz` |
|---|---|---|
| откуда берётся | **скачивается снаружи** (Geofabrik и т. п.) | **делаем сами** из `.osm.pbf` |
| что внутри | весь OSM района: узлы, пути, отношения, **все теги всех объектов** | только нужные слои, **уже в километрах** (13 804 массива) |
| чем читается | `pyrosm` + `geopandas` + `shapely` (тяжёлый геостек) | **один `numpy`** |
| **размер** (область 291 × 250 км) | **17.1 МБ** | **7.2 МБ** |
| **время чтения** | **4.3 с** | **0.03 с** — в 140 раз быстрее |
| как часто читается | **один раз**, при подготовке | при каждом запуске программы |

⚠️ **Главный выигрыш — не в размере, а во времени и в зависимостях.** По объёму разница
всего вдвое, а по скорости — **в 140 раз**; и главное, `.npz` читается там, где геостека
нет вовсе. Замеры — [УСТАНОВКА_БИБЛИОТЕК §1](../сборка/УСТАНОВКА_БИБЛИОТЕК.md).

⚠️ **Главная тонкость, из-за которой чаще всего путаются: `.npz` в проекте ДВА РАЗНЫХ.**
Расширение одно, а содержимое совершенно разное:

| Файл | Что внутри | Кто пишет | Кто читает |
|---|---|---|---|
| `threat_layers_<участок>.npz` | **ВЕКТОРНЫЕ СЛОИ**: реки, дороги, ЛЭП, застройка, метки НП — ломаные в километрах | `tools/build_threat_grid.py` | `load_layers` :: **1248** |
| `<что-то>.npz` весовой сетки | **РАСТР**: массив весов `weight`, маска воды, счётчик слоёв, рамка, шаг ячейки | `ThreatGrid.save_npz` :: **1120** | `load_npz` :: **1128** |

Первый — «что нарисовано на местности». Второй — «во что это превратилось после
наложения на сетку 500 м». Из первого получается второй, обратно — нет.

## 2. `.osm.pbf` — что это и почему его нельзя читать каждый раз

**PBF** = Protocol Buffers, двоичный формат сжатого обмена OpenStreetMap. В нём лежит
**всё подряд** по району: каждая точка, каждая линия, каждый тег — включая скамейки,
урны и часы работы магазинов.

**Почему не читаем его при каждом запуске** — три причины, и все три весомые:

1. **Объём.** Нужных нам объектов — доли процента от файла. Остальное разбирается впустую;
2. **Скорость.** Замер: **4.3 с против 0.03 с** у `.npz` — разница в 140 раз, и она
   ложится на каждый запуск;
3. ⚠️ **Библиотеки.** `pyrosm` и `geopandas` — тяжёлый геостек, который на машине
   заказчика **не нужен вовсе**. Это не мелочь: ровно на этом программа однажды и
   сломалась, когда чтение `.osm.pbf` стало путём по умолчанию (задача 8.2 — свой район
   моделирования; исправлено, правило [ОГРАНИЧЕНИЯ 5.1м](../правила/ОГРАНИЧЕНИЯ.md)).

### 2.1. Как он читается — `layers_from_osm`

`model/threat_grid.py` :: `layers_from_osm` :: **1388**. Порядок работы:

1. `from pyrosm import OSM` — ⚠️ импорт **внутри функции**, а не в шапке модуля. Так
   модель остаётся загружаемой там, где `pyrosm` не установлен: падение произойдёт только
   при попытке прочитать `.osm.pbf`, и с внятным сообщением «нужен pyrosm/geopandas»;
2. объекты фильтруются по тегам — таблица `OSM_LAYER_FILTERS` :: **1327**:

   | слой | фильтр по тегам OSM |
   |---|---|
   | `river` | `waterway = river, canal` |
   | `stream` | `waterway = stream` |
   | `ditch` ⭐ | `waterway = ditch, drain` |
   | `road_major` | `highway = motorway, trunk, primary, secondary` |
   | `road_local` | `highway = tertiary, unclassified, residential, road` |
   | `track` ⭐ | `highway = track, service` · `abandoned:highway = track` |
   | `cutline` ⭐ | `man_made = cutline` |
   | `railway` | `railway = rail, narrow_gauge` |
   | `railway_old` ⭐ | `railway = abandoned, disused` |
   | `power` | `power = line, minor_line` |
   | `pipeline` | `man_made = pipeline` |
   | `tree_row` | `natural = tree_row` |
   | `bridge` | `bridge = yes, viaduct` |
   | `built_up` | `landuse = residential, industrial` |

   ⭐ — 13.09.2026. ⚠️ Если у слоя несколько КЛЮЧЕЙ (`track`: `highway` и
   `abandoned:highway`), `pyrosm` объединяет их через «или»: замер — 12 163 объекта против
   8 702 у одного `highway=track`, прибавка ровно на подъезды и заброшенные.

   отдельно — населённые пункты: `OSM_PLACE_FILTER` = `place = city, town, village,
   hamlet, suburb, borough`. Они в вес **не входят**: по ним классифицируются пятна
   застройки (город запрещён, деревня обходится по краю);
3. координаты `(lon, lat)` переводятся в **километры** от юго-западного угла участка —
   `_ll` :: **1819** → `lonlat_to_km`;
4. результат — словарь `имя_слоя → список массивов (N, 2)`.

⚠️ **Один и тот же код читает OSM и из скрипта, и из окна «Выбрать цифровые карты»** —
единый источник правды. Дублировать разбор тегов в двух местах нельзя: разойдутся молча.

### 2.2. Две ловушки самого `pyrosm`

* ⚠️ **теги приходят ОДНОЙ JSON-строкой** в колонке `tags`, отдельной колонки `name` нет
  — название пункта достаётся разбором этой строки (`threat_grid.py` :: **1756**);
* ⚠️ **линия приходит не цельной**, а `MultiLineString` из двухточечных кусков
  (:: **1775**) — их приходится сшивать, иначе река распадается на сотни обрубков.

## 3. `.npz` слоёв — рабочий формат

`.npz` — это **zip-архив массивов numpy** со стандартной функцией `np.savez_compressed`.
Никакого своего формата мы не придумывали: читается одной строкой `np.load(path)`.

### 3.1. Как устроен внутри

```python
def _load_layers_npz(path):
    """Формат: ключи '<layer>__<i>' -> массив (N,2) в км; наличие ключа задаёт слой."""
    d = np.load(path, allow_pickle=True)
    out = {}
    for key in d.files:
        if "__" not in key:
            continue
        name, _idx = key.rsplit("__", 1)
        out.setdefault(name, []).append(d[key])
    return out
```

Ключ строится по правилу **«имя слоя + два подчёркивания + номер объекта»**: для слоя рек
это будут ключи с номерами 0, 1, 2… по числу ломаных, для дорог — свои. ⚠️ Таких имён нет
в исходниках: они собираются на лету при записи, искать их грепом по коду бесполезно.

Почему так: `.npz` умеет хранить только плоский набор именованных
массивов, вложенности в нём нет. Имя с номером — самый дешёвый способ разложить список
ломаных по слоям, не заводя своего формата и не сериализуя питоновские объекты.

⚠️ **`rsplit("__", 1)`, а не `split`** — имя слоя само может содержать подчёркивания
(`road_major`, `place_pts`). Разрез справа и ровно один раз отделяет номер, не трогая имя.

⚠️ **Наличие ключа задаёт слой.** Пустого слоя в файле просто нет — не нужно хранить
пустые массивы и не нужен отдельный список слоёв.

### 3.1а. ⚠️ Упакованный формат — для больших областей (14.09.2026)

Массив на каждую линию годился, пока линий были десятки тысяч. На области Marshut их
**2.6 млн**: файл 741 МБ, и модель читала его **десятки минут** — каждый массив в `.npz` это
отдельный файл внутри zip-архива, и открывается он отдельно. Программа при открытии
области просто стояла.

**Упакованный формат** — на слой два массива:

| Ключ | Что внутри |
|---|---|
| `<слой>@xy` | все точки всех линий слоя подряд, `(N_точек, 2)` или `(N_точек, 3)` |
| `<слой>@off` | где начинается каждая линия: `N_линий + 1` чисел, последнее — конец |

```python
xy, off = d[keys["xy"]], d[keys["off"]]
out.setdefault(name, []).extend(np.split(xy, off[1:-1]))   # линии — виды на один буфер, без копий
```

Пишет его `threat_grid.packed_npz_arrays`, читает тот же `_load_layers_npz` — **оба формата**,
отличает по символу `@` в ключе. Слой строк (имена пунктов) пишется по-старому: строки в
один числовой буфер не упаковать. Итог `tools/pack_area.py` — только упакованный; прежние
файлы (`arh`, Донецк) не переписывались и читаются как раньше.

**Пример.** Области Marshut: 2.6 млн массивов → по два на слой, около 35 ключей на весь файл.
`model/map_fit.py` :: `layers_for_fit` читал ключи сам, по префиксу, и упакованный файл не
увидел бы — переведён на общий загрузчик.

### 3.2. Служебные слои населённых пунктов

Кроме обычных ломаных, в файле лежат три особых слоя:

| Слой | Что в нём |
|---|---|
| `place_pts` | метки-точки НП: `(N, 3)` — `x_км`, `y_км`, **код типа** |
| `place_poly` | контуры НП: массивы `(M, 3)` — то же плюс код |
| `place_names` | **строки** названий, `i`-я отвечает `i`-й точке `place_pts` |

⚠️ `place_names` — массив строк, поэтому `np.load` вызывается с `allow_pickle=True`.
Названия нужны **только для подписей** на карте и на расчёт не влияют: подписи подложки
впечатаны в тайлы кеглем ~10 px и при обзоре всего участка нечитаемы.

⚠️ **У 2/3 пунктов в OSM границ нет вовсе** — только точка. Поэтому тип берётся с метки, а
границы даёт связное пятно застройки вокруг неё.

### 3.3. Второй `.npz` — растр весовой сетки

Совсем другое содержимое (`save_npz` :: **1120**):

```python
np.savez_compressed(path, weight=self.weight, water=self._water,
                    attr_count=self._attr_count,
                    bbox=np.array([self.kx0, self.kx1, self.ky0, self.ky1]),
                    cell=np.array([self.h]))
```

Здесь уже нет ни рек, ни дорог — только **готовая сетка**: вес каждой ячейки, маска воды,
сколько слоёв её задело, рамка в километрах и шаг. Это снимок результата, а не исходные
данные: по нему нельзя перестроить слои, зато можно мгновенно восстановить карту.

## 4. Откуда программа берёт слои — приоритет источников

`load_layers` :: **1248**. Порядок строгий:

| № | Источник | Когда срабатывает |
|---|---|---|
| 1 | **явный путь** из окна «Выбрать цифровые карты» | пользователь сам указал файл: `.npz` читается как слои, `.osm.pbf` разбирается на месте |
| 2 | **кэш участка** `geo_cache/<участок>/threat_layers_<участок>.npz` | путь не задан — берётся файл активного участка (`layers_cache_path` :: **1319**) |
| 3 | ⚠️ **синтетическая СХЕМА** | файла нет: рисуется демонстрационная схема, офлайн, без внешних данных |

⚠️ **Третий пункт молчаливый, и это главная ловушка всего механизма.** Если файла слоёв
нет, программа **не падает** — она рисует схему. На экране появляется что-то
картоподобное, и это легко принять за «данные загрузились». Отличить можно по подписи
источника: `СХЕМА (демо, офлайн)` против `OSM (офлайн-кэш: …)`.

⚠️ **У каждого участка СВОЙ файл слоёв** (`config.THREAT_AREAS[...]["layers"]`). Иначе
кэш прежнего района подменял бы новый — а выглядело бы это как «карта не обновилась».

## 5. Как собрать `.npz` самому — по шагам

### 5.1. Что понадобится

```bash
pip install pyrosm geopandas shapely pyproj
```

⚠️ Это нужно **только на машине, где готовят данные**. На машине, где программа просто
работает, геостек не нужен: там читается готовый `.npz` одним `numpy`. Если интернета нет
— колёса лежат в `offline_packages/`, см. [УСТАНОВКА_БИБЛИОТЕК](../сборка/УСТАНОВКА_БИБЛИОТЕК.md)
(там же ловушка с `cykhash`).

### 5.2. Шаг 1 — скачать экстракт района

Где брать `.osm.pbf` и как обрезать по рамке — [МЕТОДИЧКА_ЗАГРУЗКА_КАРТ](МЕТОДИЧКА_ЗАГРУЗКА_КАРТ.md).
Файл кладётся в папку участка: `geo_cache/<участок>/`.

⚠️ **Рамка участка в `config` должна быть УЖЕ данных.** Экстракт обрезан по своей рамке,
и если участок совпадает с ней край в край, у границы слои обрываются. Отступ задаётся
`THREAT_AREA_PAD_KM` = 2 км.

### 5.3. Шаг 2 — собрать слои

```bash
python tools/build_threat_grid.py                        # исходник и приёмник из участка
python tools/build_threat_grid.py geo_cache/APX.osm.pbf  # явный исходник
python tools/build_threat_grid.py <исходник> <имя.npz>   # и явный приёмник
python tools/build_threat_grid.py --area plesetsk_wide   # собрать ДРУГОЙ участок
```

⚠️ **`--area` существует ради конкретной ловушки:** область часто заводят заранее, и её
данные готовят ДО переключения `THREAT_AREA`. Без этого ключа пришлось бы менять активный
участок туда-обратно — и легко забыть вернуть.

Скрипт — тонкая обёртка: прочитать через `layers_from_osm` → сохранить. Вся логика чтения
живёт в модели, чтобы окно «Выбрать цифровые карты» и командная строка работали одинаково.

### 5.3а. Если экстракт скачан КУСКАМИ — `tools/pack_area.py`

Большую область скачивают полосами, а программа читает ОДИН `.npz`. Склейка — отдельный
скрипт, потому что простое объединение ломает вес:

```bash
python tools/pack_area.py geo_cache/<область> --only layers           # все .pbf → один .npz
python tools/pack_area.py geo_cache/<область> --only layers --pbf A.pbf  # один кусок (параллельно)
```

* каждый `.pbf` разбирается тем же `layers_from_osm` в км-фрейме ОБЛАСТИ (якорь — её
  юго-западный угол), результат — `_части/<файл>.npz`; свежая часть не пересобирается;
* части сливаются, и **одинаковые ломаные с точностью 1 м выбрасываются** — отпечаток
  округлённых координат (`_key`). Пункты сравниваются по координатам, типу и имени;
* имя итога — ключ `слои` в `область.txt`.

⚠️ **Почему без очистки нельзя.** Экстракт полосы включает дорогу, пересекающую её
границу, целиком. Та же дорога есть и в соседней полосе. Её длина вошла бы в вес
дважды, и ровно по линии стыка встала бы ложная полоса коридоров.

**Пример.** Область Marshut: полосы 51–55°, 55–59°, 59–63° (320 + 481 + 105 МБ). Малая
полоса разобрана за 4.2 мин: лесных дорог 94 122 линии, канав 50 756, местных дорог 41 623.

⚠️ **Разбор долгий и растёт быстрее размера файла.** Полоса 320 МБ с Москвой — **46.1 мин**
при 4.2 мин у 105 МБ: файл ×3, время ×11. Файл читается один раз, но на каждый из 15
слоёв `pyrosm` заново проходит все разобранные записи и собирает геометрии, а пересчёт в
километры идёт циклом Python. Полосы — параллельными процессами (`--pbf`); память — до
~11 ГБ на процесс. ⚠️ Деление слоёв одной полосы по ядрам (`--jobs`) замерено и **не
ускоряет** (4.2 → 5.1 мин): основное время — чтение файла. Как устроено и что ускорит —
[код/УПАКОВКА_ОБЛАСТИ §6.8](../код/УПАКОВКА_ОБЛАСТИ.md). Как ускорить, в том числе библиотекой
`osmium`, — [план 10, задача 10.13](../планы/10_ПЛАН_ПРОЕКЦИЯ_И_ОСТАТКИ.md).

### 5.4. Шаг 3 — проверить

Запустить программу: в строке источника должно быть `OSM (офлайн-кэш: …)`, а не
`СХЕМА (демо, офлайн)`. Либо `UAV_SELFTEST=1 python main_qt.py` — самопроверка печатает,
какие файлы участка найдены и строится ли карта.

## 6. Частые вопросы

**«Почему не хранить всё в одном `.osm.pbf` и читать по мере надобности?»** Потому что
разбор стоит минуты и требует геостека. Раздельное хранение — это ровно размен «один раз
долго» против «каждый запуск быстро».

**«Можно ли из `.npz` получить обратно `.osm.pbf`?»** Нет, и не нужно. В `.npz` попадает
доля процента исходных данных: только те слои и только те теги, что участвуют в расчёте.
Понадобилось новое свойство объектов — пересобрать из исходника.

**«Программа не видит карту, хотя файл на месте.»** Проверить три вещи по порядку:
имя файла совпадает с ключом `слои` в `область.txt` (у области без файла — с
`THREAT_AREAS[<участок>]["layers"]`) · файл лежит в папке **своей** области · в программе
открыта та область, чьи данные готовили (подпись в «Исходные данные»). ⚠️ Промежуточная
часть `<кусок>.pbf.npz` из `pack_area` — НЕ файл слоёв: она покрывает одну полосу, и
программа её не читает.

**«Нужен ли `pyrosm` заказчику?»** Нет. Только тому, кто **готовит** данные участка.
