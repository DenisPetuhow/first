## 0. Три вида данных — важно не путать

Слово «карта» в проекте означает три РАЗНЫЕ вещи (с 03.09.2026 — четыре, добавилась своя
карта картинкой, см. конец раздела). Ключевое различие — **вектор против растра**:

* **ВЕКТОР** — это список объектов с координатами: «река идёт через точки (38.4, 49.0),
  (38.5, 48.9)…», «дорога М-30 идёт так-то», «контур села — такой-то многоугольник».
  Здесь можно спросить «что это за объект и какой он длины». Формат — `.osm.pbf`.
* **РАСТР** — это таблица чисел по клеткам, как пиксели картинки: «в клетке 500×500 м
  значение 217». Спросить «что это за объект» нельзя — объектов там нет, только
  значения. Форматы — `.png` (картинка), `.tif` (числа).

| Что | Вид | Файл в проекте | Скачивать? | Участвует в расчёте? |
|---|---|---|---|---|
| **Подложка-фон** (вид местности под картой) | растр (картинки) | `tile_cache/` — 13 273 тайла, 210 МБ, ⚠️ **общий на все участки** (см. ниже) | само качается из интернета | **нет**, только оформление |
| **Цифровые слои** (реки, дороги, ЛЭП, застройка, НП) | **вектор** | `geo_cache/plesetsk/ARX_1.osm.pbf` (1.8 МБ) — активный участок; рядом лежат прежние `APX.osm.pbf` (1.4 МБ) и `severodonetsk.osm.pbf` (23 МБ) | **да, вручную один раз на участок** | **да**, это основа весов |
| **Карта высот** (рельеф) | растр (числа-высоты) | `geo_cache/plesetsk/ARX_1_hh.tif` — активный участок (высоты 27.9…203.7 м); у `severodonetsk` свой `dem.tif` | **да, вручную один раз на участок** | да, по кнопке «Добавить рельеф» (§4.1) |
| **Своя карта картинкой** (с 03.09.2026) | растр (картинка) | `geo_cache/карты_картинки/*.png, *.jpg` | приносит заказчик | **нет**, только показ поверх слоёв |

⚠️ **Все три вещи — свойства УЧАСТКА, а не программы.** Участки перечислены в
`config.THREAT_AREAS`, активный выбирается строкой `THREAT_AREA`; при переключении
меняются сразу границы, файл слоёв, файл рельефа. Подложка общая по расположению
тайлов, но кэш заполнен только для того района, который качали.

### Раскладка `geo_cache/`: у каждого участка своя папка

```
geo_cache/
├── plesetsk/                    ← активный участок (THREAT_AREAS["plesetsk"]["dir"])
│   ├── ARX_1.osm.pbf            исходный экстракт OSM          ["source"]
│   ├── threat_layers_ARX_1.npz  разобранные слои (кэш)         ["layers"]
│   ├── ARX_1_hh.tif             рельеф                         ["dem"] = "ARX_1_hh"
│   ├── APX.osm.pbf              прежний экстракт (уже участок)
│   ├── threat_layers_APX.npz    его слои
│   └── ARX_hh.tif               его рельеф
└── severodonetsk/               ← прежний участок, рабочий
    ├── severodonetsk.osm.pbf
    ├── threat_layers.npz
    ├── dem.tif
    └── архив/                   старые версии слоёв (не удаляем: по ним сняты замеры)
```

**Почему по папкам.** Пока участок был один, всё лежало в корне `geo_cache/`. С двумя
участками стало невозможно понять, чей это `dem.tif` и какой `.npz` к какому району —
а подстановка чужого рельефа НЕ ВИДНА: файл читается, ошибок нет, просто описывает
другую местность.

**Корень остаётся запасным местом поиска** (`area_file`): файл, положенный прямо в
`geo_cache/`, по-прежнему находится, если в папке участка его нет. Так продолжают
работать старые раскладки и `.hgt`-тайлы, брошенные «куда попало».

**Куда класть новый файл:** в папку своего участка. Имя без расширения прописывается
в записи участка — `dem` для рельефа, `source` и `layers` для карты.

Отдельно есть файл слоёв участка (`THREAT_AREAS[...]["layers"]`: для активного —
`geo_cache/plesetsk/threat_layers_ARX_1.npz`, для `severodonetsk` — `threat_layers.npz`, 8.7 МБ). Это
**не** скачанный файл, а выжимка: программа один раз прочитала тяжёлый `.osm.pbf`,
взяла оттуда только нужные слои, перевела координаты в километры, обрезала по участку
и сохранила. Собирается командой `python tools/build_threat_grid.py` и нужна, чтобы не
парсить исходник при каждом запуске (чтение выжимки — секунда).

### Правило шире файлов: по папкам участка делятся ВСЕ данные, включая тайлы ✅

Правило звучит так: **всё, что относится к одному участку, лежит в одной папке — чтобы
участок переносился целиком.** Вектор и рельеф так лежали давно; с 03.09.2026 так
качается и подложка.

```
tile_cache/
├── plesetsk/                    ← НОВОЕ: сначала участок, потом поставщик
│   ├── osm/{z}/{x}/{y}.png          всё, что качается с 03.09.2026
│   └── topo/{z}/{x}/{y}.png
├── osm/{z}/{x}/{y}.png          ← СТАРОЕ: 9 915 тайлов, лежат как лежали
├── osm_hot/{z}/{x}/{y}.png          2 742      всего 13 273 файла, 210 МБ;
├── topo/{z}/{x}/{y}.png               468      участки в них перемешаны, но
└── cyclosm/{z}/{x}/{y}.png            148      это ЗАПАСНОЕ место поиска
```

⚠️ **Старое НЕ перекладываем — решение заказчика 03.09.2026.** Разбирать 210 МБ по
рамкам, дублируя краевые тайлы, ради одного лишь порядка невыгодно: весь выигрыш даёт
уже то, что **всё новое ложится правильно**. Старая раскладка остаётся рабочим запасным
местом поиска — ровно как корень `geo_cache/` для файлов, брошенных мимо папки участка
(`area_file`).

**Как это устроено в коде** (`view_qt/geomap.py`):

| Что | Как |
|---|---|
| путь тайла | `tile_cache_path(layer, z, x, y, ext, area=…)` — `area` пустой даёт прежний путь |
| поиск | `find_cached_tile(…, area=…)` смотрит **два места**: папку участка, затем общий корень |
| запись | `fetch_tile_bytes(…, area=…)` кладёт скачанное в папку участка |
| кто задаёт участок | вкладка 3 — `_init_basemap(tile_area=THREAT_AREA_DIR)`; скрипт — ключ `--tile-area` (по умолчанию поле `dir` участка) |
| ⚠️ почему аргументом, а не импортом | `geomap.py` намеренно не зависит от `config` (только stdlib + numpy), **и у вкладок разные районы**: вкладка 2 работает по Курску. Глобальный участок заставил бы её искать курские тайлы в папке Плесецка |

Две мели, на которые наткнулись при реализации:

* **кэш тайлов в памяти** (`_TILE_MEM`) ключевался по `(слой, z, x, y)`. На общих зумах
  у разных участков эти числа совпадают — вкладка получила бы чужую картинку из памяти;
  теперь участок входит в ключ;
* **`discover_local_layers`** считал слоем любую папку в корне кэша — и принял бы за слой
  папку участка. Теперь различает: у слоя первым уровнем идут ЗУМЫ (числа), у участка —
  имена слоёв (буквы).

### Четвёртый вид: своя карта КАРТИНКОЙ (кнопка «Добавить карту (картинкой)…»)

Заказчик приносит готовую карту растром — скан топокарты, экспорт из другой программы,
снимок. Кнопка на панели вкладки 3 открывает окно, где задают файл и **координаты
углов**; папка выбора по умолчанию — `geo_cache/карты_картинки/`.

| Свойство | Как сделано |
|---|---|
| привязка | углы (град.) → километры **тем же** преобразованием, что и все слои → `ImageItem.setRect`. Проверено: картинка, привязанная к рамке участка, ложится в те же км с расхождением **0.0 мм** |
| порядок наложения | Z = **−19**: сразу над тайлами (−20) и **под всем остальным** — рельефом (−9), весами (−8), водой (−7), застройкой (−5.5), векторными слоями (−5…−3), зонами (0.4), маршрутами (1…5), датчиками. Картинка заменяет ФОН, поверх неё ложится вся работа |
| ⚠️ чему научила первая версия | слой стоял на Z = −1 — «поверх векторных слоёв», как звучало первое задание. На карте остались только датчики и маршруты, а свои слои и весовая карта пропали под картинкой (снимок заказчика 04.09.2026). Формулировка «поверх» означала «вместо подложки», а не «выше данных» |
| зум и перемещение | обычные: картинка живёт в тех же километрах и ездит вместе с картой. Пределы вида под неё **не подгоняются** — попытка сжать район до её рамки ломала привычное поведение зума |
| координаты из имени файла | `map_39.8794_62.5901_41.7516_63.0869.png` — четыре числа подставятся сами |
| большие сканы | прореживаются по длинной стороне до **4000 px** (9000×3000 → 4000×1333): RGBA-скан 10 000×10 000 занял бы 400 МБ |
| режим «только картинка» | гасит тайлы и сжимает район показа до её края (флаг `_basemap_off` проверяется в `_refresh_basemap`, иначе тайлы вернулись бы при первом движении мыши) |

⚠️ **Картинка НЕ участвует в расчёте.** Веса, маршруты и датчики по-прежнему считаются по
векторным слоям и рельефу. Это подложка для глаз, а не источник геометрии.

**Как проверить, что координаты заданы верно.** Включить свои подписи населённых пунктов
и посмотреть, совпали ли они с подписями на картинке. Проверка 04.09.2026 на карте района
Плесецка (997×625 px, рамка `39.87 62.48 42.15 63.14`): подписи «Мирный», «Плесецк»,
«Савинский» легли точно на `MIRNY`, `PLESETSK`, `SAVINSKIY`. Это же подтверждает, что и
векторные слои (дороги, реки) лягут по своим местам — привязка у них общая.

⚠️ **Привязка только прямоугольная** — по параллелям и меридианам. Если у карты есть
поворот (снимок под углом, скан с рамкой), внутри останется сдвиг той же природы, что
расхождение проекций ([план 8 §0.4](../планы/8_ПЛАН_КАРТА_И_ИНТЕРФЕЙС.md)): для листа
1:50 000 (≈20 км) он мал, для листа 1:1 000 000 — километры.

**Почему сейчас карта выглядит «странно» (не все дороги/объекты).** Пока реальные
векторные слои не скачаны, вкладка рисует **демо-СХЕМУ** — несколько условных
прямых линий (русло + пара дорог/ЛЭП), чтобы показать саму механику. Это не баг:
в панели «источник данных» так и написано `СХЕМА (демо, офлайн)`. Как только
подключите реальные данные (ниже) — появятся настоящие дороги/реки/объекты, и
источник сменится на `OSM …`.

## 1. Быстрый путь (рекомендуется): BBBike Extract → .osm.pbf

Один раз выгружаем небольшой кусок OSM ровно по нашему прямоугольнику.

**Шаг 1. Открыть BBBike Extract.**
🔗 https://extract.bbbike.org/

**Шаг 2. Задать прямоугольник участка.** Ввести координаты bbox активного участка
(`config.THREAT_AREAS[config.THREAT_AREA]["bbox"]`, оно же `THREAT_BBOX_LONLAT`).
Участков в реестре несколько — брать координаты того, который собираете:

| Участок | Ю-З угол (lon, lat) | С-В угол (lon, lat) |
|---|---|---|
| **`plesetsk`** — Плесецк — Мирный (активный) | **40.0842**, **62.5717** | **41.5959**, **63.1080** |
| `severodonetsk` — Северодонецк → Луганск | 38.375, 48.335 | 39.654, 49.016 |

На BBBike это поля *Left/Bottom/Right/Top* соответственно: для активного участка
Left=40.0842, Bottom=62.5717, Right=41.5959, Top=63.1080. Можно и просто обвести
прямоугольник мышью по этим ориентирам (северо-запад — верх-лево, юго-восток —
низ-право).

**Шаг 3. Формат — Protocolbuffer (PBF).** В списке *Format* выбрать
`Protocolbuffer (PBF)` → это даст файл `.osm.pbf` (компактный, читается быстрее
всего). Указать e-mail, нажать *extract*. Через несколько минут придёт ссылка —
скачать архив, внутри `planet_*.osm.pbf`.

**Шаг 4. Положить файл в проект.** Создать папку `geo_cache/` внутри
`uav_sensor_mvc/` и положить туда файл, переименовав так, как назван исходник
участка в реестре (`THREAT_AREAS[...]["source"]`) — например
`geo_cache/plesetsk/ARX_1.osm.pbf` для активного участка.
(Путь к кэшу можно переопределить переменной окружения `UAV_GEO_CACHE`.)

**Шаг 5. Установить геостек** (один раз; нужен только для обработки OSM):
```
pip install pyrosm geopandas shapely pyproj rasterio
```
На Windows `geopandas`/`rasterio` тянут библиотеку GDAL, которая через голый `pip`
иногда не собирается. Если ловите ошибки сборки — ставьте через conda:
```
conda install -c conda-forge geopandas rasterio pyrosm
```

**Шаг 6. Собрать слои** (превратить .osm.pbf в готовые слои приложения):
```
python tools/build_threat_grid.py                        # исходник и приёмник — из участка
python tools/build_threat_grid.py geo_cache/plesetsk/ARX_1.osm.pbf  # явный исходник
```
Скрипт отфильтрует объекты по тегам (реки/дороги/ж-д/ЛЭП/трубопроводы/лесополосы/
застройка), переведёт их в км-фрейм участка и сохранит слои в файл этого участка
(`THREAT_AREAS[...]["layers"]`, для активного — `geo_cache/plesetsk/threat_layers_ARX_1.npz`).
**Кэш каждого участка свой**, поэтому сборка нового куска карты не затирает прежний.

**Шаг 7. Подключить в приложении.** Есть два способа:
* автоматически — при следующем «Построить карту» приложение само найдёт файл слоёв
  активного участка; или
* через окно **«Выбрать цифровые карты…»** → *Загрузить файл* → указать
  `.npz` (готовые слои) **или сразу `.osm.pbf`** (приложение обработает его на
  месте тем же кодом, если установлен pyrosm).

Готово: «источник данных» станет `OSM (офлайн-кэш)` / `NPZ: …` / `OSM: …`, и на
карте появятся реальные дороги/реки/объекты.

## 2. Альтернатива: Geofabrik (весь регион) + локальная нарезка

Если планируете часто менять/расширять область или работать совсем без интернета —
удобнее скачать регион целиком и резать локально сколько угодно раз.

**Скачать регион:** 🔗 https://download.geofabrik.de/ — для активного участка это
северо-запад России (`northwestern-fed-district-latest.osm.pbf`), для прежнего —
`ukraine-latest.osm.pbf`.

**Нарезать по bbox** (любым из двух):
* `osmium` (CLI, 🔗 https://osmcode.org/osmium-tool/):
  ```
  osmium extract -b 40.0842,62.5717,41.5959,63.1080 \
        northwestern-fed-district-latest.osm.pbf -o geo_cache/plesetsk/ARX_1.osm.pbf
  ```
* либо сразу отдать весь `ukraine-latest.osm.pbf` нашему скрипту — `pyrosm` сам
  прочитает только заданный `bounding_box` (медленнее, чем предварительная нарезка,
  но проще). Дальше как в разделе 1 с шага 6.

## 3. Быстрый разовый вариант без файлов: Overpass Turbo

Если нужен разовый экспорт нескольких слоёв «здесь и сейчас», без скачивания
регионов:

🔗 https://overpass-turbo.eu/ — вставить запрос по bbox, выполнить, *Export →
GeoJSON*. Пример (река + крупные дороги в нашем bbox):
```
[out:json][timeout:60];
(
  way["waterway"="river"](62.5717,40.0842,63.1080,41.5959);
  way["highway"~"motorway|trunk|primary|secondary"](62.5717,40.0842,63.1080,41.5959);
);
out geom;
```
(Overpass принимает bbox в порядке `south,west,north,east`.) Экспортированный
GeoJSON затем можно конвертировать в наш `.npz`/подать через geopandas — как
расширение (сейчас скрипт заточен под `.osm.pbf`; поддержку GeoJSON легко добавить
в `layers_from_osm`, если понадобится).

Официальный портал OSM (посмотреть объекты/теги глазами): 🔗 https://www.openstreetmap.org/ ·
справочник тегов: 🔗 https://wiki.openstreetmap.org/wiki/Map_features

## 4. Какие теги в какие слои идут

Единый список — в коде (`model.threat_grid.OSM_LAYER_FILTERS`), здесь для справки:

| Слой | OSM-тег(и) |
|---|---|
| Река/канал | `waterway = river / canal` |
| Ручей | `waterway = stream` (отдельный слой: ручьёв в разы больше, вес меньше) |
| Дорога крупная | `highway = motorway / trunk / primary / secondary` |
| Дорога местная | `highway = tertiary / unclassified / residential` |
| Железная дорога | `railway = rail` |
| ЛЭП | `power = line` |
| Трубопровод | `man_made = pipeline` |
| Лесополоса | `natural = tree_row` |
| Застройка | `landuse = residential / industrial` |
| Мост | `bridge = yes / viaduct` — РЕАЛЬНЫЕ объекты OSM |
| Населённые пункты | `place = city / town / village / hamlet / suburb / borough` — служебный слой, в вес не входит (см. §13 МЕТОДИЧКА_КАРТА_УГРОЗ) |

Чтобы добавить/убрать теги — правьте `OSM_LAYER_FILTERS` (один раз, в одном месте:
его используют и скрипт, и окно выбора карт).

> **Тонкость чтения (июль 2026).** `pyrosm` отдаёт way не цельной линией, а
> `MultiLineString` из 2-точечных сегментов: дорога из 40 точек приходила как 39
> обрезков. В кэше копились десятки тысяч «дорог» (10 717 вместо 790), и прореживание
> при отрисовке выкидывало большинство — М-30/Р-66 пропадали вдали от города. Теперь
> `_geom_to_kms` сшивает сегменты `shapely.ops.linemerge`, а `OSM(...,
> complete_relations=True)` добирает члены мультиполигонов за пределами bbox (контуры
> городов на краю участка приходят без дыр). После правки кэш нужно пересобрать:
> `python tools/build_threat_grid.py geo_cache/severodonetsk.osm.pbf`.

> **Обрезка по участку.** `complete_relations=True` тянет объекты далеко за bbox
> (замер: трубопровод от −94 до +94 км при участке ±37 км) — такие линии уходили за
> край карты и зря весили в кэше. Геометрия обрезается по участку **+10 км** запаса
> (`OSM_CLIP_MARGIN_KM`), причём на границе строится ТОЧКА ПЕРЕСЕЧЕНИЯ с рамкой, а не
> берётся ближайшая внешняя вершина (иначе линия вылезала на длину сегмента — до
> 11.7 км вместо 10).

## 4.1 Карта высот (рельеф) — отдельный файл

Полёт по низине вероятнее, чем по линейному ориентиру на холме, поэтому рельеф входит
в весовую карту отдельным слоем. В OSM высот нет — нужен файл DEM.

**Что скачать.** Прямоугольник на участок с запасом.

| Участок | запад | юг | восток | север | состояние |
|---|---|---|---|---|---|
| **`plesetsk_wide`** (активный) | **39.8** | **62.5** | **41.8** | **63.2** | ✅ `geo_cache/plesetsk/ARX_1_hh.tif`, получен 31.08.2026 (высоты 27.9…203.7 м) |
| `plesetsk` (прежний) | 40.0 | 62.5 | 41.7 | 63.2 | ✅ `geo_cache/plesetsk/ARX_hh.tif`, получен 29.08.2026 |
| `severodonetsk` | 38.3 | 48.3 | 39.7 | 49.1 | ✅ `geo_cache/severodonetsk/dem.tif`, получен 05.08.2026 |

⚠️ **DEM привязан к участку**, а не к программе: имя файла (без расширения) — поле
`THREAT_AREAS[...]["dem"]`, ищется в папке участка. Растр прежнего участка на новом не
подходит и **не подставляется молча**. Пустое поле `dem` означает «своего рельефа
нет»: кнопка «Добавить рельеф» тогда неактивна, пока файл не появится.
Вместо одного GeoTIFF можно положить `.hgt`-тайлы (`N62E040`, `N62E041`, `N63E040`,
`N63E041` для этого участка) — они подхватываются без правки конфига.

**Файл участка `plesetsk`:** GeoTIFF, `float32`, EPSG:4326, 6151 × 2255 пикселей,
48 МБ, шаг 1″ (≈ 30 м, SRTM GL1), охват lon 39.986 … 41.694, lat 62.527 … 63.153 —
участок покрыт целиком (проверено: высоты легли во все **18 326** ячеек сетки).
Высоты на участке: 22 … 203 м, медиана 103 м.

* 🔗 https://portal.opentopography.org/raster?opentopoID=OTSRTM.082015.4326.1 —
  ввести эти координаты, формат **GeoTIFF**, скачать одним файлом (нужна бесплатная
  регистрация). Самый простой путь.
* 🔗 https://srtm.csi.cgiar.org/srtmdata/ — SRTM 90 м тайлами 5°×5°, без регистрации.

Разрешение 30 м (SRTM GL1) предпочтительно (~25 МБ), но 90 м достаточно: ячейка сетки
500 м, на неё и так попадает 5–6 замеров высоты.

**Куда положить:** `geo_cache/dem.tif` (GeoTIFF) или `geo_cache/*.hgt` (сырой SRTM,
имя тайла вида `N48E038.hgt`). Оба формата читаются: GeoTIFF через `rasterio`, `.hgt` —
чистым numpy (int16 big-endian, квадрат 1201² или 3601² на тайл 1°×1°). Файла нет —
слой просто не участвует, остальная карта работает как прежде.

**Зачем.** Чем выше аппарат над окружающей местностью, тем он заметнее — и для
радиолокации, и для глаза, и на слух. Позиции наблюдателей неизвестны, поэтому зоны
обнаружения не считаются; задача проще: **исключить пролёт через высокие места и рядом
с ними, прижав маршрут к низинам**. Абсолютная высота для этого бесполезна — участок
может лежать на плато, важно **превышение над окружающей местностью**.

**Файл получен и проверен** (5 августа 2026). Что в нём:

| Параметр | Значение |
|---|---|
| Формат | GeoTIFF, `int16`, EPSG:4326, одна полоса, 8.8 МБ |
| Размер | 5040 × 2880 пикселей |
| Шаг | 1″ ≈ 20.4 м (В-З) × 30.7 м (С-Ю) — **SRTM GL1**, то самое «30 м» |
| Охват | 38.300 … 39.700 в.д., 48.300 … 49.100 с.ш. — точно как просили |
| Пропуски | **нет**, 100 % валидных пикселей |
| Высоты | 23 … 365 м, медиана 137 м, СКО 62 м |

Покрытие сетки 500 м — все 28 539 ячеек. Чтение и приведение к сетке 0.2 с.

**Как включить.** Кнопка **«Добавить рельеф»** на панели вкладки 3. По умолчанию карта
строится БЕЗ высот — как раньше; кнопка пересобирает её с учётом рельефа, повторное
нажатие возвращает обратно. Нет файла — кнопка неактивна. Отдельно от этого работают два
чекбокса показа: «карта высот (рельеф)» и «приоритет по высоте».

**Как учитывается.** Считается превышение над окружающей местностью в двух масштабах —
над районом (15 км) и над окрестностью (2 км), — и из них строится **множитель** к уже
накопленному положительному весу: от 0.25 на гребне до 1.40 в пойме. Ноль остаётся нулём,
отрицательный вес не трогается, ослабленный коридор не опускается ниже 1, а «очень высокая
гора» (превышение ≥ 80 м над районом или ≥ 50 м над окрестностью) снимается совсем.

Полное описание механики с числами — [МЕТОДИЧКА_КАРТА_УГРОЗ.md §4.5](../вкладка_3/МЕТОДИЧКА_КАРТА_УГРОЗ.md),
правила — [ОГРАНИЧЕНИЯ.md §5.1](../ОГРАНИЧЕНИЯ.md), физика и отклонённые варианты —
[РАДИОВИДИМОСТЬ_ЗАДЕЛ.md](../вкладка_3/РАДИОВИДИМОСТЬ_ЗАДЕЛ.md).

> **Почему не «прибавить к весу», как было задумано сначала.** Первая реализация
> прибавляла вклад ко всем ячейкам и усредняла по одному окну 3 км. Замер на полученном
> файле вскрыл два дефекта. Во-первых, одного масштаба мало: на высоком открытом плато
> превышение над ближней окрестностью равно нулю — штрафа нет, хотя аппарат виден во все
> стороны. Во-вторых, и это важнее, **прибавление перекраивает карту**: старая формула
> создала 5 003 коридора там, где ориентиров нет вовсе (низина без дорог становилась
> «коридором»), и уничтожила 1 113 существующих. Множитель этого не может по построению.

> **Про разрешение файла.** 90 м вместо 30 м тоже сработает, но хуже, чем кажется:
> высота ячейки берётся как СРЕДНЕЕ по ячейке 500 м, и на 30-метровом растре это
> усреднение по ~400 пикселям, а на 90-метровом — всего по ~30. Мелкие балки, которые и
> дают укрытие, на 90 м уже сглажены.

## 5. Как это отображается и как проверить

После «Построить карту»:
* **источник данных** в панели: `OSM …` (не `СХЕМА`) — значит, данные реальные;
* **векторные слои** (чекбокс «векторные слои») — теперь настоящие дороги/реки, а
  не прямые демо-линии;
* **весовая карта (тепло)** — тепловой слой идёт вдоль реальных линий;
* окно **«Выбрать цифровые карты…»** позволяет включать/выключать отдельные слои и
  сразу видеть, как меняется карта весов (например, снять «застройку», чтобы убрать
  репеллер).

Проверка через показатели: в блоке «ВЕС КАРТЫ (по слоям)» суммы должны стать
заметно больше и разнообразнее, чем на демо-схеме.

### Производительность и почему раньше «не считалось»

Коротко о том, как менялось поведение на реальных данных (полезно понимать):

1. **Сначала «Построить карту» вообще не завершалась** (казалось, что зависло
   навсегда). Причина — определение мостов перебирало ВСЕ пары «река × дорога» с
   вложенными циклами по сегментам: O(N²). При тысячах линий это миллиарды операций,
   и расчёт практически никогда не заканчивался.
2. **После оптимизации вычислений** (векторные операции, мосты «по сетке» вместо
   перебора пар, фоновый поток) карта стала считаться за 1–2 секунды. Но при
   тысячах OSM-линий (сотни тысяч точек) и тысячах маркеров-мостов **тормозила
   отрисовка** — панорама/зум дёргались уже ПОСЛЕ построения.
3. **После оптимизации отрисовки** (прореживание линий, отключение сглаживания для
   слоёв, ограничение числа мостов, убран `autoDownsample` подложки) — и расчёт, и
   интерфейс работают быстро.

Практические советы, если на вашей машине всё же тяжело:
* **Чекбокс «векторные слои»** полностью убирает наложенные линии/мосты (карта весов
  «тепло» остаётся) — мгновенно возвращает плавную панораму. Это самый быстрый способ.
* В окне **«Выбрать цифровые карты…»** снимите **`дорога (местная)`** — самый тяжёлый
  слой (тянет все жилые улицы), затем «Построить карту».
* Расчёт идёт **в фоне**: кнопки блокируются, курсор — «ожидание»; интерфейс не
  «висит».

> Порядок работы с окном выбора: сначала в «Выбрать цифровые карты…» отмечаете
> источник и слои, затем нажимаете **«Построить карту»** — накладываются именно
> выбранные слои. Само окно карту не строит (только запоминает выбор).

Быстрая проверка без GUI, что слои прочитались:
```
python -c "from config import Params; from model.threat_grid import ThreatModel; \
m=ThreatModel(Params()); m.set_data_source('geo_cache/severodonetsk.osm.pbf'); \
m.build(); print(m.source); print({k:len(v) for k,v in m.layers.items()})"
```

## 6. Как расширить подход на вкладку 2 (район Курска) и другие области

Механика вкладки 3 полностью **переносима на любой участок**. Чтобы, например,
построить весовую карту угроз для района вкладки 2 (Курск):

1. **Bbox.** Задать прямоугольник области (для Курска — по рамке
   `geomap.OBLAST_BBOX`, например `34.05,50.90,38.45,52.35`). Аккуратный путь —
   не хардкодить, а вынести bbox в параметр (сейчас `config.THREAT_BBOX_LONLAT`
   один; для нескольких участков стоит сделать словарь `REGIONS = {"severodonetsk":
   (...), "kursk": (...)}` и выбирать активный — это небольшой рефакторинг).
2. **Данные.** Скачать `.osm.pbf` для нового bbox (раздел 1, те же шаги, свои
   координаты). Файлы разных участков держать раздельно, например
   `geo_cache/kursk.osm.pbf`.
3. **Слои.** `layers_from_osm(pbf, lon0, lat0, bbox)` уже принимает произвольные
   `lon0/lat0/bbox` — достаточно передать якорь и bbox нового участка.
4. **Отображение.** `ThreatMapView`/`ThreatModel` привязаны к своему bbox через
   конструктор — можно создать **второй экземпляр** вкладки угроз для Курска, ничего
   не меняя в коде отрисовки. Тайловая подложка уже общая (`basemap_mixin`) и
   принимает любой якорь.

То есть «весовая карта угроз для вкладки 2» = тот же `ThreatModel`/`ThreatMapView`
с курским bbox и курским `.osm.pbf`. Единственная доработка под мультирегион —
вынести bbox/якорь из констант в выбор региона (по желанию).

**Растровые** слои местности — их источники:

* **рельеф (ЦМР)** Copernicus DEM GLO-30 / SRTM — 🔗 https://opentopography.org/ —
  ✅ **РЕАЛИЗОВАН** (журнал п. 148). Файл кладётся как `geo_cache/dem.tif`, читается
  через `rasterio`, даёт множитель к весу ячейки по превышению в двух масштабах и
  отсечку слишком высоких мест. Механика — [МЕТОДИЧКА_КАРТА_УГРОЗ.md §4.5](../вкладка_3/МЕТОДИЧКА_КАРТА_УГРОЗ.md),
  правила и пороги — [ОГРАНИЧЕНИЯ.md §5.1](../ОГРАНИЧЕНИЯ.md);
* **землепокрытие** ESA WorldCover (вода/болота/застройка, 10 м) —
  🔗 https://esa-worldcover.org/ — ⏳ **задел, не сделано.** Читалось бы тем же `rasterio`
  и накладывалось на ту же сетку (уклон, влажность — как дополнительные веса и
  репеллеры). Отдельный этап.

> ⚠️ Раньше здесь оба пункта числились одним «отдельным этапом, в текущей версии не
> реализованным». Для рельефа это устарело с п. 148 — он работает и входит в контрольный
> прогон.

## 7. Про виджет отображения (задокументировано на будущее)

Сейчас карта рисуется на **`pyqtgraph.PlotWidget`** (аппаратное ускорение, зум/пан
мышью, наложение растровых и векторных слоёв в одной сцене). Это осознанный выбор
на данном этапе, **оставляем его**. На случай, если позже понадобится сменить
виджет отображения, зафиксируем точки замены:

* **Что развязано.** Вся отрисовка сосредоточена во `view_qt/` (слой VIEW): тайловая
  подложка — `basemap_mixin.py`, карта угроз — `threat_view.py`. Модель
  (`model/threat_grid.py`) и контроллер (`controller_qt/threat_controller.py`)
  **не знают** про pyqtgraph — они оперируют массивами (км-координаты, веса) и
  вызывают методы `render_*`. Значит, сменить виджет = переписать только VIEW,
  сохранив те же методы (`render_threat/layers/sensors/entry_target`, `frame_bbox`,
  `get_toggles`, `set_metrics`).
* **Кандидаты на замену, если понадобится:**
  * чёткость тайлов на HiDPI — послойные `QGraphicsPixmapItem` вместо одного
    композитного растра (см. журнал, п. про размытие) — остаётся в pyqtgraph;
  * веб-виджет с настоящей slippy-map (Leaflet/MapLibre GL) в `QWebEngineView` —
    даёт «родные» тайлы и плавный зум, но усложняет наложение расчётных слоёв;
  * Matplotlib-канвас (как вкладка 1) — проще, но медленнее для интерактива.
* **Критерий выбора.** Пока приоритет — единая сцена «тайлы + векторы + тепло +
  датчики» с быстрым зумом; ему отвечает текущий pyqtgraph. Менять есть смысл
  только под конкретную новую задачу (например, онлайн-slippy-map).

## 8. Короткий чек-лист

1. BBBike (🔗 extract.bbbike.org) → bbox активного участка
   (`plesetsk_wide`: `39.8794,62.5901,41.7516,63.0869`) → PBF → `geo_cache/plesetsk/ARX_1.osm.pbf`.
   ⚠️ Экстракт брать ШИРЕ рамки участка: рамка ужимается внутрь на 2 км (ОГРАНИЧЕНИЯ 5.1в).
2. `pip install pyrosm geopandas shapely pyproj rasterio`.
3. `python tools/build_threat_grid.py` — сложит слои в файл участка.
4. Приложение → вкладка «Карта угроз» → «Построить карту» (или «Выбрать цифровые
   карты…» → указать файл).
5. Убедиться: «источник данных: OSM …», на карте — реальные объекты.
