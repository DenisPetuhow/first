# МЕТОДИЧКА — ВВОД И ВЫВОД ДАННЫХ ЧЕРЕЗ ФАЙЛЫ

> **Что здесь.** Как программа обменивается данными с человеком и с другими программами
> через файлы: какие папки, какие форматы, по каким правилам читается и пишется. Сейчас
> так работают ДАТЧИКИ; по тем же правилам будут сделаны маршруты пролёта (задача 8.6) —
> формат заранее устроен так, чтобы их разбор был общим.
>
> **Зачем отдельный документ.** Форматов будет несколько, и каждый следующий соблазнительно
> сделать «как удобнее сейчас». Через полгода это оборачивается тремя разными способами
> писать координаты и тремя разборщиками. Здесь записаны общие правила — новый формат
> заводится по ним, а не заново.

---

## 1. Папки: что читаем и что пишем — врозь

```
датчики/
├── загрузка/      ← сюда кладут файлы, которые программа ЧИТАЕТ
└── выгрузка/      ← сюда программа ПИШЕТ по кнопке «В файл…»
```

| Правило | Почему так |
|---|---|
| папка **своя**, а не корень программы | выгрузки терялись среди исходников; теперь всё в одном месте |
| две подпапки, а не одна | входные файлы человек готовит сам, выходные создаёт программа; в общей папке они путаются |
| папки создаются **сами** при первом обращении | требовать от человека создать папку — лишний шаг, а забытая папка ломала бы кнопку |
| путь считается от **корня программы**, а не от текущей директории | иначе файлы разбредаются по диску в зависимости от того, откуда запустили |
| в git **не попадают** (`.gitignore`) | это рабочие данные конкретного расчёта, а не код |

**Имя файла по умолчанию — дата и время:** `2026_09_05_09_15_sensor.txt`.
Год первым, разделитель `_`: такие имена сортируются по алфавиту в том же порядке, что и
по времени, и в папке выгрузки сразу виден порядок работ. Двоеточие времени Windows в
имени файла не допускает, потому и подчёркивания.

⚠️ **Память последней папки здесь НЕ применяется.** Обычно программа запоминает, где
человек был в прошлый раз, но для этих кнопок правило другое (заказчик 05.09.2026):
диалог всегда открывается в своей папке. Иначе один поход в чужую папку уводил бы туда
все следующие выгрузки, и файлы снова расползались бы.

**Где в коде:** `view_qt/input_window.py` :: `sensors_dir(kind)`, `default_file_name(when)`,
константы `SENSORS_DIR`, `DIR_LOAD`, `DIR_SAVE`.

## 2. Общие правила формата — на все файлы программы

Эти семь правил делают файл читаемым обратно и переносимым. Новый формат заводится по ним.

| № | Правило | Зачем |
|---|---|---|
| 1 | всё, что начинается с `#` — **комментарий** | шапку можно дополнять, не ломая чтение |
| 2 | первая строка — **опознавательная**: `# UAV-SENSORS v1` | по ней видно, что файл наш и какой версии |
| 3 | колонки разделены **пробелами**, число пробелов не важно | файлы правят руками в блокноте, ровнять по столбцам никто не станет |
| 4 | координаты — **только градусы** (lon, lat) | не зависят ни от якоря, ни от района: файл переносится между участками. Километры программа считает сама |
| 5 | кодировка **UTF-8 без BOM**, перевод строки любой | блокнот Windows пишет UTF-8 с BOM: при чтении первую строку чистим от `﻿`, иначе она не опознаётся |
| 6 | **одна плохая строка не роняет чтение** | отчёт «принято 18, отброшено 2 (строки 7, 12)» полезнее, чем отказ читать весь файл |
| 7 | то, что программа записала, она **обязана прочитать сама** без правки руками | иначе выгрузка бесполезна как вход |

⚠️ **Числа в шапке — справочные.** Программа их показывает, но параметры расчёта берёт
из своих полей: файл описывает ПОЗИЦИИ, а не настройки. Иначе загрузка чужого файла молча
меняла бы радиусы и кратности, и человек считал бы не то, что видит в окне.

## 3. Файл датчиков (формат `UAV-SENSORS v1`)

```
# UAV-SENSORS v1
# дата: 2026-09-05 09:15
#
# типы датчиков:
#   тип  класс    N   R, км   кратность k
#     1  малый    20    2.0        3
#     2  малый     0    3.0        3
#     3  малый     0    5.0        3
#     4  большой   3   15.0        3
#
#  N  тип  режим           lon          lat
#--- ---- -------------- ----------- -----------
    1    1  динамический    40.881100    62.793400
    2    1  статический     40.512000    62.802000
    3    4  статический     40.330000    62.760000
```

| Колонка | Что значит |
|---|---|
| `N` | номер по порядку — **при чтении необязателен** |
| `тип` | 1–3 малые, 4 большие |
| `режим` | `статический` / `динамический`; принимаются также `стат`/`дин`, `static`/`dynamic`, `s`/`d` |
| `lon`, `lat` | градусы, точка или запятая как разделитель дробной части |

**Опора разбора — слово режима**, а не номер колонки: тип стоит перед ним, координаты —
сразу после. Поэтому читается и файл, выгруженный программой (с номерами), и строка из
трёх полей, набранная руками: `2 s 40.5 62.8`.

**Что проверяется при чтении:** тип из списка существующих; координаты — числа и в
земном диапазоне (±180, ±90). Не прошло — строка в отчёт «отброшено», остальные читаются.

**Датчик вне района — законно.** Человек мог задать позиции заранее, до выбора района.
Окно показывает, сколько таких (`manual_outside_area`), но не «чинит» их подтягиванием.

**Где в коде:** `view_qt/input_window.py` :: `write_sensors_file`, `read_sensors_file`,
`parse_mode`, `mode_word`. Читает и пишет одно и то же место — иначе форматы разъезжаются.

## 4. Куда попадают прочитанные датчики

Прочитанная строка — это **условие моделирования**, а не результат расчёта:

```
файл → read_sensors_file → (тип, режим, lon, lat)
     → ThreatModel.add_manual_lonlat(...)          # градусы → километры фрейма
     → manual_sensors[]                            # живут рядом с запретными зонами
```

Список `manual_sensors` переживает пересборку карты и смену района: он задан человеком и
от местности не зависит. Убирается только явно — кнопкой «Очистить датчики», «Сбросом»
или из таблицы окна.

Что с ними делает расстановка — [МЕТОДИЧКА_ДАТЧИКИ_РЕЖИМЫ §1–2](вкладка_3/МЕТОДИЧКА_ДАТЧИКИ_РЕЖИМЫ.md).

## 5. Задел: файл маршрутов пролёта (задача 8.6)

Следующий формат — выгрузка и загрузка накопленных пролётов. Он делается по тем же семи
правилам; отличия только в содержании.

**Что нужно хранить:** каждый маршрут — это ломаная из точек (lon, lat). Маршрутов сотни,
точек в каждом — десятки, поэтому формат построчный: строка = точка, маршруты разделены
строкой-заголовком.

```
# UAV-ROUTES v1
# дата: 2026-09-05 10:20
# маршрутов: 150   точек всего: 8 430
#
# R 1  длина 141.8 км
   40.881100  62.793400
   40.872000  62.788100
   …
# R 2  длина 147.3 км
   …
```

**Открытые вопросы, которые решать при реализации** (записаны, чтобы не решать их дважды):

| Вопрос | Умолчание, если не решим иначе |
|---|---|
| хранить ли высоту точки | нет: модель плоская, высоты берутся из рельефа по координате |
| хранить ли время/скорость | нет: скорость постоянная и лежит в параметрах |
| что делать при загрузке в ДРУГОЙ район | принимать и показывать, как датчики: координаты самодостаточны |
| нужен ли отдельный модуль | да, `model/flight_log.py` — это новый механизм, а не часть окна |

**Папки — по тому же правилу:** `маршруты/загрузка` и `маршруты/выгрузка`, имя по дате и
времени: `2026_09_05_10_20_routes.txt`.

## 6. Задел: своя карта по клику мыши (задача 8.5)

Растровая карта уже загружается через окно «Карта картинкой» с указанием координат углов.
Следующий шаг — **задавать привязку кликами по карте**: человек кликает на карте-подложке
две точки, соответствующие углам своей картинки, и координаты подставляются сами.

Это тоже ввод данных, но не через файл, поэтому здесь только упоминание — подробности в
[плане 8, §8.5](планы/8_ПЛАН_КАРТА_И_ИНТЕРФЕЙС.md).

## 7. Чем проверяется ввод-вывод

`python tools/gui_check.py` — раздел окна «Исходные данные»:

| Проверка | Что подтверждает |
|---|---|
| запись → чтение того же файла | координаты, типы и режимы совпали до знака |
| строка без номера, по-английски (`2 s 40.5 62.8`) | разбор опирается на слово режима, а не на колонки |
| строка «мусор в строке» | отброшена одна, остальные приняты, чтение не упало |
| папки `загрузка` и `выгрузка` | создаются сами, диалоги открываются в них |
| имя файла | `2026_09_05_09_15_sensor.txt` при заданных дате и времени |
