## 1. Сектор появления и пять точек входа

### 1.1. Зачем: одна точка входа давала вырожденную картину

Сперва БПЛА появлялся из **одной** фиксированной точки. Все маршруты выходили из неё
веером — и вся расстановка невольно стерегла этот единственный угол.

На деле известно не место, а **направление**: «ожидаем с северо-запада». Это сектор, а не
точка.

### 1.2. Как задаётся

`set_sector(x_km, y_km)` — клик по краю карты в режиме «Задать сектор кликом» окна «Сектор
налёта». Ось строится «цель → клик», и от неё по полураствору `sector_half_deg()` в каждую
сторону: по умолчанию `THREAT_SECTOR_HALF_DEG` = 30°, **полный раствор 60°**. С 16.09.2026
раствор и число точек — поля `Params` (`threat_sector_half_deg`, `threat_sector_entries`),
их правят в окне, и точки сразу переотбираются (`set_sector_params`).

Вид сектора хранит `sector_kind`: `None` — не задан, `"click"` — ось по клику, `"auto"` —
«Построить сектор» по всем 360° (§1.5).

⚠️ Сектор задаётся **относительно цели**, а не относительно центра карты. Это важно:
«приходят с северо-запада» означает «с северо-запада **от объекта**».

### 1.3. Отбор точек входа — четыре шага, и порядок не случаен

`compute_entry_points` :: **3934**:

1. взять ячейки **приграничной полосы** района (`_edge_band`): полоса 1 км вдоль рамки либо
   кольцо той же ширины у окружности круглого района;
2. оставить те, чьё направление «цель → ячейка» попало в сектор;
3. **выбросить непроходимые и те, из которых цель недостижима**;
4. жадно взять N лучших по весу, **разнося их между собой**.

**Два решения здесь стоит разобрать отдельно.**

⚠️ **Проверка сектора — через скалярное произведение, а не через арктангенс.** Углы имеют
разрыв на 180°: точка на 179° и точка на −179° соседние на местности, но по числам
разнесены на 358°. Сравнение косинусов угла этого разрыва не имеет вовсе — и не требует
ни `atan2`, ни нормировки углов к диапазону.

⚠️ **Достижимость проверяется ЗДЕСЬ, а не потом.** Из точки, откуда до цели нет пути по
коридорам, БПЛА не полетит: это **не «вариант появления», а дырка в выборке** — каждая
попытка старта оттуда гарантированно провалилась бы, и выборка молча недобирала бы
маршруты. Считается одним полем Дейкстры от цели — тем же, что потом нужно маршрутам,
поэтому стоит дёшево.

⚠️ **Разнос точек обязателен.** Без него все пять слипаются в одном «горячем» углу
сектора — там, где вес максимален, — и сектор из 60° вырождается обратно в точку.

### 1.4. Где вес участвует, а где нет

| Этап | Вес учитывается? |
|---|---|
| **отбор** пяти точек входа | **да** — берутся лучшие по весу |
| **розыгрыш старта** конкретного маршрута | **нет** — равномерно между отобранными |

Решение заказчика. Логика: вес говорит, *какие места правдоподобны как точки появления*;
но раз уж пять точек отобраны, каждая из них — равноправный вариант, и делать одну втрое
вероятнее другой оснований нет.

⚠️ **Смена сектора пересобирает карту** (`build()` в `_apply_sector`): свободные зоны
привязаны к точкам входа. Забыть это — получить зоны от прежнего сектора при новых точках.

### 1.5. Сектор по 360° — «Построить сектор» (план 11, 11.6)

Направление не ограничено: берётся весь край района. Дальше — тот же отбор, с одним шагом
перед жадным выбором:

```python
step = np.radians(float(THREAT_SECTOR_AUTO_STEP_DEG))          # доля края, 10°
part = np.floor((ang % (2.0 * np.pi)) / step).astype(int)      # номер доли точки
for i in np.argsort(-score, kind="stable"):
    best.setdefault(int(part[i]), int(i))                      # лучшая точка на долю
```

⚠️ **Лучшая точка на КАЖДУЮ долю, а не N лучших по всему краю.** Иначе все точки собрались бы
на одной «горячей» стороне, и «по 360°» осталось бы на словах. Из 36 «приоритетных направлений»
N берутся тем же `take` с угловым разносом: идеальный шаг — 360° / N.

**Пример.** Круг R = 35 км вокруг Мирного, 12 точек: азимуты 42, 68, 85, 129, 148, 174, 210, 234,
260, 293, 333, 360° — все стороны, самый широкий промежуток 44° (замер 16.09.2026).

### 1.6. Точки входа — три поля, итоговый список один

| поле | что | кто меняет |
|---|---|---|
| `_sector_pts` | отобранные сектором | `compute_entry_points` при каждом пересчёте |
| `manual_entries` | заданные человеком (кнопка «Точки старта») | только человек; «Сброс» и смена района |
| `entry_points` | **итог**: сначала сектор, затем человек | только `_compose_entries` |

⚠️ **`entry_points` руками не присваивается.** Его читают отрисовка, ключ контекста выборки,
свободные зоны и запас хода; стоило одному месту записать туда голый сектор — точки человека
молча пропали бы из маршрутов. Правка мышью разобрана в
[РАЙОН_И_ДАТЧИКИ_МЫШЬЮ §3а](РАЙОН_И_ДАТЧИКИ_МЫШЬЮ.md).

### 1.7. Пауза повтора по углу

`sample_one_route`. Прежняя пауза — по **номеру** точки (`THREAT_SECTOR_ENTRY_COOLDOWN` = 2).
Заказчик 16.09.2026 для сектора по 360° попросил другое: **3 следующих маршрута не стартуют в
районе 45°** от прежнего старта.

```python
if n_ang and recent_ok and ctx.get("entry_span_deg", 0.0) > (n_ang + 1) * zone:
    last = [ents[j]["az"] for j in recent_ok[-n_ang:]]       # азимуты недавних стартов
    far = [i for i in live if all(_deg_diff(ents[i]["az"], a) >= 0.5 * zone for a in last)]
    if far:
        avail = far                                          # нет — остаётся пауза по номеру
```

Три решения, каждое с причиной:

| решение | почему |
|---|---|
| зона шириной 45° (±22.5°), а не ±45° | при пяти точках на круг ±45° запрещали бы почти всё, и старты шли бы строго по кругу |
| правило работает, только если точки разнесены шире **(3 + 1) × 45° = 180°** (`_azimuth_span`) | в секторе 60° оно запретило бы всё; так обычный сектор и эталоны движения остались прежними до бита — `reference_run` и `motion_check` сошлись без пересъёмки |
| история — старты **дошедших** маршрутов (`_recent_ok_entries`), а не попыток | заказчик говорил о «следующих маршрутах». По попыткам замер дал **28 нарушений** зоны на 150 принятых маршрутов, по дошедшим — **0**; старты разошлись по всем 12 точкам (6…17 на точку) |

**Окно создаётся один раз** и живёт до закрытия программы — как «Посмотреть маршруты»:

## 2. Снимок начальных позиций

### 2.1. Что это

Чтобы сравнить «до и после моделирования», нужно запомнить расстановку **до**. Поля:
`initial_sensors` (малые), `initial_sensors_type`, `initial_sensors_big` :: **2789–2791**.

### 2.2. Два решения, каждое оплачено ошибкой

**Снимок берётся РОВНО ОДИН РАЗ за цикл** — на самой первой расстановке:

```python
if self.initial_sensors is None:
    ...
    self.initial_sensors = np.array(self.sensors, float, copy=True)
```

⚠️ Иначе «до» и «после» совпали бы, и сравнивать стало бы нечего: каждая новая расстановка
переписывала бы эталон сравнения самой собой.

⚠️ **`copy=True` обязателен.** Без копии снимок остался бы ссылкой на тот же массив,
который расстановка перезапишет на следующем проходе, — и «до» молча стало бы равно
«после». Ошибка из разряда тех, что не падают, а просто дают пустой результат.

⚠️ **Условия «до итераций» в проверке НЕТ, и это исправление бага 06.09.2026.** Раньше
стояло `len(iter_routes) < 5` — предполагалось, что первая расстановка всегда случается до
моделирования. Но датчики в первый раз считаются не обязательно кнопкой «Расставить»:
их считает и запуск итераций. При таком порядке снимок не брался вовсе, и анализ
размещения оказывался пустым.

## 3. Венгерский алгоритм: куда переехал датчик

### 3.1. Почему это вообще задача

Казалось бы, тривиально: сравнить датчик №1 старый с датчиком №1 новым.

⚠️ **Номер датчика — это просто порядок жадного выбора.** При пересчёте порядок меняется
целиком: позиция, бывшая первой, легко становится седьмой. Сравнение «по номерам» рисовало
бы **случайные пары точек через всю карту** — и не сказало бы ничего.

Правильная постановка: найти такое соответствие «старые ↔ новые», при котором **суммарное
перемещение минимально**. Это классическая **задача о назначениях**.

### 3.2. Что ЭТОТ механизм НЕ делает

⚠️ **Алгоритм расстановки не затрагивается вовсе.** Соблазн велик: заставить жадный выбор
тяготеть к прежним местам, чтобы датчики «не прыгали». Так делать нельзя — это добавит
задаче ограничение, которого в ней нет, и **снимет гарантию (1 − 1/e)**.

Поэтому здесь всё происходит **после** расстановки: позиции не двигаются и не меняются,
рисуется только стрелка «старое → новое».

### 3.3. Сопоставление — только внутри одного типа

`match_by_type` :: **121**. Тип 1 с типом 1, большие с большими. Смешивать бессмысленно:
это разные датчики с разными радиусами, и «минимальное перемещение» между малым и большим
физического смысла не имеет.

**Появление и исчезновение** предусмотрены: датчик без пары получает `new_idx=None` либо
`old_idx=None` и `dist_km=None` — стрелку для него не рисуют, соединять не с чем.

### 3.4. Почему своя реализация, а не `scipy`

Решение заказчика 03.09.2026. `scipy` нужен ради **одной функции**
`linear_sum_assignment`, а тянет за собой риск для сборки `.exe` — и риск перевешивает
выгоду. Матрицы здесь малые (обычно меньше 50 × 50), считаются за доли миллисекунды.

⚠️ **Контракт совпадает со `scipy`** намеренно: `hungarian(cost)` возвращает
`(rows, cols)` ровно как `linear_sum_assignment`. Понадобится `scipy` — заменить нужно
будет **только эту функцию**, ничего вокруг.

### 3.5. Как устроена реализация

`hungarian` :: **30** → `_hungarian_square` :: **70**. Классический венгерский алгоритм
**O(n³)**, метод потенциалов с поиском кратчайших дополняющих путей.

**Прямоугольная матрица** (датчиков стало больше или меньше) дополняется до квадратной:

```python
big = 1.0e6
sq[:n, :m] = cost
sq[:n, m:] = big        # реальная строка → фиктивный столбец
sq[n:, :m] = big        # фиктивная строка → реальный столбец
# sq[n:, m:] остаётся 0 — «фиктивный к фиктивному» ничего не стоит
```

⚠️ **Константа большая, но КОНЕЧНАЯ.** Бесконечность здесь не годится: потенциалы
венгерского алгоритма с `inf` считать нельзя — арифметика вида `inf − inf` разрушает
метод. Значение `1e6` заведомо больше любой настоящей стоимости (километры внутри
участка — максимум пара сотен), поэтому реальная пара предпочтительнее фиктивной всегда.

⚠️ **Внутри 1-индексация, наружу 0-индексная.** Так короче запись через массивы
потенциалов `u`/`v` (классическая реализация), но на границе функции индексы приводятся к
обычным — иначе ошибка на единицу расползлась бы по всему вызывающему коду.

### 3.6. Чем проверяется правильность

`total_movement(matches)` :: **167**. Проверка строгая и содержательная: **сумма
перемещений при венгерском сопоставлении обязана быть меньше либо равна сумме при наивной
нумерации «по порядку»**.

Это не «выглядит правдоподобно», а математическое свойство: венгерский алгоритм даёт
**оптимум**, значит любое другое паросочетание не может быть лучше. Если проверка
показала обратное — сломана реализация, и это видно немедленно.
