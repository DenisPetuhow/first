## 1. Список целей

### 1.1. Что хранится

```python
@dataclass
class Target:
    x_km: float                   # восток от якоря, км
    y_km: float                   # север от якоря, км
    weight: float = 1.0           # приоритет, доля; сумма по всем целям не больше 1
    sectors: bool = True          # рисовать ли у цели компас секторов (только показ, §9.3)
```

`TargetSet` — упорядоченный список таких записей плюс предел `limit`. Порядок важен: номер
цели в таблице, на карте и в мешке — это номер в списке.

⚠️ **Хранение в километрах, а не в градусах** — отступление от плана (§13.12.2 предлагал
градусы, «как у датчиков»). Причина: якорь км-фрейма в сеансе **не меняется** (ОГРАНИЧЕНИЯ
5.1л), и так же в километрах живут все остальные точки, поставленные человеком:
`manual_entries`, `uav_start_km`, `sector_point_km`. Смена района всё равно сбрасывает цели
(`set_area`), как сбрасывала единственную `target_km`. Градусы нужны только таблице — их
считает `target_table_rows`.

### 1.2. `target_km` осталось — свойством

До плана 13 цель была полем `self.target_km`: `None` — не ставили, `(x, y)` — поставили
кликом. Его **пишут** `set_area`, `clear_area`, «Сброс» в контроллере и две проверки
(`gui_check`, `flow_check`). Переименовать поле значило бы тронуть все эти места и молча
сломать то, что пропустили.

```python
@property
def target_km(self):
    pts = self.targets.points_km()
    return pts[0] if pts else None          # ПЕРВАЯ из поставленных

@target_km.setter
def target_km(self, xy):
    if xy is None:
        self.targets.clear()                # «= None» убирает ВСЕ цели
    else:
        self.targets.replace_all(xy[0], xy[1])   # «= (x, y)» оставляет одну
```

Пример, на что влияет: строка контроллера `self.model.target_km = None` в «Сбросе» без
единой правки стала убирать **все** объекты защиты, а не только первый.

### 1.3. Доли: поровну, сумма не больше 1

Правило заказчика 22.09.2026: одна цель — `1.0`, две — `0.5` и `0.5`, три — `0.33`
каждой; правка руками — с проверкой, что сумма **не больше** единицы.

```python
def equal_share(n):
    return math.floor(100.0 / n + 1e-9) / 100.0     # вниз до сотых
```

⚠️ **Округление вниз, а не до ближайшего.** Три по `0.33` дают `0.99` — это **не ошибка**:
правило «не больше 1», а в таблице человек видит два знака, и сумма обязана сходиться с
тем, что он видит. Округление до `0.333…` дало бы в таблице `0.33 + 0.33 + 0.33`, а в
памяти `1.0` — два разных ответа на один вопрос.

`+ 1e-9` — страховка от двоичной записи: `100 / 5` может оказаться `19.999…`, и `floor`
дал бы `0.19` вместо `0.2`.

Проверка правки:

```python
total = self.weight_sum() - self.items[i].weight + w   # сумма ПОСЛЕ правки
if total > 1.0 + WEIGHT_EPS:                          # WEIGHT_EPS = 1e-6
    return "сумма приоритетов стала бы %.2f — больше 1" % total
```

Отсюда порядок правки для человека: чтобы из `0.5 / 0.5` сделать `0.7 / 0.3`, сперва
**уменьшить** вторую до `0.3`, потом **увеличить** первую. Наоборот программа не пустит —
промежуточная сумма `1.2`. Это проверено `gui_check` (раздел 20).

⚠️ **Доли раздаются поровну заново при каждом добавлении цели** — ручные правки при этом
теряются. Сознательно: при появлении новой цели прежнее распределение теряет смысл
(«0.7 / 0.3» между двумя ничего не говорит о третьей).

### 1.4. Приоритетная цель

```python
def priority_index(self):
    ws = [t.weight for t in self.items]
    top = max(ws)
    leaders = [i for i, w in enumerate(ws) if w > top - WEIGHT_EPS]
    return leaders[0] if len(leaders) == 1 else None
```

Приоритетная — та, у которой доля **больше, чем у каждой другой**. Две с одинаковой
наибольшей долей — приоритетной нет (`None`). Одна цель — всегда она (доля `1.0`).

## 2. Мешок: розыгрыш без повторов подряд

### 2.1. Почему не монетка

Требование: «рандомным образом разыгрывается цель налёта, но так, что не может
повторяться след раз». Простой `rng.integers(n)` даёт серии — «2, 2, 2» — и неровный счёт
на коротких прогонах. Поправка «если совпала с прошлой — бросить ещё раз» убирает повтор,
но не выравнивает счёт.

Мешок решает обе задачи разом. Номера целей — колода: перетасовали, выдаём по одной,
кончились — тасуем заново.

```python
def peek(self, rng):
    if len(self.ids) == 1:
        return self.ids[0]                  # ⚠️ одна цель: rng не трогаем
    if not self.deck:                       # круг кончился — новая колода
        self.deck = [self.ids[int(k)] for k in rng.permutation(len(self.ids))]
        if self.deck[0] == self.last:       # стык кругов дал бы повтор подряд
            self.deck[0], self.deck[1] = self.deck[1], self.deck[0]
    return self.deck[0]

def commit(self):
    if len(self.ids) == 1:
        self.last = self.ids[0]
    elif self.deck:
        self.last = self.deck.pop(0)
```

Три свойства, и каждое проверяется `flow_check` (раздел 5г):

| Свойство | Откуда берётся | Замер 23.09.2026 |
|---|---|---|
| подряд одна цель не выпадает | внутри круга номера разные; на стыке — обмен первых двух | 30 маршрутов, повторов **0** |
| за круг каждая ровно по разу | колода — перестановка всех целей | все круги по три — `[0, 1, 2]` |
| доли ровные | следствие второго | **33 % / 33 % / 33 %** |

Пример, на что влияет: при двух целях розыгрыш вырождается в строгое чередование
«1, 2, 1, 2…» — случайна только цель первого маршрута. Это прямое следствие требования
«не повторяться», а не недосмотр.

⚠️ **«Не повторяется» понято как «не подряд»** (вопрос В13.9): «каждая ровно один раз за
весь прогон» при трёх целях и 250 маршрутах невыполнимо.

### 2.2. Одна цель — поток случайных чисел прежний

Это главная ловушка механизма. Любое лишнее обращение к `rng` сдвигает весь дальнейший
поток: разойдутся маршруты, датчики, эталон — и причину не отличить от настоящей поломки.
Поэтому мешок из одной цели отвечает, не трогая `rng`.

Доказано двумя способами:

* `flow_check`, раздел 5г: состояние `rng.bit_generator.state` до и после 20 розыгрышей
  совпадает;
* `motion_check` (зерно закреплено) на коде с целями и на коде коммита `d0cb404` дал
  **построчно одинаковые таблицы** — все показатели формы маршрутов до третьего знака.

### 2.3. Мешок сдвигается только ПРИНЯТЫМ маршрутом

`peek` не снимает цель с колоды — снимает `commit`, и зовут его, когда маршрут **принят**:
дошёл, уложился в запас хода и не дубль.

```python
r = self._sample_route(bag, rng, wmode, spread, spend, approach)
if r is None:                     # не дошёл
    continue                      # — та же цель попробует ещё раз
...
seen.add(sig); pool.append(r)
bag.commit()                      # маршрут принят — очередь следующей цели
```

Почему. Не доходит в среднем **71 %** попыток (замер в шапке `iter_batch`). Если бы колода
сдвигалась на каждой попытке, «не повторяется подряд» выполнялось бы для **попыток**, а
среди принятых маршрутов повторы шли бы сплошь. Хуже того: цель, до которой дойти трудно,
чаще других пропускала бы очередь — и выборка молча перекашивалась бы к лёгким целям.

### 2.4. В мешок идут только достижимые цели

```python
def _new_bag(self):
    return TargetBag([i for i, c in enumerate(self._ctxs) if c.get("reachable")])
```

Если до цели нет пути ни из одной точки входа, каждая попытка к ней провалится — а раз
мешок ждёт принятого маршрута, очередь встала бы навсегда (до `stale` отказов подряд).
Недостижимая цель из розыгрыша исключается; предупреждение о ней даёт `no_fly_check`
(§4.3).

## 3. Контексты выборки — по одному на цель

### 3.1. Почему свой у каждой

Контекст выборки (`build_iter_context`) — это поля Дейкстры **от цели** (`gt`, `gt_geo`,
веер «жадностей»), ось «вход → цель», VIA-точки и пояса облёта **вокруг цели**. Общего у
двух целей нет почти ничего. Разбор самого контекста — Word «Маршруты и датчики», §6а.

Цена замерена до работы (план 13 §0.3г): **5.0 с и 20.7 МБ на цель**; три цели —
12.5 с и ~54 МБ. Заказчик назвал 2–3 цели, поэтому все контексты живут разом, без
вытеснения. Предел `THREAT_TARGETS_MAX` = 5 — запас: 10 целей дали бы ~200 МБ
(оценка по формуле, не замер).

### 3.2. Как устроено

```python
def _ensure_ctx(self, entry):
    key = self._ctx_key()             # разрыв, уход, ЦЕЛИ, точки входа
    if self._iter_ctx is None or self._ctx_built_key != key:
        shared = dict(_recent_entries=[], _recent_ok_entries=[])
        self._ctxs = []
        for t in self.target_points_km():
            c = build_iter_context(self.grid, entry, t, gap, slack_km=slack)
            c.update(shared)          # списки — ОДНИ на все контексты
            self._ctxs.append(c)
        self._iter_ctx = self._ctxs[0]
        self._ctx_built_key = key
```

Три решения, каждое с причиной:

1. **Список, а не словарь.** План предлагал словарь `{цель: контекст}`; список проще
   держать в соответствии с мешком — номер цели в мешке и номер контекста совпадают.
2. **`_iter_ctx` — контекст первой цели.** Его читают показатели интерфейса,
   `count_routes` и четыре проверки (`motion_check`, `plot_run`, `perf_check`,
   `flow_check`). При одной цели это ровно прежний контекст.
3. ⚠️ **История стартов общая.** Пауза повтора точки входа (`_recent_entries`,
   `_recent_ok_entries`) живёт в контексте. Будь она своя у каждой цели, каждая видела бы
   лишь каждый второй-третий маршрут, и пауза стала бы вдвое-втрое короче. Словарь
   `shared` раздаёт один и тот же список всем контекстам.

⚠️ **Счётчики облёта — свои у каждой цели** (`_orbit_done`, `_appr_done`): пояса облёта
строятся вокруг своей цели, и «недобор пояса» у разных целей свой. `iter_reset` обнуляет
их во всех контекстах.

### 3.3. Почему кэш почти всегда пересобирается целиком

Цели входят в ключ контекста. Можно было бы достраивать контекст только новой цели — но
смена цели всё равно **пересобирает карту**: у каждой цели своя свободная зона
(`THREAT_TARGET_FREE_KM`, §4.1), а от карты зависят все поля. Достраивание сэкономило бы
ноль секунд, добавив сложность.

## 4. Где цель входит в расчёт

### 4.1. Карта: свободная зона у каждой цели

```python
free_points += [(t[0], t[1], THREAT_TARGET_FREE_KM, THREAT_TARGET_FREE_KM)
                for t in self.target_points_km()]
```

Цель в центре города без свободной зоны была бы доступна только с одной стороны — город
обнуляет вес. Так было с единственной целью; теперь то же у каждой.

### 4.2. Зона пролёта — объединение

```python
def _envelope_all(self, entry, gap, slack):
    env, lens = None, []
    for t in self.target_points_km():
        m, d = flight_envelope(self.grid, entry, t, self.route_L_max(), gap, slack_km=slack)
        env = m if env is None else (env | m)
        lens.append(d)
    fin = [d for d in lens if np.isfinite(d)]
    return env, (max(fin) if fin else float("inf"))
```

**Объединение, а не пересечение** — та же логика, что у нескольких точек входа: БПЛА летит
к какой-то одной цели и пролететь может над всем, что достижимо хоть к одной.

**Кратчайший путь — по самой дальней из достижимых целей** (`max`, а не `min`). От него
считается авто-запас хода («кратчайший + 20 %»); возьми ближнюю — до дальней маршрут не
уложился бы, и она выпала бы из выборки. Тем же правилом `sync_auto_L_max` берёт самую
дальнюю пару «вход — цель».

## 5. Розыгрыш цели на маршрут

### 5.1. Где разыгрывается

```python
def _sample_route(self, bag, rng, mode, spread, spend, approach):
    ti = bag.peek(rng)                        # чья очередь
    if ti is None:                            # ни одна цель не достижима
        return None
    return sample_one_route(self._ctxs[ti], mode, self.route_L_max(),
                            self.p.threat_turn_interval_km, rng, ...)
```

План предлагал разыгрывать цель **внутри** `sample_one_route`, рядом с точкой входа.
Отвергнуто: функция получает один контекст, а контекст уже привязан к цели — выбрать цель
внутри нельзя, не передавая туда все контексты. Обёртка в модели оставила
`threat_routes.py` нетронутым, и прямые вызовы `sample_one_route` в проверках работают
как прежде.

Три места выборки зовут обёртку: `plan_routes` (свой мешок на каждый вызов),
`iter_step` и `iter_batch` (общий мешок итераций, заводится в `iter_reset`).

### 5.2. Чья цель у готового маршрута

```python
def route_target_index(route, points):
    pts = np.asarray(points, float)
    end = np.asarray(route[-1], float)
    return int(np.argmin(np.hypot(pts[:, 0] - end[0], pts[:, 1] - end[1])))
```

Маршрут кончается в ячейке своей цели — ближайшая к концу и есть его цель. Отвергнутый
вариант — хранить номер цели рядом с маршрутом отдельным списком. Маршруты режутся,
отбираются, грузятся из файла, обобщаются, и параллельный список разъехался бы с ними при
первой же такой операции. Та же приёмка уже работает для точек входа: владелец маршрута в
`_spread_over_area` определяется по ближайшей к **началу**.

### 5.3. Синие линии — поровну и по целям

`_spread_over_area` делит выборку поровну между «хозяевами». Раньше хозяин — точка входа,
теперь пара **«вход × цель»**:

```python
n_own = max(len(ents), 1) * len(tpts)
owner[i] = e_i * len(tpts) + route_target_index(r, tpts)
quota = np.full(n_own, int(np.ceil(want / n_own)), int)
```

Без этого жадный отбор «самых расходящихся» мог отдать все синие линии одной цели — той,
к которой маршруты шире расходятся. При одной цели `n_own` — число точек входа, как было.

## 7. Окно и режим постановки

### 7.1. Поток событий

```
«Указать цель» → TargetsDialog
  «Задать объект» (n) → _begin_targets(n): окна прячутся, правая кнопка — выход
    двойной клик → _target_click → controller.on_target_add → model.add_target
      '' → счётчик вниз; набрали n → _end_targets_mode
      причина («за районом», «предел 5») → в заголовок, режим держится
  правая кнопка / Esc → _end_targets_mode (поставленные остаются)
_end_targets_mode → окна вернулись → on_targets_done (если что-то поставили)
  → _run_async("targets", model.apply_targets): карта + зона пролёта в фоне
  → задача готова: карта, таблица окна, окно сектора, заголовок «Целей: N …»
```

### 7.2. Три решения

1. ⚠️ **«Автоматически применяется» — это пересчёт, и он в фоне.** Каждая постановка
   пересобирает карту (свободные зоны), а это секунды. Пересчёт идёт **один раз**, когда
   постановка закончена: пять кликов — одна пересборка, а не пять. Зона пролёта, синие линии и
   датчики — по «Расставить датчики» (решение заказчика 25.09.2026; до того зона считалась сразу).
2. ⚠️ **Другие режимы мыши выходят из режима целей через `_end_targets_mode()`**, а не
   присваиванием `self._target_mode = False`, как было при одиночной цели. Режим теперь
   держит правую кнопку и прячет окна; простое присваивание оставило бы правую кнопку
   забранной, а окно целей — спрятанным навсегда. Поправлено в шести местах.
3. **«Количество объектов» — сколько ДОБАВИТЬ**, а не «очистить и поставить заново»
   (умолчание по вопросу В13.11): очистка — отдельная кнопка, как заказчик и просил.

⚠️ **Пока идёт фоновый расчёт, цели не ставятся** (`on_target_add` отвечает «идёт
расчёт»): фоновая задача читает список целей, и правка на ходу дала бы полупересчитанную
картину.

### 7.3. Показ

Каждая цель — крест `target_scatter`; при двух и больше — номер над крестом, чёрным
жирным, цветом `THREAT_COLORS["sensor_num"]`, как номера датчиков (белый пропадает на
светлой подложке). Номер на карте совпадает с номером строки таблицы.

## 11. Этап целей: доля по приоритету, потребность по кривой (30.09.2026; прежде — 13.1 Д9–Д10)

**Зачем.** Заказчик 30.09.2026: минимум — не константа 3, а расчёт из числа ПВН, мест и приоритета; приоритет должен
задавать **число**, а не только порядок; старшая не должна забирать долю младших («3 3 3 → 10 3 3»); цель не должна
бросаться ниже уровня защиты (снимок 6: Мирный 81.6 % при 92 %, стоп «прирост < 3 %»). Правило и замер —
[датчики/ЗАЩИТА_ОБЪЕКТОВ](../датчики/ЗАЩИТА_ОБЪЕКТОВ.md).

**Как устроено** (`src/model/placement/target_stage.py :: stage`):

1. **кривая и потребность** — у каждой цели ОДНОЙ `_fill` ставит ПВН до вместимости и отдаёт долю подлёта ≥ k после
   каждого; `need` по кривой: до уровня, а недостижим — пока до потолка кривой остаётся ≥ k порогов:

```python
got = [need(fill(i, empty, len(own[i]))[1], lvl, thr, k) for i in range(K)]   # (шт., достижим ли, потолок)
...
n = int(np.nonzero(S[L] - S < w * thr - 1e-12)[0][0])   # первое n с малым остатком до потолка
```

2. **доля** — `allot(budget, pri, want, least(want, st), k)`: пропорциональное деление `_water` — nᵢ = min(потребность,
   max(наименьшее, λ·pᵢ)), λ делением пополам до Σ = бюджет, округление по дробной части; не хватает на наименьшее
   всем — сперва по k каждой (старшим первыми), остаток снова пропорционально;
3. **постановка** — `put(i, n)` = `_fill` поверх уже стоящих (`anchors=range(nf)`: засечки соседних целей в счёт,
   разнос от них), стоп на уровне по кривой `sh`. Три прохода по убыванию приоритета: минимум min(доля, наименьшее) →
   до доли → остаток бюджета целям ниже уровня;
4. порог и уровень — `gain_pct`, `level_pct`: своё значение паспорта или от k (1 · 3 · 4 … % и 99 · 92 · 89.3 · 86.7 … %).

⚠️ `_fill` читает кривую прямо из матрицы кэша: засечки стоящих + `cumsum` по добавленным в порядке жадного —
отдельного пересчёта нет. Префикс жадного устойчив: первые n из прогона «до вместимости» — те же, что прогон до n.

**Что снято.** Общий жадный по всем целям с весом p / (Σp · подлётов) и стопом `stop_gain` (13.1 Д9) — приоритет в нём
был лишь весом (90/5/5 при k 2 давали 8 / 3 / 3 «по пользе», а при k 1 — как при равных), а стоп по одному ПВН
обрывал цель на неровной кривой. `greedy` умеет это и сейчас (`traj_w`, `groups`, `goals`, `stop_gain` — проверка
`flow_check` 4м), этап целей ими больше не пользуется.

**Отчёт.** `report[i]`: `placed`, `share` (подлёт ≥ k всеми ПВН этапа), `want`, `reach`, `top` (потолок кривой),
`allot`, `n_min`, `why` — «уровень X %» / «мест с подлётом нет» / «насыщение: максимум X %» / «доля N, потолок B» /
«доля N, квота N» / «ПВН не хватило»; `budget`, `gain_pct`, `level_pct`. «Мест с подлётом нет» — `_useful_left`:
ни одно свободное место зоны не видит подлёт с засечками < k; проверяется раньше бюджета — маленькой зоне он не поможет.

**«Анализ» у цели (Д10)** — `ThreatModel.target_protection(i)` → `target_stage.protection`: подлёт ≥ 1 / ≥ k всеми ПВН
типа; у незасечённых — «мест в радиусе R меньше k» / «мешает разнос» / не хватает ПВН; «сколько добавить» — тот же
жадный от стоящих ПВН до вместимости, только счёт. В заголовке раздела — минимум, доля по приоритету, «нужно». 0.1 с на цель.
