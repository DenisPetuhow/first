## 1. Зачем: область приходит кусками, а программа берёт по одному файлу

Программа читает у области **один** файл слоёв (`.npz`) и **один** растр рельефа — их
имена записаны в `область.txt` (ключи `слои`, `рельеф`). Большую область так не скачать:
источники режут её полосами.

**Пример — область Marshut (13.09.2026).** 500 × 1 340 км пришли пятью файлами: слои —
три `.pbf` полосами по широте (51–55°, 55–59°, 59–63°, всего 906 МБ), рельеф — два `.tif`
(51–57°, 57–63°, 4.9 ГБ). До `pack_area` склейки не было ни в одном скрипте.

## 2. Кто за что отвечает

| Где | Отвечает за |
|---|---|
| `area_file.read_area_folder` | рамка области и имена итоговых файлов из `область.txt` |
| `pack_area.main` | разбор ключей: `--only dem/layers`, `--pbf`, `--jobs`, `--force` |
| `pack_area._files`, `_part_path` | где искать исходники и части: корень папки **и** `_части/` |
| `pack_area.merge_dem` | сшивка растров в один GeoTIFF построчными кусками |
| `pack_area.pack_layers` | слои: собрать недостающие части, затем слить — только если есть ВСЕ |
| `pack_area.build_part` | слои ОДНОГО `.pbf` → `_части/<файл>.npz`; последовательно или по ядрам |
| `pack_area._groups` | раскладка слоёв по процессам с близкой трудоёмкостью |
| `pack_area._worker` | тело процесса: своя группа слоёв из того же файла |
| `pack_area.merge_parts`, `_key` | слияние частей с выбрасыванием дублей на стыках полос |
| `model/threat_grid.py` :: `layers_from_osm` | **само чтение OSM**: `pyrosm` → фильтр тегов → геометрия → км → обрезка по рамке |

⚠️ **Чтение OSM живёт в модели, а не в скрипте** — тем же кодом пользуются
`build_threat_grid.py` и окно «Цифровые карты». `pack_area` только раскладывает работу и
собирает результат: второй копии разбора нет.

## 3. Как течёт работа

```
geo_cache/<область>/область.txt ──► рамка, имена «слои» и «рельеф»
│
├─ РЕЛЬЕФ   все *.tif (корень и _части/) ─► merge_dem ─► <рельеф>.tif
│
└─ СЛОИ     все *.pbf (корень и _части/)
            │   по каждому .pbf:
            ├─► build_part ─┬─ --jobs 1: layers_from_osm(все слои)
            │               └─ --jobs N: N процессов, у каждого своя группа слоёв
            │                            └─► _части/<файл>.pbf.npz
            │
            └─► все части есть? ─► merge_parts (дубли на стыках — вон) ─► <слои>.npz
```

⚠️ **Части нужны не для порядка, а для живучести.** Полоса 320 МБ разбирается 46 минут.
Часть, сохранённая на диск, не пересобирается: прерванный прогон продолжается с того
места, а полосы можно разбирать разными запусками одновременно (`--pbf`).

## 4. Рельеф: сшивка построчными кусками

```python
for r0 in range(0, H, DEM_CHUNK_ROWS):              # 2 048 строк за проход, а не 43 300 разом
    buf = np.full((n, W), np.nan, np.float32)
    for s, sr, sc in place:                          # файл и его сдвиг в итоговой сетке
        part = s.read(1, window=((lo - sr, hi - sr), (0, s.width)))
        take = np.isnan(tgt) & np.isfinite(part)     # первый файл важнее — не затираем
        tgt[take] = part[take]
    dst.write(buf, 1, window=((r0, r0 + n), (0, W)))
```

**Почему кусками.** Итог Marshut — 33 528 × 43 300 пикселей, 5.4 ГБ без сжатия. Кусок в
2 048 строк — 275 МБ: в памяти держится одна полоса, а не весь растр.

⚠️ **Сетки обязаны совпасть до пикселя** — та же проекция, шаг и выравнивание. Сдвиг файла
в итоговой сетке должен быть целым числом пикселей, иначе высоты съедут на долю шага; тогда
скрипт отказывает с причиной, а не сшивает криво.

**Пример.** Marshut: сшито за 17 с, 4.60 ГБ; 1 000 случайных точек совпали с исходниками
1 000 из 1 000, строки у стыка — точь-в-точь.

## 5. Слои: части и дубли на стыках

**Почему дубли вообще есть.** Экстракт полосы берёт дорогу, пересекающую её границу,
**целиком**. Та же дорога есть и в соседней полосе. После обрезки по рамке области обе копии
одинаковы — и без очистки её длина вошла бы в вес ячеек дважды.

**Пример, на что это влияет.** Ровно по линии стыка 55° встала бы полоса удвоенного веса —
ложные коридоры поперёк всей области, и датчики потянулись бы к ней.

```python
def _key(arr):                                      # отпечаток ломаной с точностью 1 м
    r = np.round(np.asarray(arr, np.float64) / DEDUP_KM).astype(np.int64)
    return hashlib.blake2b(r.tobytes() + str(r.shape).encode(), digest_size=16).digest()
```

Координаты округляются до 1 м — одинаковые линии дают один отпечаток, разные почти
никогда. Пункты сравниваются иначе: по координатам, типу **и имени** — точка и её подпись
идут парой, и терять эту связь нельзя.

## 6. ⭐ Параллельность: как это вообще устроено

### 6.1. Поток и процесс — в чём разница

| | Поток (thread) | Процесс (process) |
|---|---|---|
| память | **общая** с остальной программой | **своя**, копия данных |
| интерпретатор Python | один на всех | свой у каждого |
| Python-код параллельно | ❌ нет — мешает GIL | ✅ да |
| чем дорог | почти ничем | запуск, память, пересылка данных |

**GIL** (глобальная блокировка интерпретатора) пропускает к Python-коду один поток за раз.
Потоки выигрывают, только когда их работа идёт **вне** Python: ожидание диска и сети,
numpy на больших массивах, декодирование картинок. Считать Python-циклы быстрее потоки не
могут — нужны процессы.

### 6.2. Где в программе уже есть потоки — и почему там их хватает

Все три — задачи `QRunnable` на общем пуле `QThreadPool.globalInstance()`:

| Где | Что делает в фоне | Зачем поток |
|---|---|---|
| `controller_qt/threat_controller.py` :: `_Task` | построение карты, маршруты, расстановка | **окно не замирает**: интерфейс живёт, пока модель считает |
| `view_qt/tile_layer.py` :: `_TileTask` | тайл с диска или из сети и его декодирование | ожидание диска и сети — GIL отпущен |
| `view_qt/basemap_mixin.py` :: `_BasemapTask` | старая сборка мозаики (`UAV_TILES_MOSAIC=1`) | то же |

⚠️ **Поток расчёта не делает сам расчёт быстрее** — он только не держит окно. Где чистый
Python держит GIL (Дейкстра — 3.94 с подряд), остальные потоки ползут; разбор —
[план 10 §10.9.3](../планы/10_ПЛАН_ПРОЕКЦИЯ_И_ОСТАТКИ.md).

### 6.3. Почему разбор `.pbf` — процессами

Разбор — это `pyrosm`, `geopandas`, `shapely` и циклы Python по сотням тысяч линий
(`_geom_to_kms`, `_clip_parts`). Большая часть работы идёт под GIL, и потоки выстроились бы
в очередь. Поэтому `pack_area` запускает **отдельные процессы** — у каждого свой интерпретатор
и своё ядро. Программе это не нужно: `pack_area` — инструмент подготовки данных, в окне он
не работает.

### 6.4. Что делится: СЛОИ, а не карта

Напрашивается нарезать область на квадраты и отдать по квадрату на ядро. **Отвергнуто**:

* **стыки.** Линия, обрезанная по краю квадрата, в двух соседних кусках — **разные** куски,
  и `_key` их как дубли не узнает. А с запасом обрезки в 3 км они ещё и перекрываются —
  вес на стыке удвоится;
* **чтение не делится.** `pyrosm` читает весь файл и только отбирает узлы по рамке — каждый
  процесс всё равно прочёл бы файл целиком.

Делятся **слои**: каждый процесс читает тот же файл и собирает свою группу слоёв тем же
`layers_from_osm`. Геометрически это ровно та же работа, что последовательно, только
разложенная по ядрам, — **итог совпадает побайтово**, стыков нет в принципе.

```python
# model/threat_grid.py — одна строка разрешила делить работу, не меняя разбор
for layer, flt in OSM_LAYER_FILTERS.items():
    if only_layers is not None and layer not in only_layers:   # слой достался другому процессу
        continue
```

### 6.5. Как раскладываются слои

Слои очень неравны: в полосе с Москвой лесных дорог 377 тыс. линий, трубопроводов — 1.5
тыс. Отдать по номеру — один процесс получит всю тяжесть. `_groups` раскладывает **жадно**:
слои от тяжёлого к лёгкому, каждый — в самую лёгкую на этот момент группу. Веса —
`LAYER_COST`, число объектов по слоям в полосе `Mar_1`.

**Как разложилось на `Mar_3` при 4 процессах** (из журнала прогона): лесные дороги — одни;
местные дороги — одни; застройка, просеки, реки, лесополосы; всё остальное вместе с пунктами.

⚠️ **Потолок задают две вещи.** Слой не делится — лесные дороги целиком в одном процессе.
И главное — **чтение файла у каждого процесса своё** (§6.8): если оно и есть основная доля
времени, раскладка слоёв не поможет, как бы ровно ни легла.

### 6.6. Как процессы запускаются и собираются

```python
from concurrent.futures import ProcessPoolExecutor
groups = _groups(list(OSM_LAYER_FILTERS) + ["place"], jobs)     # "place" — пункты
with ProcessPoolExecutor(max_workers=len(groups)) as ex:
    for got, sec in ex.map(_worker, [(pbf, lon0, lat0, bbox, sorted(g)) for g in groups]):
        layers.update(got)                                       # группы не пересекаются
layers = {n: layers[n] for n in order if n in layers}            # порядок — как последовательно
```

| Шаг | Что происходит | ⚠️ На что наступить |
|---|---|---|
| запуск | на Windows процесс **порождается заново** (spawn): новый Python импортирует модуль | тело скрипта обязано быть под `if __name__ == "__main__":` — иначе каждый процесс запускал бы процессы |
| задание | аргументы (путь, рамка, имена слоёв) **сериализуются** и пересылаются | передавать пути и числа, а не данные |
| работа | `_worker` → `layers_from_osm(only_layers=…, with_places=…)` | функция процесса — на верхнем уровне модуля, иначе её не переслать |
| результат | массивы слоёв **копируются** обратно в главный процесс | сотни МБ на полосу: это цена, а не ошибка |
| сборка | `ex.map` отдаёт результаты в порядке заданий; порядок слоёв восстанавливается | без восстановления порядка `.npz` отличался бы от последовательного |

### 6.7. Память — главное ограничение

Каждый процесс держит **свой полный разбор файла**: узлы и пути `pyrosm` кэширует в объекте
на всё время работы. Поэтому память = число процессов × память одного разбора.

**Пример.** Полоса `Mar_1` (320 МБ) одним процессом занимала до **11.4 ГБ**. Четыре процесса
на неё — около 45 ГБ (оценка, не замер) при 61.6 ГБ на машине. Для такой полосы — не больше
3 процессов, для полосы 105 МБ — 4.

### 6.8. ⚠️ Замер: деление по слоям НЕ ускорило — и что ускорит

Проверка 13.09.2026 на `Mar_3` (105 МБ), `--jobs 4`, рядом шёл разбор `Mar_2`:

| | Последовательно | 4 процесса по слоям |
|---|---|---|
| время всего | **4.2 мин** | **5.1 мин** (×0.8) |
| время каждого процесса | — | 4.8 … 5.0 мин |
| итог против последовательного | — | ✅ **все 17 слоёв совпали побайтово** |

**Почему так.** Процесс, собиравший ОДНИ лесные дороги, шёл 4.9 мин — столько же, сколько
весь последовательный разбор всех 15 слоёв. Значит, почти всё время — **чтение и разбор
самого файла** в `pyrosm`, а проходы по слоям дёшевы. Чтение у каждого процесса своё, и
делить нечего; четыре чтения одного файла рядом с пятым процессом ещё и толкались за диск.

**Пример, что из этого следует.** Файл ×3 давал время ×11 (`Mar_3` 105 МБ — 4.2 мин, `Mar_1`
320 МБ — 46.1 мин). Раз время растёт быстрее размера, выгодно делить **сам файл**: полоса
320 МБ, нарезанная на три файла по ~107 МБ, разбиралась бы тремя процессами порядка 5 мин
вместо 46 (оценка по двум замерам, не проверено). Но резать `.pbf` нечем: это делает
утилита `osmium extract` — новая библиотека ([план 10, 10.13](../планы/10_ПЛАН_ПРОЕКЦИЯ_И_ОСТАТКИ.md),
вариант В), и решение о ней за заказчиком.

⚠️ **`--jobs` оставлен, но по умолчанию выключен (1).** Он верен побайтово и пригодится, если
чтение станет дешёвым (например, после нарезки файла). Сейчас включать его смысла нет.

## 7. Где ломается легко

* ⚠️ **часть `<кусок>.pbf.npz` — не файл слоёв.** Она покрывает одну полосу, программа её не
  читает. Итог — только после слияния, под именем из `область.txt`;
* ⚠️ **слияние, пока нет всех частей, не запускается** — иначе итог молча вышел бы без
  полосы. Отсюда и поиск в двух местах: исходник, убранный в `_части/`, иначе потерялся бы;
* ⚠️ **новый слой в `OSM_LAYER_FILTERS` без веса в `LAYER_COST`** получит вес 1 — разбор
  останется верным, но раскладка по процессам станет хуже. Добавить вес по числу объектов;
* ⚠️ **разбор по ядрам не ускоряет чтение файла** — только сборку слоёв, а она оказалась
  малой долей: замер ×0.8 (§6.8). Не включать `--jobs` в расчёте на выигрыш без нового замера.
