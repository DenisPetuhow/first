## 1. Запрос: где поставить датчики, если маршрут неизвестен

**Как поставлен.** Надёжно засекать БПЛА при минимальном числе датчиков. ⚠️ Ни точка
вылета, ни цель заранее **не заданы**.

**В чём трудность.** Нельзя написать «возьмём путь БПЛА и прикроем его» — пути нет. Его
надо **придумать правдоподобно**, и не один, а множество.

**Чем отвечает код** — три шага, каждый работает на выходе предыдущего:

```
местность (OSM, рельеф)
   ▼  во что превратить местность, чтобы по ней считать
ВЕСОВАЯ СЕТКА 500 × 500 м     где полетит скорее, а где не полетит вовсе
   ▼  как из «где вероятнее» получить конкретные пути
ВЫБОРКА МАРШРУТОВ             сотни траекторий, а не одна «оптимальная»
   ▼  как из путей получить позиции
РАССТАНОВКА ДАТЧИКОВ          жадный выбор с гарантией (1 − 1/e)
```

⚠️ **Каждая стрелка — смена типа данных**, и ломается обычно на стыках: градусы → км,
линии → сетка, сетка → пути, пути → позиции.

## 2. Запрос: откуда берётся местность и что загружается

**Главные элементы.**

| Что | Кто читает | Во что превращается |
|---|---|---|
| **область** — `geo_cache/<область>/область.txt` | `area_file.active_area` из `config.py` | рамка области, начальный район, имена файлов слоёв и рельефа |
| векторные слои (реки, дороги, ЛЭП, застройка, НП) | `load_layers` | ломаные `(N, 2)` **в километрах** |
| рельеф (GeoTIFF / `.hgt`) | `load_dem_grid` | высота в центре каждой ячейки |
| подложка (тайлы OSM) | `tile_layer.TileLayer` | каждый тайл — свой элемент сцены, пиксель в пиксель |
| своя карта картинкой | `map_image` + `MapAnchor` | фон |

**Как это в коде** — `threat_grid.py` :: `load_layers`, приоритет источников:

```python
if data_path:                                  # 1) человек выбрал файл сам
    if ext == ".npz":  return _load_layers_npz(data_path), "NPZ: …"
    if ext in (".pbf", ".osm"):                #    сырой OSM — разбирается на месте
        return layers_from_osm(data_path, lon0, lat0, bbox_lonlat), "OSM: …"

path = layers_cache_path()                     # 2) кэш СВОЕГО участка
if os.path.exists(path):
    return _load_layers_npz(path), "OSM (офлайн-кэш: …)"

return _synthetic_layers(lon0, lat0), "СХЕМА (демо, офлайн)"   # 3) ⚠️ молчаливый запас
```

⚠️ **Третья ветка — главная ловушка всего механизма.** Файла нет — программа **не падает**,
а рисует демо-схему. На экране появляется что-то картоподобное, и это легко принять за
загруженные данные. Отличить можно только по подписи источника.

**Важное.**

⚠️ **Подложка и картинка-карта в расчёт не входят вовсе** — только показ. Веса считаются
по векторным слоям: у картинки нет геометрии, из неё нельзя узнать, где река.

⚠️ **Форматов данных два, и это не случайность.** `.osm.pbf` — исходник (весь OSM подряд,
нужен тяжёлый геостек), `.npz` — рабочий формат (отобранное, уже в километрах, читается
одним `numpy`). Замер: **17.1 МБ / 4.3 с против 7.2 МБ / 0.03 с** — в 140 раз быстрее.
⚠️ **`.npz` в проекте ДВА РАЗНЫХ**: векторные слои и растр весовой сетки.
Разбор — [МЕТОДИЧКА_ФОРМАТЫ_PBF_И_NPZ](../карты/МЕТОДИЧКА_ФОРМАТЫ_PBF_И_NPZ.md).

⚠️ **Большая область ломает то, что на малой незаметно** (14.09.2026, область Marshut
500 × 1 340 км). Два места, оба читаются `threat_grid.py` без смены математики:

* **слои** — у большой области 2.6 млн линий, и по массиву на линию `.npz` читался 15+ мин.
  Упакованный файл хранит слой двумя массивами (точки подряд + границы), `_load_layers_npz`
  понимает оба вида: **1.8 с** ([ФОРМАТЫ §3.1а](../карты/МЕТОДИЧКА_ФОРМАТЫ_PBF_И_NPZ.md));
* **рельеф** — `_sample_geotiff` читает не весь растр, а **окно под районом**: сшитый
  растр 4.6 ГБ, построение карты на районе **86 → 12–15 с**, высоты те же до 1.3·10⁻⁷ м
  ([КАРТА_УГРОЗ §4.5](../вкладка_3/МЕТОДИЧКА_КАРТА_УГРОЗ.md)).

⚠️ **Всё считается в километрах** от юго-западного угла области. Градусы живут только на
границе: при загрузке и при показе координат.

**Какие объекты OSM вообще попадают в слои.** Решает один словарь тегов, и **пропущенное
в нём до расчёта не доходит никак**. Ни рендер, ни подложка этого не покажут: объекта
просто нет в файле слоёв.

```python
OSM_LAYER_FILTERS = {                          # model/threat_grid.py — единственный источник тегов
    "road_local": {"highway": ["tertiary", "unclassified", "residential", "road"]},
    # несколько КЛЮЧЕЙ объединяются через «или»: подъезды и заброшенные — тоже лесные дороги
    "track":      {"highway": ["track", "service"], "abandoned:highway": ["track"]},
    "cutline":    {"man_made": ["cutline"]},   # просека
    ...
}
```

⚠️ **Пример, почему это главное место.** До 13.09.2026 фильтр брал 7 значений `highway` из
17 и терял **72 % дорог** лесного участка (20 498 км), в том числе все лесные дороги и
просеки. Слой живёт ещё в трёх местах: вес `config.THREAT_LAYERS`, порядок, стиль. Слой,
заведённый наполовину, ловит `gui_check.py`, раздел 11. Подробно, с весами и отложенными
тегами — [МЕТОДИЧКА_КАРТА_УГРОЗ §2.1](../вкладка_3/МЕТОДИЧКА_КАРТА_УГРОЗ.md).

**Показ и расчёт порознь (окно «Цифровые карты»).** Галочка слоя только **скрывает** его на
карте, в весах он остаётся. «Применить к расчёту» передаёт набор в модель, и следующий
«Построить карту» собирает веса без снятых слоёв:

```python
self.view.set_vector_visible(name, on)         # галочка: перерисовать, расчёт не трогать
self.view.apply_digital_maps(path, enabled)    # «Применить»: model.set_enabled_layers(enabled)
```

**Какая область открыта — из файла, и до импорта `config`.** Область (чёрная рамка) —
это рамка, начальный район и имена файлов в `область.txt` своей папки. Её выбирают в окне
«Исходные данные», выбор запоминается, программа перезапускается:

```python
# main_qt.py — ДО `from config import …`
area_file.apply_saved_choice()         # память окна -> UAV_AREA_DIR, UAV_TILE_CACHE
# config.py
THREAT_AREA, _AREA, THREAT_AREA_SOURCE = area_file.active_area(THREAT_AREAS, THREAT_AREA)
```

⚠️ **Почему перезапуск, а не смена на лету.** `config` отдаёт область константами, и их
разбирают при импорте ~30 мест модели и вида. Сменить на лету — значит переделать всё это
на аргумент. ⚠️ **Разбор файла — в корне проекта, не в `model/`**: `config` → `model/__init__`
→ `threat_grid` → `config` — круговой импорт. Папка тайлов меняется сразу: `geomap` читает
корень при каждом обращении.

**Пример.** Проверочные скрипты память окна не читают: иначе `reference_run` молча считал
бы область, которую последней открывали в программе, а эталон снят на `arh`.
Кто за что отвечает, порядок при запуске, почему перезапуск и выбор файла, а не папки, —
[ОБЛАСТЬ_ИЗ_ФАЙЛА](ОБЛАСТЬ_ИЗ_ФАЙЛА.md).

**Большая область качается кусками — склеивает `tools/pack_area.py`.** Рельеф из нескольких
`.tif` одной сетки сшивается в один растр, слои из нескольких `.pbf` — в один `.npz`.
⚠️ Дорога через стык лежит целиком в обоих соседних `.pbf`; без выбрасывания дублей её
длина вошла бы в вес дважды, и на стыке встала бы ложная полоса коридоров. Как устроено,
кто за что отвечает и как разбор делится по ядрам (замер: не ускоряет — время съедает
чтение файла) — [УПАКОВКА_ОБЛАСТИ](УПАКОВКА_ОБЛАСТИ.md); формат файла и Marshut —
[план 10 §10.5](../планы/10_ПЛАН_ПРОЕКЦИЯ_И_ОСТАТКИ.md).

**Подложка — поштучные тайлы, пиксель в пиксель.** Склеенная в одну картинку мозаика
расходилась со слоями к середине вида (Меркатор внутри, линейная натяжка снаружи) и
мылилась при любом масштабе, кроме 1:1. Теперь каждый тайл кладётся своим прямоугольником,
колесо ходит ровно по уровням тайлов, сглаживание включено только у тайла.

**Пример.** Вид «вся область»: расхождение со слоями **11 px → 0.71 px**, масштаб тайла

## 3. Запрос: где БПЛА вообще МОЖЕТ пролететь

**Главный элемент.** Область залёта `route_area` — `flight_envelope` в `threat_routes.py`,
вызывается из `_refresh_envelope`.

**Как это в коде** — вся суть в пяти строках:

```python
gt = _dijkstra_dist(pas, goal, grid.h)         # поле расстояний ДО ЦЕЛИ — считается один раз
env = np.zeros(gt.shape, bool)
for s in starts:                               # точек входа несколько: сектор и точки человека
    ge = _dijkstra_dist(pas, s, grid.h)        # поле расстояний ОТ ЭТОГО ВХОДА
    total = ge + gt                            # ключ: длина пути «вход → ячейка → цель»
    env |= np.isfinite(total) & (total <= L_max)
```

**Почему так.** Ячейка достижима, если сумма «дойти до неё» + «дойти от неё до цели»
укладывается в запас хода. Два поля Дейкстры дают это **для всех ячеек разом**, а не
перебором путей — отсюда и точность, и дешевизна.

⚠️ **`|=` — объединение по входам, а не пересечение.** БПЛА появится из какой-то ОДНОЙ
точки сектора, значит пролететь он может над всем, что достижимо **хотя бы из одной**.
Пересечение дало бы «куда он долетит из любой точки» — ответ на другой вопрос, и куда
более узкий.

⚠️ **`np.isfinite` обязателен.** Недостижимые ячейки получают `inf`, и `inf <= L_max`
даст `False` — но `inf + inf` в сумме тоже `inf`, а при разных знаках в других расчётах
вылезет `nan`. Явная проверка дешевле, чем ловить это потом.

**Важное.**

⚠️ **Это ТОЧНЫЙ ответ, а не приближённый.** На карте — розовая заливка. Именно она
отвечает на вопрос «куда он может долететь»; голубые линии поверх неё отвечают на другой
вопрос и полными быть не могут (§4).

⚠️ **Вес ячейки здесь не участвует** — только проходимость и запас хода. Вес говорит, где
*вероятнее*, а область — где *возможно*.

## 4. Запрос: как он полетит

**Главные элементы.** `plan_routes` (показ, 250 линий) и `iter_batch` → `sample_one_route`
(моделирование, 150 маршрутов).

**Как это в коде** — `_walk_field`, оценка одного соседа и выбор:

```python
prog = dfield[cur] - dj                        # насколько этот сосед БЛИЖЕ к цели
corr = _mode_corridor_pref(wnorm[vy, vx], wmode)   # привлекательность по весу (режим панели)
s = float(np.exp(prog / tau)) * corr * hf      # оценка = прогресс × вес × удержание курса
if vy * nx + vx in visited:
    s *= 0.12                                  # был здесь — гасим петли, но НЕ запрещаем
...
# РАЗВИЛКА — «метод рулетки»: вероятность выбрать соседа ∝ его оценке
sc = np.asarray(score, float)
j = int(np.searchsorted(np.cumsum(sc), rng.random() * sc.sum()))
```

**Три множителя — три разных соображения, и каждый нужен:**

| Множитель | Что выражает | Что будет без него |
|---|---|---|
| `exp(prog / tau)` | стремление к цели | маршрут бродит и не долетает |
| `corr` | привлекательность местности | летит напрямик, коридоры не при чём |
| `hf` | удержание курса (14.0 прямо, 0.5 на пределе) | зигзаг: физика аппарата нарушена |

⚠️ **`tau` — «температура».** Запас хода на исходе → `tau` мал → `exp` резко выделяет
соседа с максимальным прогрессом, и маршрут перестаёт петлять, а идёт к цели. То есть
случайность **сама убывает** по мере расхода топлива, без отдельного правила.

⚠️ **Повторный заход штрафуется, а не запрещается** (`*= 0.12`). Запрет загонял бы
маршрут в тупики: иногда единственный выход — вернуться на клетку назад.

⚠️ **Рулетка через `cumsum` + `searchsorted`, а не `rng.choice(p=…)`** — то же
распределение, но без нормировки и без аллокаций на каждом шаге; шагов миллионы.

**Важное.**

⚠️ **Почему не ищем кратчайший путь.** Дейкстра дал бы ОДНУ линию — самую дешёвую. Но
задача не «куда полетит идеальный аппарат», а «где он может оказаться». Единственный путь
здесь — **неверный** ответ, а не приближённый. Прежний детерминированный роутинг из кода
удалён вместе с константами.

⚠️ **Перечислить все пути нельзя ни при каких мощностях.** Замер 11.09.2026: **7.24 ·
10¹⁶²** для действующей области (Плесецк — 8.24 · 10¹⁰⁴). Атомов во Вселенной ~10⁸⁰.
Само число при этом считается **точно** — динамическим программированием от цели наружу,
за O(числа ячеек): `count_possible_routes`.

⚠️ **Полей расстояний ДВА.** Одно в километрах — по нему проверяется запас хода; другое в
«стоимости» — по нему выбирается направление. Смешать их значит либо считать топливо по
привлекательности, либо лететь по километражу мимо коридоров.

**Повадки маршрута — четыре случайные оси, каждая своим списком в панели** (разыгрываются в
`sample_one_route` каждому маршруту): вес (к коридорам / к пустошам), разброс (через какую
точку обхода VIA и насколько широко облёт), **облёт цели** (обычный заход / сбоку / с
обратной стороны: 85/10/5 · 60/25/15 · 30/35/35 · смесь; `_pick_approach` → `_orbit_chain` →
`_walk_chain`) и расход хода (когда вилять). Облёт идёт через точку в одном из пяти поясов
вокруг цели, границы поясов — доли среднего расстояния вход→цель, край — точка входа
(`_orbit_pool`). Без этой оси заход с обратной стороны был невозможен: участок к цели идёт под уклон.

⚠️ **Доли повадок и поясов держатся среди ДОШЕДШИХ маршрутов** (`_quota_order`, 11.5): вариант,
недобравший своё, выпадает чаще. Простой розыгрыш терял дальние облёты — они чаще не
укладываются в запас: облёту «максимального» заказано 35 %, в выборку попадало 24.9 %, теперь 35.0 %.

⚠️ **Облёт и разброс раздельны, потому что управляют разным** — замер 16.09.2026 (11.5): доля
облёта от разброса не зависит (17.9 / 17.1 / 17.1 % в выборке), а радиус зависит (12.6 / 13.9 /
20.7 км) — разброс выбирает ближний или дальний ряд пояса. Как к этому пришли —
[модель/МАРШРУТЫ_ИСПРАВЛЕНИЕ](../модель/МАРШРУТЫ_ИСПРАВЛЕНИЕ.md).

⚠️ **Точки обхода (VIA) готовятся заранее, а не подбираются на лету.** Район делится
сеткой **4 × 5 = 20 узлов**; узел притягивается к ближайшей проходимой ячейке и выбывает,
если он позади старта, за целью дальше 10 км или подошёл к цели ближе рубежа подхода (точка
вплотную ЗА целью не выбрасывается, а отодвигается за круг обхода). Уцелевшим считаются поля
расстояний — поэтому набор считается **один раз на выборку**, а маршрут лишь разыгрывает
номер. «Сектора» разброса — это не углы, а **дальность от прямой вход→цель**: «центр» берёт
ближнюю треть списка, «края» — дальнюю половину, «середина» — середину. Замер 18.09.2026
(эталон движения, запас 129 км): из 20 узлов доживает **11**, по силам при этом запасе
**8.8**, пулы одного входа — 3 / 4 / 4. Разбор —
[РАССТАНОВКА_И_ДВИЖЕНИЕ §2.6](РАССТАНОВКА_И_ДВИЖЕНИЕ.md).

⚠️ **Возвраты по своей трассе давала точка обхода, а не виляние.** Участок обязан был войти
в саму ячейку VIA и шёл обратно; теперь VIA достигается в 3 км (`VIA_REACH_KM`), а позади
своей трассы стоит запретный сектор 140° на 2 км (`BACK_SECTOR_KM`). Форму маршрутов
проверяет `tools/motion_check.py` — у контрольного прогона она невидима. Разбор с замерами —
[план 11](../архив/11_ПЛАН_МОДЕЛЬ_ДВИЖЕНИЯ.md), [РАССТАНОВКА_И_ДВИЖЕНИЕ §2.5](РАССТАНОВКА_И_ДВИЖЕНИЕ.md).

## 5. Запрос: куда ставить датчики

**Главный элемент.** `place_sensors` — развилка; `_place_by_routes` — основной путь;
`CoverageCache.greedy` — сам выбор.

**Как это в коде** — `CoverageCache.greedy`, сердце расстановки:

```python
while len(chosen) < min(N, self.C):
    new_min = np.minimum(n_vec[:, None] + H, k)        # кратность с НАСЫЩЕНИЕМ на k
    gain_n  = (new_min - cur_min[:, None]) / k         # прирост кратности
    new_pop = _popcount(mask_vec[:, None] | M)         # сколько сегментов пути накрыто
    gain_m  = (new_pop - cur_pop[:, None]) / Lseg      # прирост ДОЛИ ДЛИНЫ маршрута
    primary = (a1 * gain_n + a2 * gain_m).mean(axis=0) # усреднение ПО МАРШРУТАМ выборки

    if   primary.max()   > 1e-9:   score = primary     # 1) основной
    elif secondary.max() > 1e-12:  score = secondary   # 2) прирост покрытой доли
    else:                          score = covsum      # 3) ⚠️ резерв кратности
    c = int(np.argmax(np.where(avail, score, -np.inf)))
```

**Что здесь важно, построчно:**

| Строка | Смысл |
|---|---|
| `np.minimum(…, k)` | после `k`-й засечки прирост **нулевой** — это и делает функцию субмодулярной, отсюда гарантия (1 − 1/e) |
| `_popcount(… \| M)` | маршрут нарезан на `L_seg` сегментов и хранится **битовой маской**: «покрыть ещё кусок пути» — это `OR` масок, а `popcount` считает результат |
| `.mean(axis=0)` | усреднение **по маршрутам**, а не по клеткам. Вот где видно, что единица покрытия — маршрут |
| `[:, None] + H` | прирост считается сразу для ВСЕХ кандидатов матрицей: цикл по кандидатам был бы в сотни раз медленнее |

⚠️ **Три ключа — лексикографика, а не сумма.** Вторичный смотрится, только когда основной
у всех нулевой. Складывать их нельзя: слабый вторичный перебивал бы настоящий прирост.

⚠️ **Без третьего ключа датчики уходили в угол карты.** При насыщении `score` обнулялся у
всех, и `argmax` брал **первого по порядку массива** — позицию без единого пролёта. Замер:
**4 из 12** датчиков не ловили ничего. `covsum` («сколько маршрутов кандидат вообще
накрывает») даёт осмысленный резервный порядок.

**Важное.**

⚠️ **Почему «жадно» здесь не значит «плохо».** Функция покрытия **субмодулярна**: каждый
следующий датчик приносит не больше предыдущего на том же месте. Для таких функций
доказано, что жадный выбор даёт **не хуже (1 − 1/e) ≈ 63 %** от оптимума. Это гарантия с
доказательством, а не «как получится».

⚠️ **Единица покрытия — МАРШРУТ, а не клетка.** Ценность считается по каждому маршруту
выборки, тремя ключами: кратность засечки (с насыщением на `k`) → **доля длины пути под
наблюдением** → сколько маршрутов кандидат вообще накрывает.

⚠️ **Третий ключ — не украшение.** Без него на насыщенной задаче прирост обнулялся у всех
кандидатов, и выбор брал первого по порядку массива: датчики уходили в угол карты. Замер:
**4 из 12 не ловили ни одного пролёта**.

⚠️ **Есть запасной путь по клеткам веса** (`_place_by_weight`) — но он включается, только
если маршрутов меньше пяти. В обычной работе не используется.

Подробно — [МЕТОДИЧКА_МОДЕЛИ_МАРШРУТОВ §5.3](../модель/МЕТОДИЧКА_МОДЕЛИ_МАРШРУТОВ.md).

| круг в расчёте | `threat_grid.py` :: `set_area_circle`, `in_area`, `ThreatGrid.set_outside_mask`; `threat_routes.py` :: `passable_mask`, `_open_endpoints` |
| окно «Сектор налёта» | `view_qt/sector_window.py` :: `SectorDialog`; режим кликов — `_begin_sector`, `_end_sector_mode` |
| сектор по 360°, раствор и число точек | `threat_grid.py` :: `set_sector_auto`, `set_sector_params`, `compute_entry_points` |
| пауза повтора по углу | `threat_routes.py` :: `sample_one_route`, `_azimuth_span` |
| точки старта мышью | `threat_view.py` :: `_begin_edit_entry`, `_edit_entry_click`, `_entry_handle_moved`; `threat_grid.py` :: `add_manual_entry`, `move_entry`, `remove_entry` |

**Как устроено перетаскивание** — у датчиков и точек старта одинаково, три шага:

```python
# 1) ЩЕЛЧОК: ближайший объект, но не дальше 25 точек экрана (допуск в ПИКСЕЛЯХ)
best = min(rows, key=lambda r: (r["x_km"] - x) ** 2 + (r["y_km"] - y) ** 2)
if d > 25.0 * self._km_per_pixel():  return            # мимо
# 2) МЕТКА: pyqtgraph сам ведёт её за мышью и сообщает об отпускании
h = pg.TargetItem(pos=(row["x_km"], row["y_km"]), movable=True)
h.sigPositionChangeFinished.connect(self._entry_handle_moved)   # у датчика — _edit_handle_moved
# 3) ОТПУСТИЛИ: модели уходят СТАРАЯ и новая координата; отказ — метка назад
if not self.on_entry_move(row["x_km"], row["y_km"], x1, y1):
    h.setPos(row["x_km"], row["y_km"])                  # за район не переносится
```

⚠️ **`TargetItem`, а не свои обработчики мыши.** У сцены pyqtgraph есть сигнал клика, но нет
пары «нажал — веду — отпустил»; тащить вручную пришлось бы, отключая панораму вида, иначе
карта едет вместе с объектом.

⚠️ **Объект ищется по КООРДИНАТЕ, а не по номеру строки.** Номер меняется от любой правки —
после переноса он указывал бы на другой датчик или другую точку.

⚠️ **Перенесённое становится «заданным человеком».** Датчик уходит в `manual_sensors`, точка
сектора — в `manual_entries`: иначе следующий пересчёт вернул бы их на место. У точек входа
поэтому три поля (`_sector_pts`, `manual_entries` и итоговый `entry_points`), а итог собирает
только `_compose_entries`.

**Окно «Сектор налёта»** — ничего не считает, всё через колбэки:

```python
# view_qt/sector_window.py: раствор и число точек — через 0.5 с после последнего шага счётчика
self.spin_angle.valueChanged.connect(self._params_changed)    # перезапуск таймера
self._timer.timeout.connect(self._apply_params)               # → on_params(полураствор, n)
# threat_view.py: окно одно; колбэки в lambda — контроллер подменяет on_* позже
SectorDialog(self, on_params=lambda h, n: self.on_sector_params(h, n), on_auto=...,
             on_click_mode=self._begin_sector, on_clear=lambda: self.on_clear_sector())
# режим кликов: левая — ось заново, правая — выход и закрытие окна
if self._sector_mode and right:  self._end_sector_mode(close_window=True)
```

Модель: `set_sector_params` → `_apply_sector` → `compute_entry_points` (раствор и N из `Params`);
«Построить» — `set_sector_auto` (`sector_kind = "auto"`, доли по 10°). Состояние окну отдаёт
`ThreatController._sector_state`. Разбор цепочки и ловушек — [СЕКТОР_И_НАЗНАЧЕНИЯ §1.8](СЕКТОР_И_НАЗНАЧЕНИЯ.md).

**Радиус мышью** — тот же конвейер, что у рамки:

```python
# threat_view.py :: _end_area — у круга первая точка центр, вторая на окружности
if self._area_shape == "circle":
    self.on_set_area_circle(x0, y0, ((x1 - x0) ** 2 + (y1 - y0) ** 2) ** 0.5)
# threat_grid.py :: set_area_circle — описанный квадрат через set_area, затем сам круг
self.set_area((lo, la, ho, ha)); self.area_circle = (cx, cy, R)
```

**Круг поверх квадратной сетки:**

```python
gx, gy = self.grid.cell_centers_km()
self.grid.set_outside_mask(~self.in_area(gx, gy))    # вес 0 за окружностью
pas &= ~np.asarray(out, bool)                        # passable_mask: ПОСЛЕ буфера
pas &= ~np.asarray(out, bool)                        # _open_endpoints: ПОСЛЕ открытия концов
```

⚠️ **Маска вычитается последней в обоих местах.** Буфер ухода от ориентира выводит коридор на
1 км наружу, открытие концов — на 3 км: первая редакция забыла второе, и область залёта заходила
за круг R = 25 км на 249 ячеек (нашёл `flow_check`, раздел 5а).

**Пауза по углу** — только при точках, разнесённых шире 180°, и по стартам **дошедших**
маршрутов: в секторе 60° правило запретило бы всё и сдвинуло эталоны; по попыткам — 28 нарушений
на 150 маршрутов, по дошедшим — 0.

Подробно: [РАЙОН_И_ДАТЧИКИ_МЫШЬЮ](РАЙОН_И_ДАТЧИКИ_МЫШЬЮ.md) — §1 режимы мыши, §2.5 круг, §3.3
перетаскивание датчиков, §3а точки старта · [СЕКТОР_И_НАЗНАЧЕНИЯ §1.5–1.7](СЕКТОР_И_НАЗНАЧЕНИЯ.md) —
сектор по 360°, три поля точек входа, пауза по углу · [план 11 §5в](../архив/11_ПЛАН_МОДЕЛЬ_ДВИЖЕНИЯ.md) —
задание и решения Р1–Р13.

## 6. Как это разложено по файлам

Строгий **MVC**: модель не знает о показе, показ не считает.

| Слой | Файлы | Что делает |
|---|---|---|
| **модель** | `threat_grid.py` · `threat_routes.py` · `optimization.py` · `trajectories.py` · `sensor_track.py` | вся математика, **без Qt** |
| **показ** | `threat_view.py` · `geomap.py` · `tile_layer.py` · `map_image.py` · `basemap_mixin.py` · `input_window.py` · `area_choice.py` · `sector_window.py` | только рисует и принимает ввод |
| **связь** | `threat_controller.py` | кнопки, пересчёт, отчёты |
| **параметры** | `config.py` | ВСЕ общие числа и умолчания в одном месте |
| **область** | `area_file.py` (только stdlib) · `geo_cache/<область>/область.txt` | рамка, район и файлы конкретной области |

⚠️ **`model/` не тащит Qt намеренно** — иначе модель нельзя проверить скриптом. Все семь
проверок программы работают именно за счёт этого.

⚠️ **Формула перевода координат одна** — `model/geo_frame.py`; `geomap.py` её импортирует,
а сам от `config` не зависит (у вкладки 2 свой район).

✅ **Закрыто 13.09.2026: тайлы больше не разъезжаются со слоями.** Тайлы нарисованы в Web
Mercator, остальное считается в км-фрейме. Пока подложка была одной картинкой, на отдалении
они расходились на 11 px; поштучная укладка оставляет 0.71 px —
[ПОКАЗ_ТАЙЛОВ](ПОКАЗ_ТАЙЛОВ.md). ⚠️ **Открыт соседний вопрос:** множитель `cos(lat0)` берётся
на широте якоря, и расстояния по X в районе расчёта завышены на 3.72 % — круг радиуса 30 км
накрывает 31.1 км. На совпадение со слоями это не влияет. Разбор —
[план 10 §0.2в](../планы/10_ПЛАН_ПРОЕКЦИЯ_И_ОСТАТКИ.md), вопрос В5.
