## 1. Откуда брался пик: что хранит кэш покрытия

Жадный выбирает место датчика по таблице «маршрут × кандидат». Её строит `CoverageCache`: на каждый маршрут выборки —
строка из трёх чисел на каждого кандидата:

| Поле | Тип | Байт | Смысл |
|---|---|---|---|
| `hit` | uint8 | 1 | засекает ли датчик в этом месте маршрут (0/1) |
| `mask` | uint32 | 4 | какие из `L_seg` участков маршрута он видит — битами |
| `cov` | float32 | 4 | доля точек маршрута в его зоне, 0…1 |

**Пример.** Эталон: T = 250 маршрутов × C = 4 367 кандидатов = 1 091 750 пар × 9 байт = **9.4 МБ** — сам кэш мал.
Пик давали **временные** таблицы: при построении строки (§2) и на каждом шаге жадного (§3, §4).

⚠️ **Кандидат (место) — это точка, где датчик МОЖНО поставить, а не поставленный датчик:** в эталоне мест 4 367,
датчиков из них выбирается 20. **Пара** — одна клетка таблицы «маршрут и место»; «9 байт на пару» — столько
хранится на клетку. Пар бывает две: постоянная «маршрут × место» и временная «точка маршрута × место» (§2).
Для чтения без кода, с примерами — Word `docs/Маршруты_и_датчики.docx`, разделы 17а–17г.

## 2. Приём 1 — расстояния кусками (`add_trajectory`)

**Было** (коммит `ced6e1c`):

```python
diff = traj[:, None, :] - self.cand[None, :, :]   # (точек, C, 2) — разности сразу со всеми кандидатами
d = np.linalg.norm(diff, axis=2)                  # (точек, C) — расстояния
within = d <= self.R                              # точка в зоне кандидата
```

`norm` в numpy 2.5.0 по одной оси устроен так (исходник):

```python
s = (x.conj() * x).real                           # conj — КОПИЯ массива, произведение — ещё один
return sqrt(add.reduce(s, axis=axis))
```

То есть на пару «точка × кандидат» разом живут: `diff` (2 × 8 байт) + копия от `conj` (16) + произведение (16) =
**48 байт**. Замер: маршрут 444 точки × 4 367 кандидатов — пик **88.8 МБ = 48 байт на пару**. С двумя целями и
радиусом 0.5 км кандидатов много — **619 МБ** на один маршрут.

**Стало:**

```python
step = max(1, int(block) // max(1, len(traj)))    # кандидатов в куске: 2¹⁹ пар / точек маршрута
for a in range(0, self.C, step):
    b = min(a + step, self.C)                     # кусок кандидатов [a, b)
    d = traj[:, 0, None] - self.cand[None, a:b, 0]    # dx, потом расстояние, (точек, кусок)
    dy = traj[:, 1, None] - self.cand[None, a:b, 1]   # dy
    d *= d; dy *= dy; d += dy                     # dx² + dy² — на месте, без новых массивов
    np.sqrt(d, out=d)                             # √ — туда же
    within = d <= self.R
    hit[a:b] = within.any(axis=0)                 # в заранее заведённые строки — срезом
    cov[a:b] = within.mean(axis=0)
    ...                                           # маска участков — так же, срезом [a:b]
```

**Пример.** Маршрут 444 точки: 2¹⁹ = 524 288 пар / 444 = **1 180 кандидатов в куске**; пик куска — **8.5 МБ** вместо
88.8. В живой расстановке `add_trajectory` — 12.7 МБ и у эталона, и у двух целей: пик больше не растёт с числом кандидатов.

**Почему биты те же.** Для вещественных чисел `conj(x) = x`, значит `s` — это `dx²` и `dy²`, а `add.reduce` по оси из
двух чисел — **одно сложение** `dx² + dy²`. Новый код делает ровно эти действия: умножение, сложение, корень. Совпадение
**по построению**, а не по случаю; замер подтверждает: 1 000 000 случайных пар — 0 расхождений; 2 858 пар ровно на
радиусе — строки кэша совпали. Кусок не влияет: у каждой пары своё расстояние, соседи в счёт не входят.

**Размер куска** (замер: 40 маршрутов × 20 000 кандидатов; прежний код — 2.96 с и 405.6 МБ):

| Кусок | Время | Пик |
|---|---|---|
| целиком | 1.03 с | 148.5 МБ |
| 2¹⁶ | 1.13 с | 8.6 МБ |
| 2¹⁸ | 1.06 с | 13.2 МБ |
| **2¹⁹** (взят) | **0.98 с** | **19.4 МБ** |
| 2²⁰ | 0.97 с | 31.9 МБ |

Мелкий кусок — больше оборотов цикла Python; крупный — больше памяти без выигрыша. **Втрое быстрее** прежнего даже
целиком: меньше проходов по памяти — нет трёхмерной разности, копии от `conj` и отдельного массива под корень.

⚠️ **`np.hypot` не взят.** На этой машине он тоже совпал (0 из 1 000 000, 0 из 200 000 пар у границы), но только **по
замеру**: это функция C-библиотеки, её округление на другой платформе не обязано совпасть с `norm`.

## 3. Приём 2 — кэш без утяжеления типов (`greedy`, `joint_greedy`)

**Было:** жадный складывал строки кэша в таблицы, **переводя их в более тяжёлые типы**:

```python
H = np.asarray(self._hit, dtype=np.int64)         # 1 байт → 8
M = np.asarray(self._mask, dtype=np.uint32)       # 4 → 4
Fc = np.asarray(self._cov, dtype=np.float64)      # 4 → 8   итого копия 20 байт на пару
```

**Стало:** `dtype=np.uint8` и `np.float32` — **9 байт** на пару, как хранится. Эталон: 20.8 → 9.4 МБ.

**Почему числа те же.** numpy сам расширяет младший тип до старшего **перед** действием:

| Действие | Тип результата (замер `np.result_type`) | Пример |
|---|---|---|
| `n_vec` int64 + `H` uint8 | int64 | 3 + 1 = 4 — то же целое |
| `cur_cov` float64 + `Fc` float32 | float64 | float32(0.3) = 0.30000001192092896 — в float64 то же число без потерь |

Замер: `cov64 + F32` и `cov64 + float64(F32)` на 1 000 000 пар — равны все.

⚠️ **Где легко сломать — сумма `uint8`.** `H.sum(axis=0)` у `uint8` даёт **`uint64`** (замер), а у беззнакового
минус «переворачивается»: `-uint64(5)` = **18 446 744 073 709 551 611**. `flow_check` сортирует
`argsort(-routes_covered_by_candidate())` — порядок сломался бы молча. Поэтому везде `sum(axis=0, dtype=np.int64)`.

## 4. Приём 3 — приросты шага на месте (`gain_rows`)

На каждом шаге жадный считает прирост у **всех** кандидатов разом — таблицу T × C.

**Было:** каждое выражение заводило новую таблицу, и все они жили до конца шага:

```python
new_min = np.minimum(n_vec[:, None] + H, k)       # таблица 1 (и временная под сумму)
gain_n = (new_min - cur_min[:, None]) / k         # 2 (и временная под разность)
new_pop = _popcount(mask_vec[:, None] | M)        # 3
gain_m = (new_pop - cur_pop[:, None]) / Lseg      # 4
primary = avg(a1 * gain_n + a2 * gain_m)          # 5, 6, 7 — a1·…, a2·… и их сумма
new_cov = np.minimum(cur_cov[:, None] + Fc, 1.0)  # 8 — второй ключ (§5)
gain_cov = avg(new_cov - cur_cov[:, None])        # 9
```

**Стало** — вложенная функция, которая пишет в уже заведённое место и сразу отпускает лишнее:

```python
def gain_rows(late=False):
    t = n_vec[:, None] + H                         # засечек с кандидатом, int64
    np.minimum(t, k, out=t)                        # не больше k — в ту же таблицу
    g = t - cur_min[:, None]                       # прирост кратности, float64
    del t                                          # целая таблица больше не нужна
    p = _popcount(mask_vec[:, None] | M)           # покрытых участков с кандидатом
    gm = p - cur_pop[:, None]                      # прирост участков
    del p
    if late:                                       # граница после цикла: (a1·Δ)/k
        g *= a1; g /= k; gm *= a2; gm /= Lseg
    else:                                          # шаг цикла: a1·(Δ/k)
        g /= k; g *= a1; gm /= Lseg; gm *= a2
    g += gm
    return g                                       # primary = avg(gain_rows())
```

**Пример.** Жадный эталона вместе с копиями §3: пик **87.7 → 34.5 МБ** — с ~84 до ~33 байт на пару «маршрут × кандидат».

**Почему биты те же.** `g *= a1` — то же умножение, что `a1 * g` (умножение в IEEE перестановочно), только результат
кладётся в старое место. Вычитание, деление, сложение — те же, над теми же числами.

⚠️ **Где легко сломать — порядок округления.** `a1·(Δ/k)` и `(a1·Δ)/k` в математике равны, в машине — нет. Замер:
режим «пересечение» (a1 = 0.75), Δ = 1, k = 5: `0.75 * (1/5)` = **0.15000000000000002**, `(0.75 * 1) / 5` = **0.15**.
Прежний код в цикле считал первое, а в границе после цикла (`last = a1 * (…) / k + …`) — второе. Отсюда флаг `late`:
сведи оба случая к одному — и при равных приростах жадный может выбрать другое место. У режимов «сбалансированный»
(0.5) и «распределение» (0.25) расхождений нет при k ≤ 6: умножение на степень двойки точное.

В `joint_greedy._Kind.gains` порядок свой, и он тоже сохранён: разность считается **в целых** (`t -= min(n, k)`), потом
делится на k.

## 5. Приём 4 — второй ключ только когда нужен (`cov_rows`, `cov_gains`)

Ключей выбора три, лексикографикой: основной (кратность и участки пути) → второй (доля пути) → третий (число маршрутов).
Второй смотрится, **только когда основной у всех нулевой** — а считался прежде на каждом шаге (таблицы 8–9 в §4).

**Стало:**

```python
if primary.max() > 1e-9:
    score = primary                                # основной растёт — второй не нужен
else:                                              # основной насыщен — только теперь второй
    secondary = SPREAD_EPS * avg(cov_rows())
    score = secondary if secondary.max() > 1e-12 else covsum
```

**Пример** (замер `sys.setprofile` — счёт вызовов): эталон — `gain_rows` 21 раз (20 шагов и граница), `cov_rows` —
**ни разу**; МОГ + ПВН — `gains` 32 раза, `cov_gains` — **ни разу**. Прежде второй ключ считался все 20 и 32 раза впустую.

**Почему числа те же.** `secondary` читался только в ветке `elif` — посчитать его там же ничего не меняет.

## 6. Как проверено, что ничего не сдвинулось

1. **Снимок до бита** — шесть обстановок до правки и после: эталон; МОГ + ПВН своей k; одна k с разносом; датчик,
   заданный человеком; две цели при кратности защиты 2 и 1. Позиции датчиков записаны как `float.hex` (точное двоичное
   значение, без округления печати), типы, оценки зазора, доля засечённых, отчёт этапа целей. Сравнение строк — **0
   расхождений** из 6. Каждая обстановка — два прогона подряд, тоже одинаковых.
2. **Строки кэша** — новый `add_trajectory` против копии прежнего кода: 40 маршрутов × 20 000 кандидатов, каждый 7-й
   кандидат ровно на радиусе от точки маршрута (2 858 пар у границы) — до бита при любом куске.
3. **Проверки программы** — `reference_run` («ВСЁ СОШЛОСЬ С ЭТАЛОНОМ»), `flow_check`, `metrics_check`.

⚠️ **Почему именно до бита.** Жадный сравнивает приросты: сдвиг в последнем знаке меняет выбор при равенстве, дальше
расходится вся расстановка — и эталон уже не отличить от поломки.

## 7. Где легко сломать — сводка

| Место | Нельзя | Почему |
|---|---|---|
| `add_trajectory` | заменить √(dx² + dy²) на `hypot` или сравнение квадратов `d² ≤ R²` | совпадение с `norm` держится по построению; у этих — другое округление (у квадратов не проверялось) |
| `gain_rows(late)` | свести `late` к одному порядку | 0.15000000000000002 ≠ 0.15 (§4) |
| суммы `uint8` | `H.sum(axis=0)` без `dtype=np.int64` | `uint64`, минус переворачивается (§3) |
| `gain_rows`, `cov_rows` | вынести в метод без передачи состояния | читают `n_vec`, `mask_vec`, `cur_*` из замыкания — их переставляет `take` (`nonlocal`) |
| взвешенное `avg = W @ X` | резать по кандидатам (шаг 7) без сверки до бита | BLAS может сложить иначе на куске другой ширины |

## 9. Шаг 9 — строки кэша нарастающим итогом (`RowStore`, 30.09.2026)

**Что было.** При «Пуске» датчики пересчитываются каждые 5 маршрутов (`THREAT_SENSOR_REFRESH_EVERY`), и
`place_sensors` каждый раз строил кэш покрытия **с нуля по всей накопленной выборке**: на 1 000 маршрутах — 1 000 строк
«маршрут × кандидат», из которых новых только 5. Кэш — 70–78 % цены пересчёта ([оптимизация §4б](../оптимизация/README.md)).

**Почему можно не пересчитывать.** Строка кэша (засекает ли, какие сегменты, доля пути в зоне — §1) зависит только от
**маршрута, кандидата, радиуса и числа сегментов**. Ни k, ни другие маршруты, ни расстановка в неё не входят. Выборка
при итерациях растёт **с хвоста** (`iter_routes.append`), значит строки старых маршрутов по тем же кандидатам — те же.

**Как сделано** (`src/model/placement/optimization.py :: RowStore`, `src/model/threat/threat_grid.py :: ThreatModel._row_cache`):

```python
# хранилище типа: постоянные кандидаты и строки уже посчитанных маршрутов
if n > len(routes) or any(a is not r for a, r in zip(self.routes, routes)):   # выборку сменили
    b = self.base = CoverageCache(b.cand, b.R, b.L_seg, 1)                     # — всё заново
for r in routes[n:]:                                                           # новые — счётом
    b.add_trajectory(r)
...
full._hit, full._mask, full._cov = H, M, F     # готовые матрицы (T, C + E)
```

1. **хранилище на тип** — `self._row_stores[номер типа]` (у одиночного типа 1 — `"lone"`); `fits` сверяет кандидатов,
   радиус, сегменты — сменились (зона пролёта, шаг сетки, R) — хранилище заводится заново; выбывшие типы убираются;
2. **выборка — по ссылкам**: если первые n маршрутов — те же объекты (`is`), досчитываются только `routes[n:]`; новая
   выборка, «Очистить», загруженная история — всё заново;
3. **то, что меняется от расстановки к расстановке**, — позиции у целей (этап целей) и закреплённые человеком — идёт
   **отдельными столбцами** `extra` по всей выборке: их единицы–десятки, это дёшево;
4. кэш запроса получает **готовые матрицы** `(T, C + E)`: `greedy` и `joint_greedy` берут их `np.asarray` без копии.

**Почему до бита.** Столбец кэша считается независимо от соседей: расстояние от каждой точки маршрута до кандидата,
`any` и `mean` по точкам (§2). Склейка «хранимые столбцы + столбцы `extra`» даёт ровно те же числа, что один кэш на всех
кандидатах. Стартовые строки чужих датчиков (`_pre_*`) пусты — `greedy` берёт нули, как и прежде.

**Пример.** 1 000 маршрутов, у эталона 4 400 кандидатов: прежде на каждом пересчёте — 4.4 млн пар «маршрут × кандидат»
(каждая — все точки маршрута), теперь — 22 тыс. (5 новых маршрутов) плюс склейка матриц.

**Замер** (`arh`, 250 настоящих маршрутов, повторённых до T; скрипт `step9_check.py` в scratchpad сессии):

| T | эталон 20 × 2 км: пересчёт · с нуля | МОГ 10 × 1 + ПВН 20 × 0.5 |
|---|---|---|
| 250 | **0.19 с** · 0.73 с | **0.46 с** · 1.56 с |
| 500 | **0.31 с** · 1.43 с | **0.56 с** · 2.89 с |
| 1 000 | **0.71 с** · 3.55 с | **1.14 с** · 5.89 с |

До бита: 12 расстановок (две обстановки × T = 5, 10, 15, 50, 55, 250 — выборка растёт с хвоста) против кэша с нуля —
позиции, типы, оценки зазора совпали все. `reference_run` на одной выборке: старый и новый код — одна кратность 6.2533.

**Попутно.** Повторная «Расставить датчики» на той же выборке (сменили N, режим, кратность) строки не пересчитывает вовсе.

**Где легко сломать.**

| Место | Нельзя | Почему |
|---|---|---|
| проверка выборки | сравнивать маршруты по числам (`array_equal`) или только по длине | по ссылкам — O(T) и точно; по длине — новая выборка той же длины прошла бы как старая |
| маршрут после добавления | менять массив маршрута на месте | хранилище этого не заметит — строки устареют молча |
| `extra` | переносить в хранилище позиции этапа целей | они меняются каждую расстановку: `fits` сбрасывал бы хранилище каждый раз |
| `routes_covered_by_candidate` | `if not self._hit` | строки бывают матрицей — у неё `not` неоднозначен (исправлено на `len(...) == 0`) |
| память | держать хранилища выбывших типов | у каждого T × C × 9 байт (1 000 × 4 400 — ~40 МБ); `_row_cache` оставляет только живые |

## 10. Потоки: «Пуск» и «Пакетно» в фоне, линии дописыванием (план 13.5, 13.5.11; шаг 11)

**Где:** `src/controller_qt/iter_worker.py :: IterWorker` (поток «Пуска») · `src/controller_qt/threat_controller.py :: _start_worker`, `_stop_worker`, `_on_worker_sensors`, `_on_worker_ended`, `_anim_tick`, `_iter_batch_work` · `src/view_qt/tabs/threat_view.py :: iter_show_accumulated` (§5 разбора [ПОКАЗ_ГРАДАЦИЙ_И_СЛОЁВ](ПОКАЗ_ГРАДАЦИЙ_И_СЛОЁВ.md)).

**Как работает.** «Считать в фоне — принимать в главном». Поток строит маршруты (`iter_step`) и раз в 5 маршрутов ставит датчики (`place_sensors`), отдаёт результат сигналами; Qt доставляет их в главный поток очередью событий, и там они рисуются. Две договорённости держат модель целой: семафор — не больше 2 маршрутов впрок (расстановка в такт показу), событие — после расстановки поток ждёт, пока главный дорисует датчики. «Пакетно» — выборка и расстановка одной функцией в пуле потоков (`_run_async`), главный только рисует.

**Суть простыми словами.** Расчёт и показ разделены на два потока. Фоновый поток строит маршруты и расставляет датчики, главный поток только выводит готовые результаты на карту и обрабатывает действия пользователя — поэтому окно не замирает. Фоновый поток держит наготове не больше двух построенных маршрутов, иначе изображение отстанет от расчёта; после расстановки датчиков он ждёт, пока главный поток их отобразит, — иначе изменил бы данные, которые в этот момент выводятся на экран.

```python
class IterWorker(QtCore.QThread):
    """Поставщик маршрутов «Пуска». Вход: модель, шаг пересчёта датчиков (маршрутов), запас маршрутов впрок.
    Сигналы: `route_ready(маршрут)`, `sensors_ready(маршрутов)`, `ended(причина)` — done · exhausted · stopped · error."""

    route_ready = QtCore.pyqtSignal(object)          # маршрут (M,2) км построен — в очередь анимации
    sensors_ready = QtCore.pyqtSignal(int)           # датчики пересчитаны по стольким маршрутам — нарисовать
    ended = QtCore.pyqtSignal(str)                   # поток закончил: почему

    FAILS_MAX = 40                                   # неудачных розыгрышей подряд — выборка исчерпана (как прежде)

    def __init__(self, model, refresh_every, start_at=0, ahead=2):
        super().__init__()
        self.model = model                           # модель — общая с главным потоком
        self.every = max(1, int(refresh_every))      # пересчитывать датчики каждые столько маршрутов
        self.at = int(start_at)                      # при скольких маршрутах датчики уже пересчитаны
        self._slots = threading.Semaphore(int(ahead))   # мест «впрок»: маршрут построен, анимация его ещё не взяла
        self._ack = threading.Event()                # главный поток дорисовал датчики — можно трогать модель
        self._stop = threading.Event()               # просьба остановиться (пауза, «Очистить», другая кнопка)

    def consumed(self):
        """Анимация взяла маршрут — освободить место впрок. Вход: нет. Отдаёт: ничего. Зовётся из главного потока."""
        self._slots.release()

    def drawn(self):
        """Датчики нарисованы — потоку можно дальше. Вход: нет. Отдаёт: ничего. Зовётся из главного потока."""
        self._ack.set()

    def stop(self):
        """Попросить остановиться: поток доделает текущий шаг и выйдет. Вход: нет. Отдаёт: ничего."""
        self._stop.set()
        self._slots.release()                        # разбудить, если ждёт места
        self._ack.set()                              # и если ждёт отрисовки

    def _place(self, n):
        """Пересчитать датчики и дождаться, пока главный их нарисует. Вход: маршрутов в выборке. Отдаёт: ничего."""
        self.model.place_sensors()
        self.at = n
        self._ack.clear()
        self.sensors_ready.emit(n)
        self._ack.wait()                             # модель не трогать, пока её рисуют

    def run(self):
        """Цикл потока: маршрут → в очередь → раз в `every` маршрутов датчики. Вход: нет. Отдаёт: ничего."""
        m = self.model                               # модель
        fails = 0                                    # неудачных розыгрышей подряд
        try:
            while not self._stop.is_set():           # пока не попросили остановиться
                if m.iter_iteration >= m.iter_target_count():   # набрали число из панели
                    n = len(m.iter_routes)           # маршрутов в выборке
                    if n >= self.every and n > self.at:   # итоговая расстановка — по всей выборке
                        self._place(n)
                    self.ended.emit("done")
                    return
                self._slots.acquire()                # не уходить вперёд анимации больше чем на `ahead`
                if self._stop.is_set():              # пока ждали — попросили остановиться
                    break
                route = m.iter_step()                # маршрут; None — розыгрыш не удался
                if route is None:                    # неудача — место впрок не занято
                    self._slots.release()
                    fails += 1
                    if fails > self.FAILS_MAX:       # выборка иссякла
                        self.ended.emit("exhausted")
                        return
                    continue
                fails = 0
                self.route_ready.emit(route)
                n = len(m.iter_routes)               # маршрутов в выборке
                if n >= self.every and n - self.at >= self.every:   # пора пересчитать датчики
                    self._place(n)
            self.ended.emit("stopped")
        except Exception as e:                       # noqa: BLE001 — текст ошибки — в заголовок окна
            self.ended.emit("error: %s" % e)
```

    w.start()

def _anim_tick(self):
    """Один кадр анимации (таймер 33 мс). Если текущий маршрут «долетел» — берём из
    модели следующую итерацию и начинаем её; иначе сдвигаем маркер БПЛА вперёд по
    текущему маршруту. По завершении всех итераций — расставляем датчики и рисуем всё."""
    # начать новый маршрут, если предыдущий долетел
    if self._cur_route is None:
        # ⚠️ МАРШРУТ СТРОИТ ПОТОК (13.5.11в): здесь — только показ; очередь пуста — поток ещё считает, окно свободно
        if not self._route_queue:                     # показывать нечего

                self._full_metrics()

def _iter_batch_work(self, fn=None):
    """«Пакетно» в фоне: выборка и итоговая расстановка (13.5.11а). Вход: чем строить выборку (по умолчанию
    `iter_batch`). Отдаёт: ничего. Окна не трогает."""

    n = len(self.model.iter_routes)                   # маршрутов в выборке

**Замер** (`arh`, 250 маршрутов; скрипт `thread_measure.py` в scratchpad): «Пуск» — главный поток дольше всего занят **0.31 с**, проходов цикла событий дольше 0.1 с — 7 из 3 874; «Пакетно» — **0.03 с**, 0 из 1 481. Прежде главный поток стоял на каждом маршруте (0.09–0.30 с) и на каждой расстановке (0.2–5.9 с).

**Пример с расчётом.** 250 маршрутов, датчики раз в 5 маршрутов, `ahead` = 2.
1. поток строит маршруты 1 и 2 → очередь [1, 2], мест впрок 0; третий ждёт на семафоре;
2. кадр анимации берёт маршрут 1 (`consumed` → место освободилось) → поток строит 3 → очередь [2, 3];
3. после маршрута 5 — расстановка; поток стоит на `_ack`, пока главный не нарисует датчики (`drawn`), и только потом строит 6. За прогон 250 / 5 = **50 расстановок** — каждая в фоне;
4. **прежде** главный поток стоял на каждом маршруте не меньше 0.09 с: 250 × 0.09 ≥ **22.5 с** замёрзшего окна только на маршрутах, плюс 50 расстановок по 0.2–5.9 с (оценка снизу по формуле). **Теперь** — дольше всего 0.31 с один раз за прогон (замер выше).

**Повторяемость.** Поток строит маршруты один и в прежнем порядке — выборка до бита та же, что у старого «Пуска» (`gui_check` 27: 12 из 12; отдельно — розыгрыш, розыгрыш с расстановкой и поток совпали). ⚠️ Попутная находка: история стартов (`_recent_entries`, `_recent_ok_entries`) `iter_reset` не сбрасывает — два прогона подряд при нескольких точках входа расходятся с первого маршрута и без потока (вопрос В13.5.5).

| Где легко сломать | Почему |
|---|---|
| трогать окна или виджеты из `run` | Qt разрешает это только главному потоку — падение или порча окна |
| убрать ожидание `_ack` после расстановки | поток поменяет `sensors`, пока главный их рисует (датчиков 18, типов 17) |
| запустить «Пакетно» или «Шаг», не остановив поток | два потока меняют одну модель |
| сигналы без `QueuedConnection` | обработчик может пойти в потоке, а не в главном |
| запускать розыгрыш в нескольких потоках | порядок случайных чисел сменится — эталоны разойдутся (шаг 4 очереди) |
